# Поддерживаемое оборудование

Полный целевой охват AR-DV1 и ограничения по прошивке/опциям:
[аудит официальной документации](ardv1/README.md). Он отделяет имеющийся
FM/AM serial-срез от ещё не реализованных цифровых, SD и memory-функций.

## Транспортные протоколы

| Схема | Описание | Модуль |
|---|---|---|
| `scpi` | SCPI по TCP/IP (порт 5025, Telnet-подобный или raw-socket) | `devices/scpi.py` |
| `vxi11` | VXI-11 через TCP/IP | `devices/scpi.py` (`Vxi11Instrument`) |
| `serial` | SCPI через последовательный порт (RS-232/USB) | `devices/serial_scpi.py` |
| `soapy` | Универсальный интерфейс SoapySDR | `devices/soapy.py` |
| `rtl` | RTL-SDR через `rtl_tcp` | `devices/rtl.py` |
| `sim` | Встроенный генератор измерений | `devices/simulator.py` |

## Программный стенд общего сеанса

Модуль `device_workers.py` дополняет прежний генератор панорам двумя явными адаптерами нового `/api/v1` контура:

| Адаптер | Результат | Управление |
|---|---|---|
| `tinysa-sim` | Непрерывные свипы, целые Гц и исходные `dBm`; `generator_output=off` | Независимые запуск и остановка потока |
| `ardv1-sim` | Наблюдения с исходными `s_meter_count`, шумоподавителем и имитацией цифрового режима | Независимые запуск, остановка и перестройка через очередь |
| `tinysa-serial` | Архивные свипы с целыми Гц и исходными `dBm`; identity, безопасный setup, `scan` | Явный порт, отдельный transport, `output off`, закрытие |
| `ardv1-serial` | Наблюдения с исходными `s_meter_count`, FM/AM, точный RF, LM | Явный порт, перестройка через очередь, EX при закрытии |

Адаптеры выбираются только через `DeviceStream.settings.adapter`. Симуляторы проверяют архив, конкурентную работу, перестройку, изоляцию сбоев и ручной handoff кандидата на частоту AR-DV1 без остановки tinySA. Дополнительные `tinysa-serial` и `ardv1-serial` используют отдельный POSIX-транспорт на worker и выполняют только документированные команды: tinySA — identity, `output off`, input/LNA setup и `scan`; AR-DV1 — RE1/VR/RN, VFA, FM/AM, RF, LM и EX при закрытии. DMR/TETRA и другие цифровые режимы в этом срезе не отправляются. `hardware_control=true`, но `hardware_validation_not_run=true`: последовательность команд и изоляция сбоев проверены scripted transport, а не физическим стендом.

### Исправления безопасности serial и происхождение частоты

На Windows ядро использует COM backend pySerial вместо `termios`; POSIX
backend остаётся прежним. Разбор ответов общий, настройка обоих приборов
не меняется. Транспорт и формы трёх клиентов описаны в
[windows-core-serial.md](windows-core-serial.md). Native COM/USB и аппаратура
пока не проверены; автоматического переподключения нет.

Серверный POSIX transport на Python 3.10+ задаёт raw 8N1 и baud через
`tcgetattr`/`tcsetattr` (поля скоростей 4/5), а не отсутствующие в Python
`cfmakeraw`/`cfsetispeed`/`cfsetospeed`. Исходные tty-атрибуты восстанавливаются
при закрытии и ошибке настройки, fd закрывается и при ошибке восстановления.
Запись ограничена общим тайм-аутом; nonblocking retry не создаёт бесконечного
ожидания. Проверка на PTY не является проверкой физического serial порта.

`tinysa-serial` проверяет ответ каждой команды безопасной настройки:
`output off`, `mode input`, `lna off`, `attenuate auto`, `rbw <kHz>` и `calc off`.
Поддержанный формат успешного setup-ответа: единственный завершающий `ch>`
на отдельной строке, необязательное точное эхо текущей команды и пустое тело.
Пробелы, табуляция и пустые строки допускаются. `ERROR`, usage/help, неизвестный
текст (включая неподдержанный `OK`), чужое/повторное эхо, лишние prompt,
не-ASCII/управляющие байты и незавершённый ответ отвергаются. Одно эхо команды
без prompt или наступление quiet timeout не подтверждают успех.
Завершённое однозначное обрамление обязательно также для identity и scan,
чтобы их запоздалый prompt не подтвердил следующую настройку.
Для scan сохранён прежний формат с одним дополнительным начальным `ch>`:
он допустим только вместе с полным набором точек и завершающим prompt,
но никогда не принимается как подтверждение setup.

Первый отказ, timeout, частичная запись или transport/protocol error немедленно
останавливает последовательность. Следующие setup/scan не отправляются, sweep
не создаётся. Соединение помечается `restart_required=true`: повторные poll,
включая автоматические попытки worker, больше не читают и не отправляют байты.
Нужны остановка и новый старт потока с новым transport; автоматического retry,
flush/resync и команд восстановления на неопределённом соединении нет.
Ошибки последующего scan также закрывают возможность повторного обмена на
этом соединении. Close только закрывает transport и восстанавливает tty.

До полного setup `generator_output=unknown`,
`generator_output_source=unconfirmed`. После полного успешного setup в
details и settings свипа указаны `generator_output=off`,
`generator_output_source=command_acknowledged` и `generator_output_readback=false`.
После ошибки или закрытия состояние и источник становятся `unknown`.
Это принятие команд в поддержанном shell-протоколе, не измерение RF-выхода
и не query/readback. У протокола нет идентификаторов транзакций; формат prompt
не доказывает отсутствие посторонних изменений или ручного управления.
Общие метаданные `hardware_validation=not_run` сохраняются: ACK не доказывает
фактическое отключение RF-выхода. Ограниченная проверка конкретной firmware
на физическом приборе описана в разделе аппаратного стенда ниже.
FIFO-тесты и собственные POSIX PTY проверяют отказы всех setup-шагов,
частичные/запоздалые ответы, отсутствие scan/retry и восстановление tty.

`ardv1-serial` не присваивает частоту из settings наблюдению LM без настройки.
Перед первым poll выполняются identity, VFA, FM/AM и RF с явными terminal ACK.
Явная команда tune сразу настраивает запрошенную частоту, без предварительной
перестройки на default. Частично выполненная или не подтверждённая настройка
сбрасывает известные частоту/режим в null и помечает соединение как
неопределённое (`restart_required=true`). После timeout, transport/protocol error, неподходящего ACK или
некорректного LM дальнейшие poll/tune не отправляют команд и не записывают
наблюдений. Нужны остановка и новый старт исполнителя с новым transport,
а не повторная настройка на том же соединении: старый запоздалый ACK мог бы
подтвердить другую команду. На неопределённом соединении close не отправляет EX.
Запрошенные значения сохраняются отдельно как `requested_frequency_hz`/`requested_mode`.

У подтверждённых команд `frequency_source=command_acknowledged`,
`mode_source=command_acknowledged`, `frequency_readback=false` и
`hardware_validation=not_run`. Это факт ACK команды в поддержанном протоколе,
не измеренная частота, не query/readback и не гарантия отсутствия ручной
перестройки прибора. Позиция RE1-кода, реальные ACK и работа на оборудовании
остаются непроверенными. Исходный `s_meter_count` не преобразуется в dBm.

## Аппаратный стенд tinySA Ultra

Ограниченная приёмная проверка на macOS и исправление ожидания длительного
`scan` описаны в [tinysa-hardware-acceptance.md](tinysa-hardware-acceptance.md).
Quiet 250 мс теперь является интервалом опроса, а не концом shell-ответа;
полный prompt ждём до общего deadline без ослабления fail-closed проверки.
Это не подтверждение AR-DV1, native Windows COM или всех подключений: общие
метаданные `hardware_validation=not_run` остаются консервативными.

## Ожидание ответа tinySA

Общий POSIX/Windows framing ждёт завершающий `ch>` до общего deadline:
3 с для identity/setup, 90 с для scan. Интервал quiet 250 мс задаёт только
опрос, а не конец ответа: после эха, между строками и частями prompt возможны
длительные паузы. Новый байт не продлевает deadline. Неполный ответ вызывает
ошибку и `restart_required`; поздний prompt не используется для новой команды.
AR-DV1 продолжает использовать отдельный `read_line` и строгие terminal ACK.

Источник изменения и границы проверки интеграции:
[tinysa-prompt-integration.md](tinysa-prompt-integration.md).

### Примеры подключения

```bash
# Agilent/Keysight N9020A по TCP/IP
python3 -m radioinspector scan \
    --connection "scpi://192.168.1.20:5025?instrument=mx&points=801" \
    --start 30e6 --stop 130e6 --bandwidth 100e3 --cycles 60 --output /tmp/data

# Rohde & Schwarz FSQ3 по TCP/IP
python3 -m radioinspector scan \
    --connection "scpi://192.168.1.30:5025?instrument=fsq" \
    --start 30e6 --stop 130e6 --bandwidth 100e3 --cycles 60 --output /tmp/data

# SoapySDR использует форму soapy://driver=uhd,serial=...
# Подключение/настройка/освобождение проверяются только синтетически.
# Калиброванный sweep не реализован, поэтому не используйте legacy scan для съёмки.
# Прямой sweep() отказывает без I/O, но CLI scan сначала открывает архив и подключение.

# RTL-SDR по rtl_tcp
python3 -m radioinspector scan \
    --connection "rtl?host=127.0.0.1&port=1234" \
    --start 88e6 --stop 108e6 --bandwidth 1e6 --cycles 30 --output /tmp/data
```

Полный перечень схем подключения:

```bash
python3 -m radioinspector devices
```

## Ограничения драйверов

* Драйверы реализуют **базовый** набор команд SCPI
  (`FREQ`, `BAND`, `SWE`, `CAL`, `TRAC`, `MKR`, `FORM`, `OUTP`), достаточный
  для панорамирования и снятия трасс. Сервисные подменю конкретных
  моделей (калибровка по внутреннему меню, загрузка таблиц коррекции,
  переключение траекторий) не реализованы — их документация в руководстве
  оригинала приведена в общем виде.
* Автоматическое определение модели и типа прибора не выполняется: параметры
  указываются в строке подключения.
* Работа с приборами, требующими аутентификации (GPIB-контроллер с
  паролем), не поддержана.

### Политика приёма tinySA Ultra ZS405

Serial-адаптер использует ограниченный [приёмный профиль](tinysa-receive-profile.md):
100 кГц–800 МГц, 2–290 точек, запрос RBW 10/30 кГц, точное совпадение
поддержанного firmware. Это лимиты приложения, не все возможности Ultra.
Неизвестные модель/firmware отклоняются до setup; недопустимые параметры —
до открытия порта. Новые sweep различают requested, command ACK и отсутствие
readback. Старые архивы не изменяются; старые живые потоки вне профиля
теперь потребуют отдельного подтверждённого профиля.
