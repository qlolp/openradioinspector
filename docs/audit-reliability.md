# Исправления надёжности по аудиту 10 ноября 2026

## Изменённое поведение

1. Все POST ограничены до чтения тела. Обычный предел — 64 КиБ; одиночные
   измерения, batch и аудиокадры — 16 МиБ. Специальные пределы анализа
   сохранены. Общий срок чтения тела — 10 с; неверные запросы не меняют архив.
   Подробности и коды ошибок: [API v1](api-v1.md).
2. JSON/NDJSON-импорт учитывает одновременно число записей и фактический
   размер UTF-8 запроса. Слишком большая одиночная запись отвергается до
   первого POST. Форматы, ID и атомарность пакета сохранены.
3. Если исследование явно запрашивает режим, для завершения подходят только
   наблюдения этого режима. `mode=null` оставляет режим неограниченным.
   Правило одинаково для памяти, SQLite и автоматического завершения.
4. tinySA различает RF off и режим input/output/unknown. Получение raw/zero
   требует подтверждённого командами input; подтверждение не является
   физическим readback. Возврат после генератора выполняется через
   monitor.resume. Ручные изменения и неопределённый обмен инвалидируют режим.
5. Trace.decimate включает неполную последнюю корзину и сохраняет исходный
   максимум. Собственные алгоритмы отображения трёх клиентов не заменены.

Исторические результаты и исходные измерения не переписаны, миграции БД нет.
API остаётся v1; поле capabilities с лимитом пакета и сведения device_mode
добавлены без удаления прежних полей.

## Три уровня проверки

Быстрый прогон из checkout:

```sh
python -m pip install -e '.[serial,test]'
./run_tests.sh
```

Он может пропускать opt-in HTTP/Tk-сценарии. Наличие таких пропусков не
означает прохождения полного релизного gate. При отсутствии venv launcher
использует uv с локальным проектом и extras serial,test, не создавая lock-файл.
Явно активированный VIRTUAL_ENV имеет приоритет над локальным .venv.

Полный синтетический gate требует NumPy, pySerial, Node и работающего Tk:

```sh
# Linux без desktop:
xvfb-run -a python -m tests.run_release_checks --report-dir release-reports
# Windows или машина с доступным desktop:
python -m tests.run_release_checks --report-dir release-reports
# macOS с Xcode, включая оба Swift-пакета и unsigned build:
python -m tests.run_release_checks --swift --report-dir release-reports
```

Runner сохраняет отдельный run-* для каждого запуска: summary.json,
python-results.json (если Python suite успел запуститься), журналы команд и
fixtures. Сводка содержит исходную ошибку и ошибки cleanup. Отчёты остаются
после неуспеха и прерывания с выполненным cleanup; SQLite, приватные HOME и
build-каталоги не копируются. Каталог release-reports исключён из Git;
существующая CI-матрица выгружает отчёты как artifacts со сроком хранения 14 дней.

На Linux/macOS неожиданные skips запрещены. На Windows сохранён список
конкретных POSIX-исключений и добавлены ровно две проверки POSIX shell
launcher с причиной `POSIX shell launcher`; новые произвольные пропуски
по этому тексту не допускаются.

## Отдельная аппаратная приёмка — не выполнена

Синтетический успех не подтверждает COM/USB, метрологию или физическое RF off.
Перед физической проверкой использовать существующие процедуры
[tinySA](tinysa-hardware-acceptance.md) и
[полного управления](tinysa-full-control.md), подготовить предусмотренный
ими стенд и явно включить lab/RF только действиями оператора.

- Проверить цепочку generator → output.off: статус остаётся output;
  acquire.raw/acquire.zero отклоняются, приёмные команды не отправляются.
- Выполнить monitor.resume, проверить mode input и получение исходного
  sweep/raw с реальными UTC-интервалами. Отдельно измерить RF/CAL off на
  предусмотренном стенде: ACK нельзя считать измерением уровня выхода.
- После ручного меню, аппаратного пресета и self-test проверить unknown и
  запрет acquisition до явного возврата. При сбое USB проверить tainted,
  отсутствие скрытого повтора и независимую работу второго прибора.
- Для AR-DV1 проверить исследование FM с наблюдением AM на той же частоте:
  завершение запрещено; после подходящего FM-наблюдения разрешено. Сохранять
  исходные s_meter_count, без преобразования в dBm.

Стендовые измерения и журналы хранить вне Git. В акте проверки указать версии
прошивки/ПО, оборудование, условия и фактический результат каждого сценария.
