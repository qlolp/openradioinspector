# Радиомониторинг и исследование

Оба режима используют одно ядро и API v1. Выбор рабочего экрана локален
клиенту и не останавливает приборы или запись. Начальный экран research
сохраняет доступность прежних аналитических панелей; monitoring выделяет
приборы, спектр и проект. Только явное управление ядром меняет сбор.

## Этап 1: проекты и подготовка

`GET/POST /api/v1/monitoring-projects`, `GET /{id}` и `GET /{id}/preflight`
создают и читают проект из выбранного двухприборного сеанса. Требуются
name, site, session_id; роли и исходные единицы проверяются до записи.
Симуляторы выбираются явно. Создание проекта и preflight не открывают порты.
Поле ready означает проверки конфигурации, не аппаратную приёмку или наличие
эталона. baseline_ready показывается отдельно. Аппаратная проверка not_run.
Для последовательных приборов preflight проверяет заданные порты, скорости,
частоту и совместимость режима AR-DV1 с выбранным профилем без открытия портов.
Также проверяются период и параметры повторов исполнителей. На Windows
используется та же проверка имён COM-портов, что и при создании transport.
Списки проектов во всех клиентах читаются страницами по 200 записей; переход
между страницами сохраняет выбранный проект, включая только что созданный.

Проекты хранятся добавочной версионированной схемой в том же SQLite и через
тот же writer ядра. Старые измерения и PRAGMA user_version не переписываются.
В memory-only сервере проекты временные. Страничный список ограничен 200
записями, максимум 1000, after — последний ID предыдущей страницы.

WebUI, Windows и macOS предоставляют создание проекта, выбор и preflight.
Исходные dBm и s_meter_count не преобразуются друг в друга. Интерфейсы
не содержат драйверов. Эталоны, обнаружение, охрана и история доступны через
описанные ниже ресурсы; само создание проекта не запускает приборы.

## Этап 2: эталон и детектор

POST /{id}/baselines с name/location/confirm=true фиксирует до 256
совместимых полных свипов, минимум 20 и 60 с. При высокой частоте обзора
используется равномерная выборка интервала вместе с последними 20 свипами;
ограниченный хвост памяти не сокращает интервал эталона. Версии неизменяемы; источники
сохраняются полностью. Отдельная адаптивная поправка не меняет эталон.
POST /{id}/allowed добавляет диапазон в целых Гц и имя; watch_changes=false
исключает совпадения из тревог, но не из исходного архива.

POST /{id}/analyze с {} обрабатывает до 64 новых записанных свипов.
Порог — max(6 dB, 3*1.4826*MAD) над P95 эталона с ограниченной тихой
поправкой. Подтверждение 3/5; импульс >=12 dB регистрируется сразу.
Широкополосное изменение >=половины бинов — одно отдельное событие.
Сначала обнаружение, затем адаптация только спокойных/неразрешённых бинов.
Подавляемые каталогом бины исключаются до широкополосной и плотной агрегации;
их уровень не становится пиком сводной тревоги. При разделении события на
несколько участков один исходный свип учитывается в его доказательствах один раз.
Переход ниже порога с гистерезисом 3 dB на пяти последовательных свипах
закрывает событие; отсутствие данных не означает отсутствие сигнала.

GET /{id}/events и /baselines возвращают ограниченные списки, GET
/{id}/events/{event} и /baselines/{baseline} — детали. Полные связи
свипов хранятся отдельно; в событии не более 100 последних source_refs.
POST /{id}/events/{event}/review с disposition задаёт операторский
вердикт, не меняя техническое состояние исследования или исходники.
Изменения источника и несовместимость сетки блокируют применение эталона.
События и курсор фиксируются одной транзакцией; повторная обработка не
создаёт дубликаты. Детектор не является классификатором протоколов/IQ.

### Охрана и AR-DV1

`POST /{id}/arm {}` явно ставит проект на охрану. Нужны подтверждённый
эталон, подходящие приборы и сохраняемый SQLite-архив. Создаётся новый сеанс;
предыдущие измерения остаются в архиве. `POST /{id}/disarm {}` останавливает
исполнителей проекта, `GET /{id}/status` показывает состояние и причины ошибки.
Выбор рабочего экрана клиента не вызывает эти команды.

Ядро обрабатывает свипы независимо от AR-DV1. Свежие узкополосные события
анализируются первыми; по одному исследованию на приёмник, без повторного
запуска уже обработанного события. Начальный интервал — 10 секунд после
подтверждённой настройки. Отсутствие сигнала при последующем приёме не отменяет
исходное обнаружение. Ручные старые маршруты перестройки заблокированы для
приборов, принадлежащих охране.

`POST /{id}/configure {"receiver_mode":"AUTO"}` выбирает режим следующего
сеанса. Новый `ardv1-monitor-v1` использует документированные MD-команды,
VR2504A и читает `MDdan` после LM. AUTO не включает TETRA. Подтверждённый
декодированный режим связан с конкретным наблюдением; S-meter остаётся в
исходных отсчётах. Старый профиль FM/AM не меняется. Статус профиля —
проверен синтетическим transport, физическая приёмка **не выполнена**.

Аналоговый выход AR-DV1 подключается к АЦП компьютера ядра. Для этого нужны
extra `audio`, PortAudio и явно выбранный вход: `GET /audio-inputs`, затем
`POST /{id}/configure {"audio":{"device":0,"name":"точное имя","confirm":true}}`.
Ни один вход не выбирается автоматически. При исчезновении/смене имени входа
запись не начинается; отсутствие аудио видно в результате. WAV начинается
после успешной перестройки, без предыстории предыдущей частоты. Прерывание
владения отменяет запись. Исходные WAV хранятся в общем архиве артефактов;
`GET /{id}/events/{event}/audio` отдаёт связанную запись. Все три клиента
предоставляют выбор входа и прослушивание записи.

Если эталон снят после просмотра панели tinySA, охрана повторяет подтверждённую
консервативную RX-подготовку и восстанавливает контекст команд. Произвольные
изменения тракта не воспроизводятся молча: несовместимый контекст блокирует
готовность и постановку на охрану. Исторические измерения не переписываются;
подтверждение команд по-прежнему не является физическим RF readback.

Для старых эталонов без поля периода обзора ядро восстанавливает медиану
по соседним доступным исходным свипам. Пропущенные ссылки не соединяются в
увеличенный интервал. Используются только временные метки и идентификаторы:
полные спектры для этого не загружаются. Восстановленный параметр применяется
как производное состояние; замороженная версия эталона не изменяется.
Если соседних источников недостаточно, preflight блокирует постановку на
охрану и предлагает собрать новый эталон. Сбор замены доступен после проверки
приборов и архива: он не требует пригодности прежнего эталона. Исследовательский анализ не
выдумывает период и не диагностирует прямые разрывы по неизвестной частоте
обзора; обратный ход времени по-прежнему сбрасывает окно подтверждения.
Новые эталоны хранят измеренную медиану периода отдельно.

### Ручное исследование и поиск источника

Ручной захват выполняется отдельно для роли `receiver` или `analyzer`:
`POST /{id}/manual/acquire {"role":"receiver"}` возвращает частный token на
30 секунд. `manual/renew {"token":"…"}` явно продлевает владение;
`manual/return` принимает и истёкший token. Истечение оставляет автоматизацию
на паузе. Потерянный token сбрасывается снятием проекта с охраны. Token
хранится в памяти клиента и не входит в публичное состояние проекта.
Проверка владельца повторяется при выполнении команды из очереди.
`manual/tune {token,frequency_hz,mode}` перестраивает только AR-DV1;
его автоматическая очередь приостановлена, tinySA продолжает обзор.

После захвата анализатора `search/start {token,event_id,span_hz}` создаёт
отдельный сеанс узкого обзора. UI явно показывает приостановку широкого
покрытия. `search/status` возвращает до 256 исходных максимумов со временем,
общий накопленный максимум и ручные отметки; `search/mark {token,label}`
связывает отметку положения со свипом. Это не автоматическое определение
координат или направления. Потеря узкого worker переводит покрытие в паузу,
сохраняя независимый приёмник. Возврат перезапускает широкий профиль с новым
соединением и допускает детектор после совместимого полного свипа.

`GET /{id}/history` читает до 64 свипов в обратном порядке UTC с непрозрачным
`after`. Фильтры: `start`, `end` (UTC), `min_hz`, `max_hz`, `event_id`.
История охватывает все сеансы проекта, включая поиск источника. Для рисования
ядро выбирает не больше 320 точек с max-агрегацией; ответ `display_only=true`
не заменяет исходник. `/history/{sweep_id}` возвращает полный исходный свип,
`/history/{sweep_id}/comparison` — сравнение с подтверждённым эталоном;
несовместимость сетки/настроек возвращается явно. `/events/{event_id}/sources`
постранично перечисляет все ссылки доказательств. Водопад клиентов использует
настоящие UTC-интервалы и оставляет временные разрывы видимыми.

Проекты мигрируются в схему 2: добавлены связи сеансов и индексы запросов.
Исходные таблицы измерений и формат экспортируемых измерений не изменяются.

### Автономная работа, тревоги и место

Схема проектов 3 добавляет постоянный журнал тревог и очередь webhook.
`GET/POST /{id}/settings` настраивает `autostart`, бюджет `archive`,
параметры `detector` и `webhook`. По умолчанию восстановление и webhook
выключены. Адрес и секрет вводит оператор; пустой секрет в клиентах не
отправляется и сохраняет прежний. Секрет хранится отдельно от публичного
проекта в SQLite ядра: защищайте доступ к файлу архива. API, диагностические
поля и журнал доставки секрет не возвращают.

`GET /{id}/alerts?limit=50&after=…` читает до 100 тревог на страницу;
`POST /{id}/alerts/{alert}/ack {}` подтверждает тревогу. Подтверждение не
подменяет операторский вердикт события и результат AR-DV1. Звук локален для
клиента и выключен по умолчанию; начальная загрузка старых тревог бесшумна.
Клиенты опрашивают журнал только GET-запросами, независимо от выбранного
рабочего экрана. При новом сеансе охраны live-панорама следует за ним один раз;
последующее ручное открытие истории не перебивается каждым опросом.

Webhook передаёт JSON с постоянным `notification_id`. Заголовки:
`X-OpenRadioInspector-Notification-ID` и
`X-OpenRadioInspector-Signature: sha256=<HMAC-SHA256 точных UTF-8 байтов тела>`.
Получатель должен дедуплицировать ID: при сбое после приёма возможна повторная
доставка. Максимум пять попыток; задержки 10/20/40/80 секунд. Перенаправления
не выполняются, содержимое ответа не читается и не попадает в журнал.
Результаты `sent`, `pending`, `failed`, `disabled` и число попыток видны в UI.
Поздний ответ не может изменить результат более новой попытки. После
прерванной последней попытки сохраняется ошибка неопределённого результата.

`GET /{id}/storage` показывает свободное место, резерв, поток и прогноз
хранения. Начальные значения: резерв 256 МиБ и не менее часа прогнозируемого
хранения. Прогноз использует фактический рост архива и консервативное окно
исходных свипов; это оценка, учитывающая общий архив ядра. Неизвестная скорость
отображается явно. Перед запуском проверяется возможность записи, затем она
контролируется периодически даже при ручном владении обоими приборами.
Недостаток места/ошибка записи переводит охрану в ошибку. Если SQLite уже не
может сохранить тревогу, критическое состояние остаётся в памяти и в API;
такой журнал помечен `volatile` и не переживает перезапуск. Исходники никогда
не удаляются автоматически.

После отдельного `autostart:true` ядро восстанавливает только ранее активную
охрану, создавая свежий сеанс после проверок. Явное снятие с охраны отменяет
намерение восстановления. Старые прерванные исследования помечаются отдельно
и повторно не запускаются. Непрошедшая проверка оставляет ошибку, а не цикл
неограниченных попыток управления приборами.

В SQLite завершённые сеансы/кандидаты/исследования больше не загружаются
целиком при старте. В памяти остаются активные графы заданий и хвост не более
128 неактивных записей каждого типа. Поиск старого ID читает SQLite без роста
кэша. Старые полные API-списки сохранены для совместимости; новые клиенты
используют ограниченные страницы истории и тревог.

### Завершение подготовки и проверка первого выпуска

Мастер сохраняет декларации оператора через `POST /{id}/preparation`
(`antenna_notes`, `receive_path_confirmed`, `location_confirmed`). Для serial
обе декларации обязательны перед сбором и охраной; явные симуляторы не требуют
ложного подтверждения физической антенны. `preparation/start {}` создаёт
приёмный сеанс и начинает сохранение исходников. `preparation/stop {}` явно
останавливает сбор. GET preflight показывает фактическое количество и
UTC-длительность в `baseline_collection`; это не утверждение о чувствительности
или физическом RF readback. Автоматический запуск генератора отсутствует.

Шесть стартовых параметров детектора редактируются отдельно от webhook и
архива, только после снятия охраны. Кнопка «Сбалансированный» заполняет форму;
сохранение выполняется явно. Событие хранит снимок параметров и версию
`robust-city-v1`. Длительный разрыв данных сбрасывает окно 3/5 и создаёт
отдельную запись качества с исходным ID. Плотная совокупность более 32
отдельных превышений представляется `dense_change` с числом областей и
глобальным пиком, а не молча обрезается. Широкие/плотные изменения не
выдаются автоматическому приёмнику за одну несущую.

При потере USB одного прибора исправный продолжает регистрацию. Статус
`degraded` явно показывает неполную связку, AR-очередь недоступного приёмника
приостановлена; отсутствие широкого анализатора отмечается `unavailable`.
Ручной возврат приёмника создаёт новое соединение при необходимости и
подтверждает профиль. Старая ручная аренда не управляет новым соединением.
При ошибке архива останавливается охрана целиком. Исследовательский экран
не отключает эти проверки.

Полный release runner теперь выполняет и ускоренную семидневную приёмку:

```bash
python -m tests.run_release_checks --report-dir release-reports
# На macOS с Xcode: добавить --swift
# Отдельный синтетический прогон, без приборов:
python -m tests.monitoring_endurance --report /tmp/monitoring-endurance.json
```

JSON с количеством сохранённых/проверенных свипов, разрывами, памятью,
размерами архива и сравнением детекторов входит в CI artifacts вместе с
журналами, включая неуспешный gate. Быстрый `./run_tests.sh` выполняет штатные
регрессии; полный runner дополнительно поднимает контролируемые fixtures и
исполняет семидневный сценарий. Методика, ограничения синтетики и пустой
протокол восьмичасовой/длительной физической приёмки находятся в
[протоколе](monitoring-hardware-acceptance.md). Непроверенное оборудование не
объявляется принятым на основании успешного CI.

Схема проектов 4 нормализует только индекс времени метаданных; события и
эталоны читаются от новых к старым с ограниченными страницами. История всех
сеансов хранится в нормализованных связях, а рабочий проект держит лишь хвост
ID последних 128 сеансов. UTC/Гц исходных измерений не переписываются.

### Перенос полного архива

Согласованная копия SQLite включает все исходные свипы, наблюдения, WAV,
связи, эталоны и события. Для переноса используйте отдельный файл:

```bash
python -m radioinspector.monitoring.archive_backup \
  --source /path/to/core.sqlite --output /path/to/portable.sqlite
```

Команда поддерживает работающий SQLite-источник, не перезаписывает его и не
заменяет существующий выходной файл. Перед публикацией копии выполняются
integrity/foreign-key checks. В переносимой копии удаляются секреты webhook
(включая свободные страницы), отключаются доставки и автозапуск, сбрасываются
физические декларации; исходный архив остаётся прежним. Нужен запас места
на согласованную копию и её уплотнение. На новом узле файл задаётся обычным
параметром архива ядра; порты, антенна, место и аудиовход проверяются заново.
Существующие форматы потокового импорта/экспорта измерений сохранены.
