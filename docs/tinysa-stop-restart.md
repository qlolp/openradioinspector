# tinySA: остановка и повторный запуск

Реализовано в Python core: новые клиенты запрашивают штатную остановку через
`POST /api/v1/sessions/{session_id}/streams/{stream_id}/stop` или
`POST /api/v1/sessions/{session_id}/workers/stop` с `{"mode":"graceful"}`.
Сначала клиент проверяет `GET /api/v1/capabilities`:
`features.graceful_device_stop` должно быть `true`. Старый сервер может
проигнорировать неизвестное поле и выполнить прежнюю принудительную остановку.

Штатная остановка возвращает ответ сразу после запроса остановки. Текущий свип
завершается, проверяется, записывается в архив; следующий не начинается.
Worker закрывает порт в собственном потоке. Клиент опрашивает список workers:
`stopping: true`, `stop_mode: "graceful"`, `alive: true` означают ожидание;
только `alive: false` подтверждает освобождение исполнителя. Состояние сеанса
при остановке workers остаётся running. Остановка самого сеанса сохраняет
прежнее синхронное поведение.

`{"mode":"force"}` явно отменяет I/O и ожидает завершения не более прежнего
лимита (5 секунд). Отсутствие mode сохраняет прежнюю force-семантику для старых
клиентов. Force может усилить уже запрошенную graceful остановку. Отменённый
свип не архивируется. Типизированная отмена не увеличивает consecutive_errors
и не публикует device.error; настоящие ошибки ввода-вывода продолжают
регистрироваться. Неизвестный mode отклоняется. Во время остановки новые
команды отвергаются, повторный старт живого worker запрещён.

## Повторное соединение

Перед **первой** командой нового соединения worker выполняет ограниченное
чтение остаточных байтов. Само открытие tinySA больше не вызывает явную очистку
входного буфера transport: это сохраняет доступный завершающий prompt.
Для каждого реального порта core хранит монотонный срок незавершённой команды.
После прерывания требуется отдельный завершающий `ch>` и 300 мс тишины.
До этого не отправляются info/version/deviceid, setup или scan. Максимум
ожидания — остаток бюджета прежней команды (для scan 90 секунд) плюс 3 секунды.
Если prompt не получен, соединение признаётся непригодным: никакой новой
команды и автоматического повтора не выполняется. Поздний scan никогда не
становится подтверждением info. Полученные при восстановлении данные
отбрасываются и не получают новых временных меток.

Новое соединение без известной незавершённой команды проверяет 300 мс тишины;
если приходят байты, оно также требует завершающий prompt (общий лимит 3 с).
Проверка input перед каждой последующей командой остаётся строгой: никакой
очистки буфера в середине транзакции или слепого повтора.

Ограничения: сведения о незавершённой команде живут в процессе core, а не на
диске. После аварии/замены процесса молча выполняющийся свип нельзя доказуемо
обнаружить по USB без отдельного аппаратного протокола синхронизации.
Потерянный prompt приводит к явной ошибке восстановления, даже если прибор
уже простаивает. ОС/драйвер могут очищать буфер при открытии независимо от
явных вызовов transport. Снятие такой блокировки требует подтверждения
готовности прибора; код не пытается угадать её по истечению таймаута.

## Проверка

Детерминированные тесты `tests/test_tinysa_stop_restart.py` проверяют graceful,
force, ошибки, паузу старого scan, фрагментированный prompt, ограниченный
таймаут и отсутствие команд при неудачной синхронизации. Windows transport
проверяется синтетическим COM; POSIX сценарии используют только PTY.
Аппаратная проверка этим изменением не заявляется: её результаты должны
фиксироваться отдельно с версией core, firmware и параметрами свипа.
