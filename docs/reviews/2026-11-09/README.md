## 1. Вердикт

**Что это.** Амбициозный open-source аналог коммерческого комплекса RadioInspector: одно измерительное ядро (Python, HTTP/SSE `/api/v1`, SQLite-архив, независимые device workers) и три клиента — WebUI (Raspberry Pi), Windows Tk, macOS SwiftUI. Кодовая база за 6 дней развития: ~60 тыс. строк Python (из них ядро 28,9 тыс., Windows-клиент 7,9 тыс., тесты 29,6 тыс.), 21,2 тыс. строк Swift (101 файл), 6,8 тыс. строк JS (26 файлов), 8,1 тыс. строк документации.

**Общая оценка.** Для проекта, развиваемого одним владельцем с ИИ-агентами, инженерный уровень заметно выше среднего: архитектурные инварианты («единственный писатель архива», «один worker на прибор», целые Гц/UTC, атомарные миграции, составные внешние ключи) реально соблюдаются, тесты объёмные и не «вакуумные», документация честно фиксирует, что аппаратная приёмка не выполнена. Это хороший **alpha-прототип**, а не релиз-кандидат.

**Почему не готов к релизу/публичному продвижению:**

1. **Безопасность (P0).** HTTP API полностью без аутентификации: любой хост в локальной сети анонимно создаёт/запускает сеансы, управляет приборами, включает планировщик, читает и экспортирует весь архив. Для сценария «ядро на Raspberry Pi + удалённые клиенты» это компрометация комплекса. Дополнительно: DNS-rebinding обходит анти-CSRF-проверку, а неограниченный `Content-Length` даёт OOM в один запрос.
2. **Достоверность измерений (P1).** Подтверждены ошибки, из-за которых числа в протоколах неверны: dBmV считается без множителя 1e-3 (ошибка 60 дБ), `field_strength()` выдаёт «max dBm + калибровка» за напряжённость поля с единицей «dB», а неполный/повреждённый ответ SCPI-прибора молча превращается в измерение с пересчитанной частотной сеткой. Для измерительного ПО это хуже падения: ошибки не видны пользователю.
3. **Инженерные гейты (P1).** В CI нет ни линтера, ни проверки типов, ни покрытия. На русской Windows полный набор тестов красный (16 из 1518), а официальная команда `python -m tests.run_release_checks` сама падает с `UnicodeEncodeError` (`β` в cp1251) — CI маскирует это переменной `PYTHONUTF8=1`. Часть заявленных возможностей (Wi-Fi, аналитика сеансов, SCPI-драйверы) не подключена или не имеет тестов расчёта.
4. **Юридический блокер (P1).** Проект — открытая реализация коммерческого продукта; по собственной документации коммерческие материалы удалены из рабочего дерева, но **публичная история не очищена**, а вопросы происхождения/лицензий не закрыты. До релиза это необходимо решить, иначе публикация несёт правовые риски.

**Итог:** до `0.4.0-rc` нужно закрыть P0 и P1, добавить quality-гейты и получить аппаратную приёмку. Список конкретных шагов — в разделе 6.

**Сводка по severity (после дедупликации):** P0 — 1, P1 — 12, P2 — 22, P3 — ~10 (см. раздел 3). Сырых находок в четырёх отчётах — 48 (12+12+12+12), часть пересекается.

## 4. Детали важнейших находок

### P0-1. API без аутентификации (✅ воспроизведено)

`web/server.py` не содержит ни одной проверки `Authorization`/`Cookie` (0 совпадений по файлу). Анонимно: `POST /api/v1/sessions` → `201`, `POST …/start` → `200 running`, `POST /api/v1/task-scheduler {"enabled":true}` → `200`, `GET /api/v1/sessions` → полный список, экспорт архива — без ограничений. Поддержка сети штатная: `serve --host` и `core_main --host 0.0.0.0` (choices `127.0.0.1`/`0.0.0.0`), при этом `docs/api-v1.md:719-720` и `docs/release/installation.md:54-57` прямо пишут, что аутентификации нет и API нельзя выставлять в Интернет.

**Почему P0.** Для WebUI на Raspberry Pi удалённый доступ — заявленный сценарий; любой хост в LAN получает полный контроль над приборами и измерениями. Это не «недостающая функция», а свойство поставки.

**Исправление:** генерируемый при первом запуске shared-secret (файл в data-dir, `0600`), `Authorization: Bearer …` для всех `/api/v1/*` кроме `/health`; отказ стартовать при non-loopback bind без секрета; далее — TLS (stdlib `ssl`/reverse proxy) и роли «наблюдатель/оператор».

### P1-1. dBmV: ошибка 60 дБ (✅ воспроизведено)

```
convert(0.0, "dBmV", "V")  -> 1.0     # должно быть 0.001
convert(0.001, "V", "dBmV")-> UnitError
convert(0.0, "dBmV", "dBuV") -> UnitError
convert(120.0, "dBuV/m", "dBV/m") -> UnitError
```
Причина: `dbmv_to_v()` возвращает `10**(v/20)` в вольтах (dBmV — дБ относительно 1 мВ), `v_to_dbmv()` — обратная ошибка; конверсии относительных единиц уходят в ветку мощности и падают. **Исправление:** `*1e-3`/`*1e3`, отдельная ветка «относительные одной группы», property-based тест на 0 dBmV ↔ 1 мВ ↔ 60 dBµV.

### P1-2. `field_strength()` — не напряжённость поля (✅ воспроизведено)

`field_strength(Trace([-63,-61] dBm), calibration_db=6)` → `value=-55.0, unit="dB"`. Это «максимум dBm + коэффициент», а не дБ(мкВ/м); переход `P_dBm → E_dBµV/m` (+107 + AF для 50 Ом) не выполняется. В отчёте (`reporting.py:283`) печатается «Напряжённость поля: … дБ», при том что `docs/measurement-methods.md:33` относит методики E/U к нереализованным. **Исправление:** убрать из отчётов/CLI до реализации методики либо вернуть исходный dBm с явным `calibration_db`; при реализации — явная единица `dBµV/m` и валидация калибровки/антенного фактора.

### P1-3. SCPI: тихая порча исходных измерений (✅ воспроизведено частично)

```
_parse_numeric_payload("1.0,2.0,bad,3.0") -> [1., 2., 3.]   # «bad» молча выброшен
_parse_numeric_payload("1.0,2.0,1e999")   -> [1., 2., inf]  # inf не отфильтрован
sweep(points=801, 100..200 МГц), ответ 4 значения ->
  points=4, freq[0]=100e6, freq[-1]=200e6, step=33.33 МГц  # сетка «досочинена»
```
Не сверяются `count == points`, `*IDN?`, SCPI error queue, `np.isfinite`. **Исправление:** fail-closed — требовать точное число точек и конечность, иначе `InstrumentError` и пометка соединения негодным; проверять SCPI definite-length заголовок.

### P1-4. DNS-rebinding обходит Origin-проверку (✅ воспроизведено)

```python
origin = self.headers.get("Origin"); host = self.headers.get("Host", "")
if origin and origin not in ("http://" + host, "https://" + host): raise ... 403
```
При `Host == Origin == rebind.attacker.test:8770` запрос получает `201`; запрос без `Host` — тоже `201`. Анти-CSRF для классических cross-origin запросов работает (чужой Origin → 403, `Content-Type` не JSON → 415), но same-origin через rebinding проходит. **Исправление:** строгий allowlist `Host` (`127.0.0.1:<port>`, `localhost:<port>`, явно настроенное имя), отклонять отсутствие/несовпадение; корень — токен из P0-1.

### P1-5. Неограниченный Content-Length → OOM (✅ воспроизведено)

`Content-Length: 200000000` без тела → +190,9 МиБ в процессе; `10^15` → `MemoryError` в `server.py:419`. Роут-специфичные лимиты есть только у «аналитических» маршрутов (`_read_bounded_analysis_request:436-452`) — корректный паттерн применён не везде. Плюс: 30 полуоткрытых соединений держат 30 потоков >12 с; 40 SSE-подписчиков — +40 потоков без отказа. **Исправление:** прогнать все тела через bounded-reader с лимитом на маршрут; `connection.settimeout(10-15)`; пул соединений с `503` при переполнении; лимит SSE-подписчиков.

### P1-6. Дублирование измерений в журнале событий (✅ замерено)

Каждое измерение пишется дважды: в `sweeps`/`observations` и целиком в `events.payload_json` (`payload={"sweep": to_primitive(sweep)}`, `session_service.py:443,474,519,562`). Замер: 201-точечный свип — массивы 3218 Б vs payload 3487 Б; для 4096 точек payload 73 771 Б; 100 удержанных событий — 6,7 МБ `tracemalloc` (~65 КБ/событие). Следствия: ~2× диска/WAL, `--archive-max-bytes` срабатывает вдвое раньше, до ~65 МБ RSS на окно истории. **Исправление:** в событии хранить ссылку (`measurement_id`, `stream_id`, интервал, края, `points`, `level_unit`, sha256), массивы — только в профильной таблице.

### P1-7. Полная материализация кандидатов/исследований (✅ код)

`SessionService.__init__` грузит `store.load_candidates()`/`load_investigations()` (SELECT * без `WHERE session_id`/`LIMIT`), list-API обходит всё под общим `RLock` и делает `deepcopy`. Время старта/RAM O(N), а GET списка блокирует ingest приборных потоков. Риск уже зафиксирован самим проектом (P1.2 в `docs/repository-audit.md:77`), но не устранён. **Исправление:** keyset-пагинация `(started_at, id)`, ленивая загрузка по сеансу, `EXISTS`-проверка открытого исследования вместо линейного прохода; замер на 100k кандидатов.

### P1-8. JSON-экспорт архива под writer-lock (⚠️ код)

`GET /api/v1/sessions/{id}/archive/export` → `archive_measurements` → `list_sweeps(limit=None)` + `list_observations(limit=None)` под `SessionService._lock`, затем `to_primitive` и `json.dumps` в память. Для 8-часового сеанса — минуты удержания общего lock и сотни МБ RAM. При этом потоковый путь уже реализован: `archive_snapshot.open_archive_snapshot` + `iter_snapshot_ndjson` (disk-backed копия, вне writer-контура). **Исправление:** перевести JSON-маршрут на snapshot+пакеты (или удалить, оставив NDJSON), ограничить конкурентность экспортов.

### P1-9. Тесты и release runner не переносимы (✅ воспроизведено)

- `python -m unittest discover`: 1518 тестов, **16 уникальных тестов красные** на русской Windows/Python 3.11: 8 × `UnicodeDecodeError` (`test_webui_*.py` читают static через `read_text()` без encoding, cp1251), 2 сравнения кириллицы (`test_windows_sweep_occupancy.py:81,104`), 6 процессных тестов (`OwnedProcessTests`, WinError 32/TimeoutExpired).
- Официальная команда из README `python -m tests.run_release_checks` падает: `Release checks FAILED: 'charmap' codec can't encode character '\u03b2'` (β в диагностике; позиция 77634) даже без учёта самих тестов.
- CI маскирует: `.github/workflows/windows-core.yml:27-28` задаёт `PYTHONUTF8: '1'`, `PYTHONIOENCODING: utf-8` глобально.
- Python 3.11 (поддерживается `requires-python >=3.10`) вообще отсутствует в матрице CI (3.10/3.12/3.14).

**Исправление:** явный `encoding="utf-8"` во всех тестах и путях экспорта; отдельный Windows-job **без** UTF-8-переменных; `errors="replace"`/reconfigure для захвата вывода в runner; добавить 3.11 в матрицу; починить процессные тесты (не кодировка) отдельной задачей.

### P1-10. Нет автоматических quality-гейтов (✅)

Ни один workflow не запускает ruff/mypy/coverage; конфигурации нет. Итог: 104 ошибки default-набора (88 неиспользуемых импортов — показатель отсутствия линтера), 1221 расширенных, 213 ошибок mypy в 27 файлах, 6761 pycodestyle. **Исправление:** `[tool.ruff]` с зафиксированным `select` (старт: `F,E9,B023,S110,PLW1510`), `ruff format --check`; mypy с baseline-allowlist; coverage с порогом и отчётом; всё — блокирующими job'ами.

### P1-11. Невоспроизводимая сборка (✅)

Нет `requirements*.txt`/lock-файла; `dependencies = ["numpy>=1.21"]` без верхней границы (покрывает и numpy 1.x, и 2.x); extras не запинены; Windows-инсталлятор тянет `choco install innosetup` из сети в момент сборки. Матрица не покрывает 3.11; EXE/DMG собираются unsigned. **Исправление:** `uv.lock`/`constraints.txt` (использовать в CI), проверенные диапазоны numpy/pyserial, кэш/pinned toolchain для Inno Setup, подпись артефактов перед релизом.

### P1-12. Происхождение и публичная история (✅ по документу проекта)

README/CHANGELOG/`docs/release/provenance.md` фиксируют: работа велась по коммерческому дистрибутиву RadioInspector (документация, базы, Firebird/Guardant); материалы удалены из рабочего дерева, сохранён приватный архив, **очистка публичной истории не завершена**; вопросы лицензий и заимствований открыты; MIT покрывает только собственную разработку. Пока это не закрыто, публичный релиз/продвижение несут правовые риски. **Исправление:** завершить очистку истории (`git filter-repo` + согласованный force-push, приватный backup), получить письменные права на исходные материалы, зафиксировать решения по спорным документам, подготовить SBOM/notices; до этого — не публиковать релиз и явно ограничить статус репозитория.

## 5. Сильные стороны (их важно сохранить)

1. **Инварианты действительно соблюдаются.** Единственный писатель SQLite + RLock, измерения и события — одной транзакцией, публикация подписчикам только после commit; живой worker на прибор, `tune` вне общего lock; целые Гц и UTC в контракте; составные FK `(stream_id, session_id)` и явные проверки владельцев; `level_unit` нельзя сменить. Это не декларации — это видно по коду и тестам.
2. **Тестовая дисциплина.** 1424 тест-метода / 5782 assert на 28,9 тыс. строк; `assert True` — 0; release runner запрещает неожиданные skip и валит прогон при `testsRun == 0`; есть интеграционные тесты на реальных сокетах и 20 Node-скриптов, исполняющих production-JS.
3. **Fail-closed приборный слой.** tinySA: строгое обрамление, проверка эха/длины/хвоста, отказ после первой ошибки без повторов; AR-DV1: `s_meter_count` не конвертируется в dBm, происхождение данных честно помечается `hardware_validation=not_run`.
4. **Безопасность местами сделана аккуратно:** path traversal закрыт (проверено live), XSS-синков нет (`innerHTML` только для очистки), SQL параметризован, во всём пакете нет `subprocess/eval/pickle/yaml.load`, actions закреплены по SHA, `permissions: contents: read`, `persist-credentials: false`, аудио/tinySA-лимиты, приватные temp-каталоги, идемпотентный ledger инструментальных операций.
5. **Честная документация.** Аппаратная приёмка — все строки `BLOCKED`; README содержит дисклеймер «не аттестованное средство измерений»; 219 записей `review-disposition.json` с 140 ссылками-доказательствами — 0 битых; 317 ключевых слов и 17 CLI-команд подтверждены кодом.
6. **Упаковка/релизная инженерия.** 9/9 entry points валидны, версия из единого источника, wheel проверяется установкой вне checkout, sdist — `verify_sdist.py`/`check_public_tree.py`, сборки под Windows/macOS автоматизированы.
