## Находки

### P0-1. Полное отсутствие аутентификации и авторизации на всех маршрутах API

**Где:** `radioinspector/web/server.py:501` (`do_GET`), `:576` (`do_POST`), `:715` (`_api_v1_get`), `:1061` (`_api_v1_post`); поддержка сетевой привязки — `radioinspector/cli.py:704-706` (`serve --host` без ограничения и без требования секрета), `radioinspector/launcher.py:240` (`core_main --host` c choices `127.0.0.1`/`0.0.0.0`).

**Суть:** в проекте нет ни одного механизма аутентификации: ни токена, ни cookie/session, ни mTLS, ни проверки прав. `Handler` не читает `Authorization`/`Cookie` и не различает клиентов. Любой читатель и мутирующий маршрут `/api/v1/*` и legacy `/api/*` доступен анонимно. Документация это фактически признаёт: `docs/api-v1.md:719-720` («не заменяет аутентификацию», «удалённый API ограничен доверенной сетью»), `docs/release/installation.md:54-57` («до проверенной аутентификации не выставлять API в Интернет»). При этом удалённый доступ к Pi-ядру (bind не-loopback) — штатный сценарий, а `--host 0.0.0.0` явно предусмотрен в CLI.

**Сценарий/последствие:** любой хост в локальной сети (или скрипт на нём) без пароля: создаёт и запускает сеанс измерения (`POST /api/v1/sessions` → `POST /api/v1/sessions/{id}/start`), управляет tinySA/AR-DV1 через `workers/streams/instrument`, включает автономный планировщик с `start_at` (`POST /api/v1/task-scheduler`), читает и экспортирует **все** измерения всех сеансов, подменяет базу панорам через `/api/database`, заполняет архив. Для WebUI в локальной сети это компрометация всего измерительного комплекса и утечка измерений.

**Рекомендация:** минимум — генерируемый при первом запуске shared-secret (файл в data-dir с правами 0600), заголовок `Authorization: Bearer …` обязателен для всех `/api/v1/*` (кроме `/health`), отказ стартовать при не-loopback bind без секрета; далее — TLS + роли (оператор/наблюдатель), привязка сеансов к клиентам. Убрать/закрыть legacy-мутации, требующие доверия.

**Как проверено (воспроизведено):** анонимные `POST /api/v1/sessions` → `201 Created`; `POST /api/v1/sessions/{id}/start` → `200`, `state: "running"`; `POST /api/v1/sessions/{id}/stop` → `200`; `POST /api/v1/task-scheduler {"enabled": true}` → `200`; `GET /api/v1/sessions` → полный список. `GET /api/v1/capabilities` не содержит ни одного признака auth/token (список `features` с `auth|token|security` пуст).

### P1-1. Origin-проверка CSRF обходится DNS-rebinding: Host-заголовок не валидируется

**Где:** `radioinspector/web/server.py:593-598`.

```python
origin = self.headers.get("Origin")
host = self.headers.get("Host", "")
if origin and origin not in ("http://" + host, "https://" + host):
    raise RequestError("Чужой Origin запрещён", 403)
```

**Суть:** защита сравнивает `Origin` с **клиентским** `Host`, а не с заранее заданным именем ядра. При DNS-rebinding браузер жертвы ходит на `http://<attacker-domain>:8770/`, и `Host` и `Origin` одинаково принадлежат атакующему — проверка проходит. Сам `Host` не ограничен allowlist'ом; запросы вообще без `Host` тоже принимаются (`host = ""`, при отсутствии `Origin` проверка пропускается). Документация описывает эту защиту как анти-CSRF (`docs/api-v1.md:718-719`), но от rebinding она не защищает.

**Сценарий/последствие:** вредоносная страница на домене с TTL≈0 отдаёт жертве JS; DNS переключается на `127.0.0.1`; `fetch("http://rebind.attacker.test:8770/api/v1/sessions", {method:"POST", headers:{"Content-Type":"application/json"}, body:...})` — это **same-origin** запрос, поэтому нет preflight и проверка `Origin == Host` проходит. Ответ читаем (same-origin), значит можно не только управлять ядром и приборами, но и выкачать архив измерений жертвы. Работает даже при дефолтном loopback-биндинге. `Content-Type: application/json` (415) и `OPTIONS → 501` тут не помогают: preflight'а у same-origin запросов нет.

**Рекомендация:** строгий allowlist `Host` (`127.0.0.1:<port>`, `localhost:<port>`, явно настроенное DNS-имя) — отклонять всё остальное и отсутствие `Host`; не выводить разрешённые имена из самого запроса; корневое лечение — токен аутентификации (P0-1) и/или проверка `Sec-Fetch-Site: same-origin`/nonce.

**Как проверено (воспроизведено):** с одним `Host: rebind.attacker.test:8770` и `Origin: http://rebind.attacker.test:8770` → `201 Created` (сеанс создан); `POST` без `Host` → `201 Created`; для контроля: `Origin: http://evil.example` при `Host: 127.0.0.1:<port>` → `403`.

### P1-2. Неограниченный Content-Length в `_read_json` приводит к выделению памяти до чтения тела (OOM/DoS)

**Где:** `radioinspector/web/server.py:415-419`, вызов `:663`; достигается для всех `/api/v1/*` POST, не перечисленных в блочных списках `:599-662`, в т.ч. `POST /api/v1/sessions` (`:1083-1086`), `POST /api/v1/task-scheduler/tasks` (`:1071-1074`), `POST /api/v1/sessions/{id}/sweeps|observations` (`:1355-1370`).

```python
length = int(self.headers.get("Content-Length") or 0)
if length <= 0:
    return {}
raw = self.rfile.read(length)
```

**Суть:** `BufferedReader.read(n)` в CPython сначала выделяет буфер размером `n` и только потом читает. Значит одного заголовка `Content-Length: 200000000` достаточно, чтобы сервер выделил ~191 МиБ **без единого байта тела**; при `Content-Length: 10^15` возникает `MemoryError` в обработчике (не перехвачен, см. P3-2). Роут-специфичные лимиты есть только у «аналитических» маршрутов (`_read_bounded_analysis_request`, `:436-452`) — это правильный паттерн, но он применён не ко всем мутациям.

**Сценарий/последствие:** анонимный клиент открывает несколько десятков соединений с огромным `Content-Length` и не отправляет тело → ядро на Raspberry Pi (1-4 ГБ RAM) уходит в OOM/своп, измерение и WebUI падают. На Windows GUI клиенте ядро тоже можно погасить. `MemoryError` не превращается в `413/500`, клиент получает обрыв соединения.

**Рекомендация:** пропустить **все** тела через `_read_bounded_analysis_request` с лимитом на маршрут (64 КиБ — 1 МиБ), отклонять дублирующийся/невалидный `Content-Length` и `Transfer-Encoding` (этот код уже написан, `:436-452`, — переиспользовать); добавить таймаут чтения; перехватывать `MemoryError` и отвечать `413/500` JSON.

**Как проверено (воспроизведено):** при `Content-Length: 200000000` и нулевом теле `tracemalloc` показал +190.9 МиБ в процессе сервера; при `Content-Length: 1000000000000000` в stderr сервера — `MemoryError` на `server.py:419`, клиент получил пустой ответ.

### P1-3. Нет таймаутов на чтение запроса и лимита числа потоков (slowloris/исчерпание ресурсов)

**Где:** `radioinspector/web/server.py:1582` (`ThreadingHTTPServer((host, port), handler)`, `daemon_threads = True`), `:93-98`; единственный `settimeout` — `:655` только для тела legacy POST. `BaseHTTPRequestHandler` не имеет дефолтного таймаута, `ThreadingMixIn` — неограниченного числа потоков.

**Суть:** каждое соединение обслуживается отдельным потоком, который может бесконечно ждать строку запроса/заголовки. Лимита количества соединений и таймаута простоя нет.

**Сценарий/последствие:** один LAN-хост открывает, например, 2000 сокетов и присылает неполный заголовок (`GET / HTTP/1.1\r\nHost: x\r\n`) — это 2000 потоков и память стека/буферов; параллельно столько же SSE-подписчиков (P2-1), и ядро Pi перестаёт отвечать легитимным клиентам.

**Рекомендация:** `self.connection.settimeout(10-15)` в `setup()`/`get_request`; ограниченный пул (например, `ThreadingMixIn` + семафор на 32-64 соединения) с `503` при переполнении; лимит заголовков/срок жизни idle-соединения; keep-alive отключать по умолчанию.

**Как проверено (воспроизведено):** 30 соединений с неполным заголовком оставались активными (30 потоков) через 12 с, т.е. сервер не закрыл их по таймауту; в сумме с 40 SSE-подписчиками `threading.active_count()` = 72.

### P2-1. Нет ограничения числа SSE-подписчиков (в отличие от аудиопотока)

**Где:** `radioinspector/web/server.py:1437-1467` (`GET /api/v1/events`), `:1469-1494` (legacy `GET /api/stream`); `radioinspector/session_service.py:1574-1588` (`subscribe`, без капа; очередь размером `max(subscriber_queue_size=100, history_limit=1000)`), `:122`.

**Суть:** каждый SSE-клиент добавляет поток и очередь до 1000 `deepcopy` событий; число подписчиков не ограничено. При этом для аудиопотока лимит сделан правильно: `radioinspector/audio_stream.py:27` `MAX_SUBSCRIBERS = 4`, `:30` `MAX_QUEUED_BLOCKS = 64`, `:90-91` отказ.

**Сценарий/последствие:** анонимный скрипт открывает сотни `GET /api/v1/events` и держит их; потоки + очереди + `deepcopy` событий съедают память Pi; при активном измерении события идут потоком и очередь заполняется.

**Рекомендация:** глобальный и per-client лимит (например, 16), `503` при превышении, уменьшить очередь подписчика (10-50 событий), учитывать SSE-клиентов в общем лимите соединений, требовать auth.

**Как проверено (воспроизведено):** 40 одновременных `GET /api/v1/events` → `len(server.session_service._subscribers) == 40`, +40 потоков; ни одного отказа.

### P2-2. Legacy `/api/database` загружает произвольный `.pan` по абсолютному пути

**Где:** `radioinspector/web/server.py:698-709`; `ApplicationState.load_database` — `:125-132`; `serve` не задаёт `library` (`:1615-1632`), `launcher.LocalCore.start` тоже (`launcher.py:121-129`). При `library=None` проверка «внутри каталога» (`:130-131`) не выполняется.

**Суть:** анонимный POST `{"path": "C:\\...\\any.pan"}` открывает любой существующий SQLite-файл панорам на хосте и подменяет текущую базу. Содержимое затем отдаётся через `/api/state`, `/api/signals`, `/api/measure`.

**Сценарий/последствие:** чтение чужих/других архивов измерений с той же машины (например, другого оператора или другой базы), обход настроенного каталога; на Windows путь может быть UNC (`\\attacker\share\x.pan`), что провоцирует исходящую SMB-аутентификацию (гипотеза NTLM-leak, см. раздел «Гипотезы»). Ошибки открытия возвращаются клиенту как текст исключения.

**Рекомендация:** удалить legacy-маршрут смены базы из HTTP (это операторская операция запуска); при необходимости — принимать только basename внутри `library`/data-dir, канонизировать и проверять `is_relative_to`, запрещать UNC/абсолютные пути.

**Как проверено (воспроизведено):** `POST /api/database` с путём к свежесозданному `.pan` во временном каталоге вне какого-либо «library» → `200 OK`, затем `GET /api/state` отдаёт данные этой базы и её абсолютный путь.

### P2-3. Планировщик принимает произвольные `task_file`/`panorama_file` → оракул существования файлов на хосте

**Где:** `radioinspector/web/server.py:1071-1074`; `radioinspector/task_scheduler.py:165-202` (allowed-поля `task_file`, `panorama_file`), `:299` и `:319-322`:

```python
for value in (task.task_file, task.panorama_file):
    if value and not Path(value).is_file():
        raise FileNotFoundError(OUTCOME_FILE_NOT_FOUND)
```

**Суть:** анонимный `POST /api/v1/task-scheduler/tasks` создаёт задачу с произвольным путём, включение планировщика (`POST /api/v1/task-scheduler {"enabled": true}`) допустимо анонимно; при наступлении `start_at` ядро проверяет `Path(value).is_file()`. Разница в публичном статусе задачи выдаёт существование файла.

**Сценарий/последствие:** перебор путей (`C:\Users\...\...`, `/etc/...`, конфиги, ключи, чужие данные) по разнице статусов «Выполнено» / «Снято: файл задания не найден»; на Windows UNC-путь инициирует SMB-аутентификацию на хост атакующего (гипотеза NTLM-leak). Побочно: имена задач не ограничены по длине и сохраняются в tasks.json.

**Рекомендация:** принимать только логические идентификаторы/имена внутри data-dir, разрешать пути через canonicalize + allowlist, запрещать UNC/абсолютные пути и `..`; проверять длину `name`; закрыть scheduler-management аутентификацией.

**Как проверено (воспроизведено):** задача с существующим `.pan` → статус «Выполнено»; с несуществующим путём → «Снято с выполнения: файл задания (на сканирование частот) не найден».

### P2-4. Нет лимита архива по умолчанию и нет квоты на анонимный батч-ингест → заполнение диска/памяти

**Где:** `radioinspector/cli.py:713-716` (help: «без опции лимита нет, автоматического удаления нет»); `radioinspector/session_store.py:132-135` (`limit is None` → `state = "unlimited"`); ингест — `radioinspector/web/server.py:1326-1370`, лимит пакета 100 (`session_service.py:112`), число запросов не ограничено.

**Суть:** при `radioinspector serve --session-database ...` без `--archive-max-bytes` (дефолт `None`) архив растёт без ограничений; при `serve` без `--session-database` используется memory-store и растёт RAM. Анонимный клиент может отправлять пакеты по 100 измерений без ограничения частоты. Механизм `ArchiveCapacityExceededError → 507` уже существует (`server.py:1418-1419`), но по умолчанию не включён. Pi-юнит задаёт 1 ГиБ (`packaging/pi/openradioinspector.service:8`), т.е. безопасный дефолт есть только в упаковке, а не в CLI.

**Сценарий/последствие:** цикл `POST /api/v1/sessions/{id}/sweeps` с батчами заполняет диск ядра (отказ записи, потеря измерений) или память (OOM). `sweeps` могут нести массивы частот/уровней в теле — это ещё и тело на сотни КиБ на запрос.

**Рекомендация:** дефолтный положительный лимит (как в Pi-юните) и в `serve`; квота на клиента/сеанс и rate-limit; включать `507` до исчерпания диска; аутентификация.

**Как проверено:** статически по коду/CLI/упаковке (динамический прогон заполнения архива не выполнялся — не хотелось создавать большие временные данные). Стоит подтвердить нагрузочным тестом на временной БД.

### P2-5. Полный экспорт архива материализуется в RAM одним запросом; NDJSON-экспорт копирует всю БД во временный каталог на каждый запрос

**Где:** `radioinspector/web/server.py:924-938` (`GET .../archive/export` → `build_archive_document` → `_send_json`), `:375-393` (`export.ndjson` → `open_archive_snapshot`); `radioinspector/archive_export.py:21-33`; `radioinspector/session_service.py:585-592` (`list_sweeps(limit=None)` — все строки списком); `radioinspector/archive_snapshot.py:139-152` (`tempfile.TemporaryDirectory` + `store._connection.backup(destination)` — полная копия БД).

**Суть:** JSON-экспорт читает **весь** архив в списки, затем `to_primitive` и `json.dumps` в память — пик RAM кратен размеру архива (по умолчанию до 1 ГиБ в Pi-юните). NDJSON-вариант делает полную дисковую копию БД на **каждый** запрос без ограничения параллелизма.

**Сценарий/последствие:** анонимный клиент делает экспорт большого архива → OOM ядра на Pi; параллельные NDJSON-экспорты N раз копируют архив во временный каталог → исчерпание диска/`/tmp` (`PrivateTmp=yes` в юните усугубляет для temp). Экспорт при этом read-only, т.е. не портит данные, но роняет сервис.

**Рекомендация:** потоковый JSON-экспорт (без агрегации всего архива), лимит одновременных экспортов (1-2) и квота на размер/время, chunked-передача, auth. Для NDJSON — снапшот создавать один раз/кэшировать или читать без полной копии.

**Как проверено:** статически (код-путь и отсутствие лимитов); стресс-тест памяти не выполнялся, поэтому практический OOM — гипотеза, подлежащая нагрузочной проверке.

### P2-6. Нет security-заголовков; WebUI можно встроить в чужую страницу (clickjacking)

**Где:** `radioinspector/web/server.py:352-363` (`_send_json`), `:395-413` (`_send_file`); заголовки `X-Frame-Options`, `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security` не отправляются; `send_error` (`:397`, `:574`, `:711`) использует HTML-страницы `BaseHTTPRequestHandler`.

**Суть:** интерфейс не запрещает фрейминг и MIME-sniffing. Аутентификации нет, поэтому «украденный клик» оператора сразу выполняет действие.

**Сценарий/последствие:** атакующая страница встраивает `<iframe src="http://127.0.0.1:8770/platform">` (или через LAN-адрес ядра), накладывает прозрачные кнопки поверх «Старт/Стоп/Экспорт» и подсказками склоняет оператора нажать нужное место — выполняется управление измерительным комплексом или экспорт данных. Плюс браузер может сниффить ответы при отсутствии `nosniff`.

**Рекомендация:** `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'; default-src 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; HSTS только при TLS-прокси; не отдавать HTML-ошибки на API-маршруты (JSON-контракт).

**Как проверено (воспроизведено):** разбор заголовков ответов `GET /platform` и API — ни один из перечисленных заголовков не присутствует; `OPTIONS` → `501`, CORS-заголовков нет (это, наоборот, хорошо).

### P3-1. Информационные утечки: версия Python в `Server`, абсолютный путь базы в `/api/state`

**Где:** `Server: OpenRadioInspector Python/3.11.9` — `BaseHTTPRequestHandler.version_string()` при `server_version` `server.py:342`; `snapshot()` отдаёт `payload["database"] = self.database` — `server.py:199`, legacy `GET /api/state` — `:528-529`.

**Суть:** ответы раскрывают точную версию Python (упрощает подбор эксплойтов) и абсолютный путь загруженной базы (имя пользователя/структура каталогов). `Server`-заголовок генерируется стандартной библиотекой и для API, и для HTML-ошибок.

**Сценарий/последствие:** разведка перед атакой; утечка локальных путей и имён пользователей в LAN/через rebinding-страницу (ответы читаемы same-origin).

**Рекомендация:** переопределить `version_string()` (без `sys_version`), не включать абсолютный путь в публичный snapshot (или отдавать basename), убрать `database` из legacy `/api/state`.

**Как проверено (воспроизведено):** заголовки `Server: OpenRadioInspector Python/3.11.9` в ответах; после загрузки базы `GET /api/state` содержит `"database": "C:\\Users\\...\\...pan"`.

### P3-2. Несогласованная обработка ошибок и HTTP-семантика: непойманные исключения, смешение legacy/v1-контрактов, HTTP/1.0

**Где:** `radioinspector/web/server.py:501-508` и `:576-585` перехватывают только `ValueError, TypeError, OverflowError, UnicodeError`; `_send_json` (`:359-363`) ловит лишь `BrokenPipeError/ConnectionResetError`. Legacy-ошибки — `{"ok": false}` (`:508`, `:585`, `:706`) против контракта `{"contract": ..., "error": {"code"...}}` (`:365-373`); `protocol_version` не задан (HTTP/1.0), `Content-Disposition` у экспорта отсутствует.

**Суть:** `MemoryError` (P1-2), `ConnectionAbortedError` (Windows), `sqlite3.Error` и прочие исключения не превращаются в `5xx`-JSON: поток падает, `socketserver` пишет traceback в лог, клиент получает обрыв без кода/контракта. Legacy `/api/*` (мутирующие `/api/database`, `/api/threshold`) живёт вне версионированного контракта и отдаёт HTML-страницы `send_error`. Это затрудняет безопасную обработку ошибок клиентами и скрывает инциденты.

**Сценарий/последствие:** атакующий намеренно вызывает исключения (гигантский `Content-Length`, оборванный клиент) — сервер не отвечает `413/500`, а пишет неограниченные traceback'и в лог; клиент не может отличить атаку/сбой от ошибки ввода. Legacy-маршруты сложнее закрыть/аудитить.

**Рекомендация:** единый обработчик на границе `do_GET/do_POST`: `try/except Exception` → `500` JSON `internal_error` (с request id, без деталей), отдельно `MemoryError` → `503/413`; логировать с traceback, но не отдавать его клиенту; перевести legacy-мутации в v1 или отключить; задать `protocol_version = "HTTP/1.1"` осознанно; `Content-Disposition: attachment` для экспортов.

**Как проверено (воспроизведено):** при `Content-Length: 10^15` в stderr — `MemoryError`; при обрыве клиента — `ConnectionAbortedError: [WinError 10053]` в `_send_json`; ответ клиенту в обоих случаях не сформирован. HTML-ответы на неизвестные маршруты и `OPTIONS/DELETE` → `501/404 text/html`.

## Сильные стороны

1. **Path traversal в статике закрыт.** `server.py:566-573` канонизирует путь и проверяет `STATIC_DIR.resolve() in target.parents`. Проверено live: `/static/../radioinspector/web/server.py` → `403`, `/static/%2e%2e/...` и `/static/..%5c..` → `404` (percent-кодирование не декодируется), `/static//etc/passwd` → `403`, существующий `/static/./index.html` → `200`. Отдаются только файлы `web/static`.
2. **XSS-поверхность минимальна.** Во всех 26 JS-файлах `innerHTML` встречается 5 раз и только как очистка (`= ""`, `app.js:295,329,347,372,424`); данные API и пользовательские строки вставляются через `textContent`/`createElement` (`app.js:298-316`, `analytics.js:47-78`, `dvb-evaluation.js:80-88` и т.д.); нет `document.write`, `insertAdjacentHTML`, `eval`, шаблонной HTML-сборки; наличие text-DOM проверяется тестом `tests/test_webui.py:142`. Внешних CDN нет (`test_assets_are_local_and_packaged`).
3. **Базовая анти-CSRF-защита есть (но см. P1-1).** Мутации требуют `Content-Type: application/json` **до** чтения тела (`server.py:593-594`), простые формы/`text/plain` получают `415` (проверено), чужой `Origin` — `403` (проверено), `OPTIONS` → `501` и CORS-заголовки не выдаются (проверено); классический cross-site form/XHR заблокирован, дыра остаётся только в rebinding.
4. **Блочные лимиты и валидаторы там, где они применены.** `_read_bounded_analysis_request` (`server.py:436-452`) отвергает `Transfer-Encoding`, дублирующиеся/нечисловые `Content-Length`, сравнивает длину как десятичную строку до `int` и до чтения; строгий JSON с запретом duplicate keys (`:421-427`), проверка конечности чисел (`:332-336`), лимиты 1..1000/100/4 в сервисах; SQL везде параметризованный (f-строки только для фиксированных `WHERE`-фрагментов/сортировок, например `session_store.py:407-408`, `session_analytics.py:107-140`); во всём пакете нет `subprocess`, `os.system`, `eval`, `pickle`, `yaml.load` (grep — 0 совпадений).
5. **Ресурсные предохранители и приватное хранение.** Аудиопоток ограничен 4 подписчиками/64 блоками/48k отсчётов (`audio_stream.py:27-33,90-91`); tinySA-операции — whitelist операций, capability-заголовок для lease, канонический запрос ≤64 КиБ, idempotency-ledger 2048, jobs ≤128, потоков ≤4 (`tinysa/api.py:22-100`); экспорт использует неизменяемый снапшот (`archive_snapshot.py:139-152`), задачи — в приватном `TemporaryDirectory` (`server.py:1561-1563`), data-dir 0700 и `O_NOFOLLOW`-lock (`launcher.py:110-135`), Pi-юнит с `UMask=0077` и `PrivateTmp`.

## Гипотезы к проверке

1. **NTLM-утечка на Windows через UNC-пути** (`/api/database`, `task_file`/`panorama_file`): `Path.resolve()/is_file()` на `\\attacker\share\...` инициирует SMB-аутентификацию. Нужен SMB-listener и подтверждение на реальном Windows — здесь не проверялось (в песочнице нет SMB).
2. **OOM при экспорте большого архива** (P2-5): оценка по коду (полная материализация + `json.dumps` в память); нагрузочный тест с 1 ГиБ архивом не выполнялся.
3. **Практическая эксплуатация clickjacking** (P2-6): заголовки отсутствуют (проверено), но нужен браузерный PoC с UI-сценарием.
4. **Неограниченный размер `name` сеанса/задачи** и произвольные metadata-поля: нет length-валидации (кроме `isinstance`), сохраняются в SQLite/tasks.json — возможен блоат БД и журналов; отдельно не измерялось.
5. **`GET /api/state` с большим `.pan`**: snapshot материализует waterfall (300 строк × все точки) и все точки измерений (`server.py:243-267`) — при большой базе, загруженной через P2-2, возможен пик RAM; тест не выполнялся.
6. **HTTP/1.0 + `Connection: keep-alive` для SSE** (`server.py:1442-1447`, `protocol_version` не задан): в браузерах/обратных прокси стоит перепроверить надёжность потока и таймаутов.
7. **Полный `unittest discover`** не запускался (долго); выполнен только `tests.test_webui` (7 OK) как базовая проверка, что окружение зелёное.

## Резюме (10 строк)

1. Ядро вообще не аутентифицирует HTTP: любой клиент управляет приборами, сеансами, планировщиком и читает/экспортирует весь архив (P0).
2. Даже при loopback-биндинге браузер жертвы можно использовать через DNS-rebinding: `Origin` сверяется с клиентским `Host`, allowlist отсутствует (P1).
3. `_read_json` доверяет `Content-Length` и выделяет память до чтения тела: 191 МиБ на один заголовок, `MemoryError` на 10^15 (P1).
4. Нет таймаутов и лимита потоков — 30 полуоткрытых соединений держат 30 потоков сколь угодно долго, SSE добавляет ещё по потоку на клиента (P1/P2).
5. SSE-подписчики не ограничены, хотя у аудиопотока лимит 4 — несогласованность и DoS-вектор (P2).
6. Legacy `/api/database` по абсолютному пути читает любой `.pan`; scheduler создаёт оракул существования файлов по произвольным путям (P2).
7. Архив по умолчанию без лимита, батч-ингест анонимный и без квот — заполнение диска/памяти (P2).
8. Экспорт всего архива материализуется в RAM, а NDJSON-экспорт делает полную копию БД на каждый запрос (P2).
9. Нет `X-Frame-Options/CSP/nosniff` → clickjacking; `Server` выдаёт версию Python, `/api/state` — абсолютный путь БД (P2/P3).
10. Что сделано хорошо: traversal закрыт, DOM без XSS-синков, параметризованный SQL, нет subprocess/eval/pickle, аудио/tinySA-лимиты и приватные temp-каталоги. Блокеры доступа — аутентификация и лимиты на транспортном уровне.
