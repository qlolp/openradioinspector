## 1. Находки

### P1-1. dBmV переводится без множителя 1e-3 — ошибка 60 дБ

- **Файл:** `radioinspector/units.py:132-137`, используется в `units.py:306`, `units.py:347-348`.
- **Суть:** `dbmv_to_v()` возвращает `10**(v/20)` в **вольтах**, хотя dBmV — дБ относительно 1 мВ. `v_to_dbmv()` — обратная ошибка (не добавляет +60 дБ). В каталоге `VOLTAGE_DB` dBmV заявлен как поддерживаемая единица (`units.py:28`, `units.py:58`, `units.py:64`).
- **Последствие:** любое преобразование с dBmV ошибочно ровно на 60 дБ: 0 dBmV превращается в 1 В вместо 1 мВ, 0.001 В объявляется −60 dBmV вместо 0 dBmV. В отчётах/экспорте с дБмВ значения будут недостоверны на 6 порядков по мощности.
- **Рекомендация:** `dbmv_to_v(v) = 10**(v/20) * 1e-3`, `v_to_dbmv(v) = 20*log10(v*1e3)`; добавить тест на 0 dBmV ↔ 1 мВ ↔ 60 dBuV.
- **Проверено:**
  ```
  convert(0.0, "dBmV", "V")        -> 1.0        (верно: 0.001)
  convert(60.0, "dBuV", "V")       -> 0.001     (верно, dBuV реализован правильно)
  dbmv_to_v(0.0)                   -> 1.0
  v_to_dbmv(0.001)                 -> -60.0     (верно: 0.0)
  ```

### P1-2. `units.convert()` падает для однотипных относительных единиц (dBmV↔dBuV, dBuV/m↔dBV/m)

- **Файл:** `units.py:212-223` (ветка «одна группа»), `units.py:250-256` (`_watts_to_dbm`), `units.py:332-343` (`_power_to_watts`).
- **Суть:** для пары «относительные единицы одной группы» (например, dBmV→dBuV, dBuV/m→dBV/m) код уходит в `_watts_to_target(_watts_to_dbm(value, src), ...)`. `_watts_to_dbm(..., "dBmV")` вызывает `_power_to_watts("dBmV")`, который знает только dBW/dBm/W/mW/uW и бросает `UnitError`. Рабочий путь для dBW→dBm (спецслучай) маскирует дефект.
- **Последствие:** документированный каталог единиц не конвертируется; любой экспорт/калькулятор с dBmV, dBuV/m и dBV/m получает исключение вместо значения. Это не «недостающая функция», а сломанная ветка уже заявленного API.
- **Рекомендация:** для `src_kind == dst_kind` сводить к канонической единице группы (В, Вт, В/м) и обратно; не переиспользовать `_watts_to_dbm` для напряжений/поля.
- **Проверено:**
  ```
  convert(0.0,   "dBmV",   "dBuV")   -> UnitError: Неизвестная единица мощности: dBmV
  convert(60.0,  "dBuV",   "dBmV")   -> UnitError
  convert(120.0, "dBuV/m", "dBV/m")  -> UnitError
  convert(0.0,   "dBW",    "dBm")    -> 30.0  (этот путь работает)
  ```

### P1-3. `field_strength()` не напряжённость поля: уровень dBm + калибровка с меткой «dB»

- **Файл:** `radioinspector/measurements.py:535-606` (значение = `max(levels)` + `calibration_db`, `unit="dB"` строка 597), потребители: `reporting.py:283` («Напряжённость поля: {{field_strength_db}} дБ»), `cli.py:275-278`.
- **Суть:** функция берёт максимум уровней трассы (в dBm), прибавляет калибровочный коэффициент и возвращает единицу «dB» — это не дБ(мкВ/м) и не дБм, физическая величина не определена. Переход `P_dBm → E_dBµV/m` (для 50 Ом: `+107 + AF`) не выполняется, хотя `units.convert()` его умеет. `docs/measurement-methods.md:33` прямо относит методики напряжённости поля E/U к **нереализованным**, т.е. код противоречит собственной документации.
- **Последствие:** в протокол и CLI попадает число с неверной единицей; при первом же аппаратном отчёте его невозможно трактовать (дБм? дБмкВ/м? дБ относительно чего?). Нарушает правила проекта «сохранять исходные измерения и единицы» и «непроверенное не выдавать за готовое».
- **Рекомендация:** либо убрать из `measure_signal`/отчётов до реализации методик E/U, либо вернуть исходный дБм с явной единицей и отдельным полем `calibration_db`, а расчёт E выполнять через `units.convert(..., antenna_factor_db=...)` с явной единицей `dBuV/m`.
- **Проверено:**
  ```
  field_strength(Trace(freq, [-63, -61], "dBm"), calibration_db=6.0)
    -> value=-55.0, unit="dB"      (это −61 dBm + 6 дБ)
    10log10(10**(-61/10)) + 107 = 46.0 dBµV/m (то, что должно быть посчитано по мощности)
  ```

### P1-4. Неполный ответ прибора молча превращается в измерение с другим шагом частоты

- **Файл:** `devices/scpi.py:161-167` (`levels.size != config.points` → `linspace` на `levels.size` точек), `devices/scpi.py:169-188` (`_parse_curve` пропускает неразбираемые токены), `devices/serial_scpi.py:87-97` (та же схема), `devices/serial_scpi.py:100-115` (`_parse_numeric_payload`).
- **Суть:** если прибор вернул меньше точек, чем запрошено (таймаут/обрыв/частичная строка), код не сообщает ошибку, а **пересчитывает частотную сетку** `linspace(start, stop, n_полученных)` и сохраняет трассу. Неразбираемые значения просто выкидываются; `float("1e999")` даёт `inf` без проверки. Ни `*IDN?`, ни SCPI error queue не проверяются.
- **Последствие:** в архив попадает «измерение» с шагом в сотни раз больше реального; частоты отсчётов не соответствуют физическим. Это тихая порча исходных данных, хуже явного отказа.
- **Рекомендация:** требовать `count == points` и `np.isfinite(levels).all()`, иначе `InstrumentError`; сверять заголовок блока `count` (SCPI definite-length); при расхождении — никакой трассы и пометка соединения негодным.
- **Проверено:**
  ```
  _parse_numeric_payload("1.0,2.0,bad,3.0") -> [1. 2. 3.]   (bad молча выброшен)
  _parse_numeric_payload("1.0,2.0,1e999")   -> [1. 2. inf]
  ScpiInstrument.sweep(points=801, 100..200 МГц), ответ из 4 значений ->
    points=4, freq[0]=100000000, freq[-1]=200000000, step=33 333 333 Гц
  ```

### P2-1. `bandwidth_at_level()`: пропуск краевой точки при поиске границы (−N дБ)

- **Файл:** `measurements.py:296-336`, циклы `for i in range(imax, 0, -1)` (строка 301) и `for i in range(imax, freqs.size - 1)` (строка 321) не проверяют индекс 0 и последний индекс.
- **Суть:** если уровень уже ниже порога в нулевой (или последней) точке, переход через порог лежит между точками 0 и 1 (n−2 и n−1), но цикл не доходит до индекса 0 / n−1 — граница подменяется краем полосы обзора, а предупреждение «сигнал не отделён от левого края полосы обзора» **фактически неверно** (сигнал отделён, край ниже порога).
- **Последствие:** завышение измеренной ширины полосы (тем сильнее, чем ближе сигнал к краю обзора); для контрольной ширины по −30 дБ это может дать ложное «не норма».
- **Рекомендация:** циклы `range(imax, -1, -1)` / `range(imax, freqs.size)` с проверкой `i+1 < n` / `i-1 >= 0`; предупреждение выдавать только если край *выше* порога. Добавить тест: сигнал отделён от обоих краёв.
- **Проверено:**
  ```
  f   = 100..105 МГц (шаг 1 МГц)
  lv  = [-80, -30, -10, -30, -80, -85] dBm,  N = 30
  bandwidth_at_level -> bw = 3.9 МГц, left = 100.0 МГц  + ложный warning
  ручной расчёт (линейная интерполяция по мощности): left = 100.1 МГц -> bw = 3.8 МГц
  ```

### P2-2. База панорам не сохраняет частотную ось: при чтении сетка синтезируется из медианного шага

- **Файл:** `panorama.py:296-337` (`append` пишет только `levels`, `start_hz`, `stop_hz`, `step_hz`), `panorama.py:341-355` (`_trace_from_row`: `frequencies = start + np.arange(n) * step`, последняя точка принудительно заменяется на `stop`).
- **Суть:** исходный массив частот не сохраняется. Любая неравномерная сетка (округление частот tinySA до целых Гц, `Trace.decimate`, ручные трассы) после записи/чтения подменяется равномерной по медианному шагу.
- **Последствие:** нарушение требования «сохранять исходные измерения»; частоты отсчётов в архиве сдвигаются (для типичного свипа tinySA 100–101 МГц / 801 точка — до 352 Гц), а для прореженных трасс — на величину порядка шага, т.е. трасса перестаёт быть тем, что измерялось. Скрыто влияет на постобработку (центр тяжести, −N дБ, сравнение свипов).
- **Рекомендация:** хранить частоты явно (BLOB `<f8`), а поля start/stop/step оставить как метаданные; чтение старых записей — только с явным флагом `grid_source="reconstructed"` в метаданных.
- **Проверено:**
  ```
  freqs = 100e6 + round(k * 1e6/801), 801 точка; PanoramaStore.append -> latest().trace
  max |f_readback − f_original| = 352 Гц (argmax на последней точке)
  частоты берутся из median(diff)=1248 Гц, а не из исходного массива
  ```

### P2-3. Два несовместимых определения «усреднения» в ядре; усреднённый график не проверяет частотную сетку

- **Файл:** `trace.py:167-182` (`combine("average")` — среднее арифметическое дБ), `trace.py:229-237` (`traces_average` — `stack.mean`), `panorama.py:423-436` (`average_trace` — `stack.mean(axis=0)` по уровням), против `sweep_average.py:77-87` (`_mean_power_dbm` — среднее **линейной мощности**), `docs/averaged-sweep-reference.md:11` («Усредняется линейная мощность, а не численные значения dBm»).
- **Суть:** «усреднённый эталон» в новом API документирован как среднее мощности, а «усреднённый график панорам» (та же семантика в UI/отчётах) остаётся средним дБ. Кроме того `combine`/`traces_average`/`db_difference`/`_aggregate` проверяют только длину/минимум размера и не сверяют частотные массивы, а `_aggregate` вообще берёт частоты первой трассы.
- **Последствие:** для прерывистых сигналов средний график занижает мощность на десятки дБ и расходится с усреднённым эталоном; при разных start/stop трассы молча смешиваются по индексам.
- **Рекомендация:** ввести единую функцию `mean_power_dbm` (как в `sweep_average.py`, устойчивую к переполнению) и использовать её для всех «усреднённых» графиков; требовать точного совпадения `frequencies` (как `validate_sweep_compatibility`).
- **Проверено:**
  ```
  Trace([-100], [-100]).combine(Trace([-100], [-50]), "average") -> -75.0 дБ
  среднее линейной мощности: 10log10((1e-10+1e-5)/2) = -53.0 дБ  (разница 22 дБ)
  ```

### P2-4. Парсер scan tinySA заменяет запятые пробелами и разрушает десятичные значения

- **Файл:** `serial_instruments.py:357` (`tokens = line.replace(",", " ").split()`), при этом `_parse_frequency` (`serial_instruments.py:334-347`) специально поддерживает запятую как десятичный разделитель (`token[:-1].replace(",", ".")`), т.е. внутри одного парсера два взаимоисключающих предположения.
- **Суть:** строка вида `100000000 -9,000000e+01 0.0` превращается в `-9` (уровень) вместо `-90`; частота с запятой ломается на два токена и даёт `WorkerError`/искажение. Для локализованной прошивки, печатающей запятую, ошибка уровня достигает 81 дБ, при этом трасса проходит проверку на количество точек и монотонность.
- **Последствие:** тихая запись неверных уровней в архив; «поддержка запятой» в `_parse_frequency` для scan-строк — мёртвый код.
- **Рекомендация:** не заменять запятые в строке; разбирать первые два токена регуляркой с явным десятичным разделителем (`. ,`), лишние токены (номер детектора) игнорировать; проверять третий токен как ожидаемое число.
- **Проверено:**
  ```
  parse_tinysa_scan("100000000 -9,000000e+01 0.0\n... ", "scan", 3)
    -> levels (-9.0, -4.0, -8.0)  вместо (-90.0, -42.5, -80.0)
  ```

### P2-5. NaN во входной трассе проходит в результат β/2 как `nan` без ошибки и предупреждений

- **Файл:** `measurements.py:96-98` (`_db_to_mw`), `measurements.py:178-215` (`total_power = nan`; проверка `total_power <= 0` для NaN даёт `False`), `measurements.py:189-213`.
- **Суть:** `Trace` не валидирует конечность уровней (`trace.py:45-51`), а расчёт β/2 не отбраковывает NaN: `searchsorted` по NaN-накоплению и последующие clamp/min/max дают `bandwidth_hz = nan`, `warnings = []`. Для `measurements.py:180` (`total_power <= 0`) NaN-сумма не считается ошибкой.
- **Последствие:** «измерение» с NaN уходит в отчёт/JSON как валидный результат (в JSON `nan` вообще не сериализуется штатно, что дальше ломает API), без признака недостоверности.
- **Рекомендация:** в начале всех измерительных функций проверять `np.isfinite(freqs).all()` и `np.isfinite(levels).all()`, `diff(freqs) > 0`; для β/2 — `if not np.isfinite(total_power) or total_power <= 0: raise ValueError`.
- **Проверено:**
  ```
  levels = [-100,-100,-100,-100, nan, -100,...]; occupied_bandwidth_beta2 ->

  ```

### P3-1. Симулятор: «время» свипа считается как 1/скорость вместо span/скорость (ошибка 10⁶)

- **Файл:** `devices/simulator.py:108` (`self._elapsed_s += 1.0 / max(self.sweep_rate_hz_per_s, 1.0)`), `simulator.py:85-89` (AM-скважность по `_elapsed_s % period_s`).
- **Суть:** для свипа 1 МГц при 2.2e9 Гц/с реальное время свипа — 4.5e-4 с, а код добавляет 4.5e-10 с (в 10⁶ раз меньше). Фаза AM-излучателя за 1000 свипов сдвигается на ~2e-7 периода.
- **Последствие:** демонстрационные сценарии и тесты с AM/скважностью не воспроизводят временную динамику: излучатель «замирает» в одном состоянии, обнаружение по времени не проверяется.
- **Рекомендация:** `self._elapsed_s += (stop_hz - start_hz) / sweep_rate_hz_per_s` (для zero-span — фиксированное время или 1/refresh).
- **Проверено:** после 1000 свипов `_elapsed_s = 4.545e-7` с; ожидаемо 1000·4.5e-4 = 0.45 с.

### P3-2. `PanoramaStore.signal_events()`: допуск ±f/2 (50 % относительной частоты) и мёртвый код

### P3-3. `SerialScpiInstrument`: команды настройки отправляются как query, `*IDN?` читается до запроса

- **Файл:** `devices/serial_scpi.py:58-60` (сразу `readline()` до `*IDN?`), `:81-85` (`query` = запись + `readline`), `:87-97` (`STAR/STOP/RESB/POIN` через `query`).
- **Суть:** команды установки не предполагают ответа; `query` для них блокируется на `timeout_s` (по умолчанию 5 с) — 4 команды дают до 20 с задержки на свип, а если прибор всё-таки ответит (`OK`), ответ будет молча выброшен/съеден следующим чтением. `connect()` тратит первый `timeout_s` на чтение «приветствия», и любой мусор в буфере будет разобран как IDN.
- **Последствие:** медленный старт свипа и риск рассинхронизации прибора и парсера.
- **Рекомендация:** для установок — `write`; `*IDN?` — явный query; проверять `SYST:ERR?` после настройки; опционально `*OPC?`.
- **Проверено:** чтение кода; аппаратно не проверялось (нет прибора), логика воспроизводима на любом SCPI-эмуляторе.

## 2. Сильные стороны

1. **Строгое обрамление обмена tinySA.** Двоичные чтения идут строго по длине, с проверкой эха, завершающего `ch> ` и отсутствия хвоста; неполный кадр/несовпадение эха → ошибка (`tinysa/protocol.py:20-61,68-90`). Shell-команды: тело ответа обязано быть пустым, иначе отказ; после первой ошибки соединение «помечается» и повторов/flush нет (`serial_instruments.py:471-501,536-592`).
2. **Честное происхождение данных.** `s_meter_count` AR-DV1 не конвертируется в дБм, частота наблюдения не приписывается без успешной перестройки; повсеместно `hardware_validation=not_run`, `settings_readback=false`, `frequency_readback=false` (`serial_instruments.py:634-794`, `docs/devices.md:83-100`). Это ровно то поведение, которого требует проект.
3. **Усреднённый эталон свипов — образцовая реализация.** Равновесное среднее **линейной мощности** с вычитанием пика (без переполнения), проверка всех входов и границ диапазона, возврат ULP-инварианта `min(peak, max(min, mean))`, явные лимиты размера ответа (`sweep_average.py:31-137,175-219`), документировано в `docs/averaged-sweep-reference.md:11`.
4. **Явные пороги и сравнения без интерполяции.** `sweep_comparison.py` требует одинаковой частотной сетки, одинакового типа единиц `dBm`, одинаковых записанных настроек, конечности уровней; `sweep_threshold.py`/`sweep_three_thresholds.py` используют строгое `>` и не усекают данные (`sweep_comparison.py:56-113`, `sweep_threshold.py:23-124`).
5. **Целочисленное округление частот.** `frequency_rounding.py` работает только с целыми Гц в диапазоне ≤ 2^53−1, корректно считает границы сетки по модулю (в т.ч. origin вне диапазона), привязывает к ближайшей точке с `tie_break=lower`, обрезает соседей по реальным границам сетки и валидирует профиль (`frequency_rounding.py:52-105,132-160`). Проверено граничными профилями — расхождений с `docs/frequency-rounding.md` не найдено.

## 3. Гипотезы к проверке

1. **Порядок SCPI в `devices/scpi.py:143-167`:** `INIT 1` отправляется раньше `TRIG:SOUR AUTO`, затем повторный `INIT;*OPC?`; `PRESET` — перед каждым свипом. На железе это может переинициализировать измерение и сбросить настройки (детектор, единицы), отправленные между свипами. Требует проверки на конкретном анализаторе.
2. **`TinySASerialAdapter.poll` (`serial_instruments.py:559-566`):** при `trace_unit != "dBm"` (например `dBuV`) scan-уровни подписываются единицей экрана без преобразования. Если прошивка печатает scan всегда в dBm (как сказано в `docs/tinysa-receive-profile.md:36`), трасса получит неверную метку; если печатает в единицах экрана — неверны те, кто считает её dBm. Нужен живой tinySA Ultra.
3. **`power_over_threshold` (`threshold.py:208-231`) и RBW:** сумма `(P_i − P_thr)` по бинам не нормируется на `шаг/RBW`. При `RBW > шаг` соседние отсчёты частично измеряют одну и ту же полосу, и «мощность превышения» завышается; при `шаг > RBW` — занижается. Нужно нормативное указание (0.5–20 пВт из оригинала) и проверка на калиброванном генераторе.
4. **`Trace.step` = медиана `diff`** (`trace.py:81-86`) используется как «шаг перестройки» в β/2 и −N дБ. Для неравномерных сеток (округление частот tinySA, прореживание, последняя точка) медиана может не совпадать с реальным шагом; систематическая погрешность границ не оценивается. Проверить на реальных сырых сетках tinySA.
5. **`exceeded_intervals` (`threshold.py:183-205`) и `signals.py:203-213`:** границы превышения берутся по частотам отсчётов, а не по интерполированным пересечениям; для сигнала уже `шаг` полоса принудительно равна шагу (`signals.py:207-210`). По §7.2 «полоса = разница конечной и начальной частоты превышения» это может систематически завышать узкие сигналы — нужна сверка с оригинальной методикой.
6. **`_ardv1_body` (`serial_instruments.py:375-391`)** — эвристика кодов результата AR-DV1; сами авторы пишут, что «позиция RE1-кода, реальные ACK… остаются непроверенными» (`docs/devices.md:99-100`). Любая прошивка с другим форматом ACK сломает подтверждение команд — проверить на приборе.

## 4. Резюме (10 строк)

1. Ядро единиц содержит две подтверждённые ошибки P1: dBmV считается без множителя 1e-3 (60 дБ), а однотипные относительные конверсии (dBmV↔dBuV, dBuV/m↔dBV/m) вообще бросают `UnitError`.
2. `field_strength()` — P1: это не напряжённость поля, а «max dBm + calibration» с единицей «dB»; отчёт печатает её как напряжённость, хотя `docs/measurement-methods.md:33` относит методики E/U к нереализованным.
3. Приборный слой SCPI (net и serial) — P1: неполный/повреждённый ответ молча пересчитывает частотную сетку на меньшее число точек и сохраняется как измерение; `inf` из ответа не фильтруется.
4. Классические DSP-дефекты: −N дБ не находит границу у края обзора и выдаёт ложное предупреждение (P2); NaN-уровни дают `nan`-результат β/2 без диагностики (P2).
5. База панорам не хранит частотную ось — она синтезируется из медианного шага; дрейф до ~0.35 кГц на типичном свипе (P2), требование «сохранять исходные измерения» нарушено.
6. «Усреднённый график» (`panorama`/`trace`) усредняет дБ, тогда как документированный стандарт проекта — среднее линейной мощности (`sweep_average`); расхождение в примере 22 дБ, сетки трасс не сверяются (P2).
7. Парсер scan tinySA заменяет запятые пробелами: при локализованной прошивке уровень −90 дБм читается как −9 дБм (P2), поддержка запятой в `_parse_frequency` для scan недостижима.
8. Симулятор масштабирует время свипа на 10⁶ неверно, из-за чего AM-скважность в демо/тестах статична (P3); `signal_events` ищет ±50 % по частоте (P3).
9. Сильные стороны: fail-closed протокол tinySA, сохранение исходных единиц AR-DV1, образцовый линейно-мощностный усреднённый эталон, строгие сравнения свипов, целочисленное округление частот.
10. Найденные дефекты не покрыты тестами; приоритет исправлений: units (P1-1, P1-2) → SCPI-парсинг (P1-4) → field_strength (P1-3) → краевые случаи измерений и архив частот (P2).
