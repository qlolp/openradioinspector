# Приёмная проверка tinySA Ultra на macOS

Дата: 8 ноября 2026 года. База: точный head PR #87
`2afba069263785e7dbdc79f8d26c8b99a7532bc6`, плюс исправление ожидания
shell-ответа в этом срезе. Это ограниченная аппаратная проверка, не
метрологическая аттестация и не заявление о завершении всей приёмки релиза.

## Подтверждённый прибор и безопасный объём

- MacBook Air, macOS arm64, USB CDC tinySA4 (`0483:5740`).
- `info`: tinySA ULTRA ZS405; `version`: tinySA4_v1.4-235-gea71dfd,
  HW V0.4.5.1. Строки получены от физического прибора, не из fixture.
- Прибором владел отдельный процесс ядра; использовались только собственные
  временные SQLite/NDJSON и loopback HTTP. Пользовательские архивы не открывались.
- Перед каждым новым приёмным потоком: identity, `output off`, `mode input`,
  `lna off`, `attenuate auto`, `rbw`, `calc off`. Все setup-команды получили
  поддержанный пустой ACK с `ch>`.
- Генератор/передача, калибровка, запись конфигурации во flash, сброс,
  firmware update, ultra/LNA enable не выполнялись. Физический RF-выход
  независимо не измерялся: `off` означает ACK команды, не readback.

AR-DV1 к этому стенду не подключён. Его физический приём, FM/AM, handoff,
аудио, цифровые режимы и IQ этой проверкой не подтверждаются.

## Реальная ошибка и исправление

До исправления `scan 88M 108M 101 3` возвращал эхо немедленно, а измерения
позже. Общий transport завершал ответ после 250 мс тишины. Fail-closed
проверка правильно отклоняла неполный ответ, но первый реальный sweep
никогда не доходил до архива.

`_SerialFraming.read_until_quiet` сохраняет имя/API, но quiet теперь
означает только интервал опроса. Чтение ждёт завершающий `ch>` либо общий
лимит: 3 с для setup/identity, 90 с для scan. Паузы после эха, между строками
и частями prompt не завершают ответ. Лимит не продлевается новым байтом.
Изменение общее для POSIX и Windows COM; AR-DV1 продолжает использовать
отдельное построчное чтение.

Строгая проверка всего frame, количества точек, чисел и монотонности
сохранена. Неполный ответ по deadline, transport error или неоднозначность
по-прежнему помечают соединение `restart_required`: дальнейшие poll не
читают и не отправляют байты. Автоматических flush/resync/retry нет.

Закрытие USB-порта само по себе не отменяет выполняемый scan. После
прерывания старые USB-байты могут появиться при новом подключении; на
аппаратном стенде такой смешанный ответ был отклонён без записи sweep.
Это не повод отключать guard. Завершение/очистка собственного прерванного
стендового обмена выполнялась отдельно, без команд генератора; штатный
адаптер не пытается скрытно восстановить неоднозначное соединение.

## Пройденные сценарии

- Три последовательных прямых sweep: 88–108 МГц, 101 точка,
  запрошенный RBW 30 кГц; около 0,94 с на повторный sweep.
- Общий HTTP API → настоящий serial worker → SQLite: 88–108 МГц,
  201 точка, запрошенный RBW 10 кГц; 12 сохранённых sweeps. Остановка и повторный запуск потока
  с новым transport; после завершившейся остановки число записей стабильно.
- Широкий обзор: 100 кГц–800 МГц, 290 точек, запрошенный RBW 30 кГц.
  Три сохранённых sweeps, включая новый после восстановления службы.
  Около 36 с на sweep: малое время quiet не соответствует времени измерения.
- Целые Гц, точное число точек и края диапазона, конечные исходные dBm,
  интервалы UTC, `simulated=false` и происхождение output проверены
  на полученных аппаратных sweeps.
- Анализ реальных архивных данных: разность двух sweeps, средняя мощность,
  поиск изменений, адаптивный порог, три порога и контекст.
- NDJSON snapshot, сохранение исходных измерений и восстановление временной
  SQLite после перезапуска службы. Экспорт каждого из 15 sweeps точно
  совпал с API-записью.
- Safari WebUI: спектр и водопад настоящего FM-сеанса, 201 точка, UTC,
  история sweeps и SSE. Визуальная проверка не заменяет проверку всех
  размеров окна, диалогов и всех UI-действий.
- Python `PlatformClient`, используемый Windows GUI, читает настоящий API
  и экспортирует аппаратные записи на Mac. Это не аппаратная проверка Windows.
- Настоящий macOS Swift `PlatformClient`: чтение трёх 290-точечных sweeps,
  общий snapshot и NDJSON export. Записи Swift/Python экспортов совпали
  полностью. Logical dump hash архива до/после read-only клиентов совпал.
- Сервер закрыт, serial-порт освобождён; повторное открытие SQLite подтвердило
  сохранность всех 15 sweeps.

Исходные уровни, графики и локальные проверочные журналы в Git не включены.
Числа времени приблизительные и зависят от диапазона/настроек. Калибровка,
точность уровня/частоты, фактический RBW, слабые/перегруженные RF-входы,
физическое отключение USB и многочасовая запись не проверены.

## Автоматические регрессии

Новые собственные PTY и fake COM воспроизводят эхо с задержкой более quiet,
паузу посередине данных, фрагменты prompt, общий deadline и нетронутый
запоздалый ответ после ошибки. Исходная реализация не проходит новые
задержанные сценарии; исправленная проходит. Никакие реальные порты не
требуются для автоматических тестов.

Полный локальный набор: **986 Python/Tk/Node**, **163 Swift SDK**,
**108 native Swift**, без failures/errors/skips; unsigned Xcode Debug
**BUILD SUCCEEDED**. Семь synthetic SQLite logical dump hash не изменились
после интеграционных проверок. `git diff --check` чистый.

Глобальные `hardware_validation_not_run`/`hardware_validation=not_run`
сохранены: они не превращаются в разрешение считать произвольный прибор,
прошивку, ОС или подключение проверенными. Отдельный результат этого стенда
относится только к перечисленной модели, firmware, диапазонам и сценариям.
