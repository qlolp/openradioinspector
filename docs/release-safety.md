# Исправления блокеров жизненного цикла, serial и Windows

Это отдельный срез после таблицы округления частот, базовый коммит
`a71690953567bef0603ad5f38147d07c0896420e`. Он не интегрирует параллельный PR #75
и не означает готовность всей накопленной серии PR к релизу. Merge, close,
удаление веток, доступ к реальным архивам и физическим приборам не выполняются.

## Воспроизведённые дефекты

- POSIX transport вызывал отсутствующие в Python функции termios; реальный PTY
  нельзя было открыть даже без физического устройства.
- Между регистрацией worker и запуском thread конкурирующий start мог создать
  второго исполнителя того же потока. Остановка теряла одного из них.
- Bulk-start и HTTP stop имели отдельные окна, в которых прежний запуск мог
  оживить поток после успешного stop.
- AR-DV1 до первого tune приписывал LM частоту из settings. Неподходящие ответы
  принимались за подтверждение tune. После timeout запоздалые ACK могли
  сдвигать FIFO и подтверждать совсем другую команду.
- Tk-форма передавала строку `"60"` из StringVar проверке, принимавшей только
  числа. Unit-тест с числовой fake variable скрывал отказ реальной кнопки.
- NDJSON export обращался к неимпортированному tkinter.filedialog. Mock
  с искусственно добавленным атрибутом не выявлял production-ошибку.

## Границы исправлений

Исполнители получают независимую сериализацию lifecycle для session/stream,
учитывающую начало остановки и закрытие реестра. Нет общей блокировки на
время длительного I/O другого прибора. Ошибка старта закрывает принадлежащий
ей адаптер; тайм-аут stop не позволяет забыть ещё живой thread. HTTP stop
закрывает приём новых start до сохранения состояния сеанса; обычный
stop-workers допускает только новый явный start после завершения остановки.
Bulk-start сохраняет первоначальные admission tickets всех потоков; остановка
отменяет и ещё не запущенную часть такого запроса. Неизвестные ID не создают
записи lifecycle. Закрытый менеджер не принимает новые старты.

Ожидающие в очереди команды отменяются при stop, завершении worker и истечении
их тайм-аута. Уже начатый I/O не прерывается принудительно: он может закончиться
после клиентского тайм-аута, а ещё живой worker остаётся учтённым. Тайм-аут
не доказывает, что физическая команда не выполнилась.

POSIX transport задаёт raw 8N1/baud через поддержанные Python tcsetattr fields,
сохраняет и восстанавливает tty attrs и закрывает fd при ошибках. Проверки
выполнены на собственных псевдотерминалах, не на serial-устройствах.

AR-DV1 записывает частоту только после terminal ACK команды RF. Это
`command_acknowledged`, а не измеренная частота или readback. Неопределённый
ответ/тайм-аут переводит соединение в fail-closed: частота и режим неизвестны,
`restart_required=true`, команды и запись LM блокируются до stop/start нового transport. Запоздалые
ответы не лечатся повтором tune или очисткой буфера. См. [devices.md](devices.md).

Windows преобразует текст длительности в конечное положительное число только
на границе формы; общий API по-прежнему требует JSON number. Форма и экспорт
защищены от повторных кликов, закрытия и смены контекста; выбор файла явно
импортирован и защищён от вложенного цикла событий native-диалога.

## Воспроизводимые проверки без приборов

```sh
python -m unittest tests.test_serial_transport tests.test_serial_instruments
python -m unittest tests.test_device_worker_lifecycle tests.test_worker_api_lifecycle
ORI_WINDOWS_RELEASE_TK=1 python -m unittest tests.test_windows_release_flows
```

Concurrency-тесты используют события/barriers, а не вероятность случайного
планирования. Serial проверяется также FIFO-эмулятором, в котором ответы не
подбираются по имени текущей команды. Скрытые Tk-тесты используют настоящие
Entry/StringVar/Button и synthetic HTTP, но подменяют системный выбор файла;
временные TaskBook, NDJSON и SQLite принадлежат только самим тестам.

Полный набор: `python -m unittest discover -s tests -t .`. Для включения
необязательных живых тестов прежних аналитических срезов нужны их отдельные
synthetic fixtures и env из соответствующих документов; Node должен быть в PATH.
Для окна округления отдельно используется `ORI_ROUNDING_TK_SMOKE=1`.

Windows OS, внешний вид системных файловых диалогов, физические приборы,
реальная частота, цифровые режимы и метрологическая пригодность не проверены.
Linux/Raspberry Pi serial transport требует собственного платформенного прогона.
Ни существующие измерения, ни версия схемы SQLite этим срезом не меняются.

## Результаты проверки 8 ноября 2026

Финально проверено 8 ноября на Mac: 857 Python/Node, 151 Swift SDK и 99 native
тестов, все без пропусков; unsigned Xcode build успешен. В полном Python-наборе
включены 215 Windows-тестов, в том числе 17 настоящих скрытых Tk-сценариев.
22 lifecycle-сценария повторены 30 раз (660/660). Независимый review и отдельные
FIFO, bulk-start и invalid-ID oracles не оставили замечаний. Все шесть synthetic
HTTP fixtures остановлены, полные logical dump hashes SQLite до/после совпали,
временные каталоги очищены. Python compileall, Node syntax и diff check успешны.
