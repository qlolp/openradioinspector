# Пять аппаратных смен для публичного пакета

Для macOS arm64, Windows 11 x64, Raspberry Pi 5 и Debian 13 amd64 оператор квалифицирует **каждый установленный пакет отдельно**. На одном комплекте байтов нужны пять физических сценариев. Каждый сценарий ведут в своём сеансе с отдельным архивным экспортом. В парном сценарии оба прибора работают одновременно.

| Ключ формы | Приборы и исходные данные |
|---|---|
| `tinysa` | tinySA Ultra ZS405, подтверждённая прошивка, входной режим. Исходные частоты в Гц и уровни в дБм. |
| `rf-explorer` | RF Explorer 3G Combo Standard 003/005, 01.34. Зафиксировать активный вход и Normal по ответу прибора. Исходные свипы в дБм. |
| `ardv1` | AOR AR-DV1 в циклическом FM-обзоре. Сверить частоту, режим, шумодав и исходный отсчёт S-метра с ответом RX. Для покрытия нужны архивные точки сканирования на разных частотах. |
| `tinysa-ardv1` | Одновременно записывать свипы tinySA и наблюдения отдельного AR-DV1 через разные последовательные порты. Эта же пара даёт счётчики для раздела `hardware`. |
| `rf-explorer-ardv1` | Одновременно записывать исходные свипы RF Explorer и наблюдения отдельного AR-DV1. |

Проверьте физическую модель компьютера, ОС, подключение антенн, приборы и свободное место. Сохраните расшифровки ответов, идентификацию оборудования и запись о сбоях у владельца стенда. Отдельные испытания архива, установки, нагрузки и замеры скорости остаются в общей форме. [Порядок выпуска](public-distribution.md) · [Сценарии наблюдения](three-source-duty.md)

## Подготовка приватных отчётов

Из checkout принятого Git SHA укажите `PLATFORM`, каталог распакованного неизменного кандидата `CANDIDATE` и новый приватный каталог `PRIVATE_REPORTS`. На Windows команды Python те же. В примере для POSIX каждая форма создаётся в своём каталоге с защитой от перезаписи.

```sh
umask 077
set -C
for config in tinysa rf-explorer ardv1 tinysa-ardv1 rf-explorer-ardv1
do
  mkdir -p "$PRIVATE_REPORTS/hardware/$config"
  python -m tools.release.bench_receipt hardware-template --platform "$PLATFORM" \
    --candidate "$CANDIDATE" --configuration "$config" > "$PRIVATE_REPORTS/hardware/$config/run.json"
done
```

Команда сверяет SHA-256 пакета и привязывает форму к его манифесту, ревизии и встроенному `ori-core`. В каждом `run.json` заполните поля по фактически установленному пакету и журналу стенда.

- В `host` укажите физическую модель и параметры целевой ОС. Значения `os_id/os_version/architecture` для Windows — `windows/11/amd64` или `x86_64` как архитектура, для Mac — `macos/27.3/arm64` с возможным номером обновления, для Debian-ПК — `debian/13/amd64`. На Pi укажите `debian` или `raspbian`, номер выпуска от 12, `arm64`, физическую модель Raspberry Pi 5 с ревизией платы.
- Укажите полное `session_id`, а в каждом элементе `streams` — исходное `stream_id` и `max_silence_seconds` по заранее измеренной частоте свипов или опросов. Предел должен быть положительным и не более 3600 секунд. Запишите фактические `physical`, `duplicates` и `unexplained_losses`. Для допуска нужны физическое подключение и нули у двух счётчиков.
- Для каждого намеренного переподключения USB добавьте в `planned_gaps` объект с `source` из ключей `streams`, `reason` равным `usb_reconnect`, `started_at` и `ended_at` в UTC. Допустимый перерыв одного прибора составляет до 300 секунд. На пару записывают отдельный интервал каждого действительно затронутого прибора.
- После штатного окончания записи сохраните полный исходный экспорт сеанса `GET /api/v1/sessions/{id}/archive/export.ndjson`. Для пары tinySA + AR-DV1 имя файла — `$PRIVATE_REPORTS/hardware-coverage.jsonl`. Для остальных четырёх — `$PRIVATE_REPORTS/hardware/<config>/coverage.ndjson`. Запишите SHA-256 точных байтов файла в `coverage_sha256`. Для парного протокола Debian используется тот же файл. [Формат экспорта](../archive-export-stream.md) · [Дополнительные оригиналы Debian](linux-bench-evidence.md)

Для каждого источника проверка требует упорядоченные интервалы UTC, допустимую паузу между новыми измерениями, уникальные ID, нативные единицы, верный адаптер и его серийные признаки. Длительность рассчитывается от самого позднего из первых окончаний измерения до самого раннего из последних. Из этого интервала вычитается объединение заявленных USB-пауз. Нужны хотя бы **28 800 полных секунд** после вычета. Запланируйте запас времени на первое и последнее измерения. Для одиночного AR-DV1 записи ручного удержания сохраняются в перечне оригиналов, а время дежурства подтверждают точки циклического обзора.

## Расчёт и подпись

```sh
python -m tools.release.bench_receipt hardware --platform "$PLATFORM" \
  --candidate "$CANDIDATE" --private-reports "$PRIVATE_REPORTS"
python -m tools.release.bench_receipt check --platform "$PLATFORM" \
  --candidate "$CANDIDATE" --build-run "$BUILD_RUN" --receipt receipt.json \
  --private-reports "$PRIVATE_REPORTS"
```

Первая команда выводит объект для `hardware_runs` публичной формы версии 2. Для промежуточной проверки одной смены добавьте `--configuration`. Перенесите поля и значения в форму без изменений. Для каждого источника `ids_sha256` считается по всем уникальным ID в лексикографическом порядке UTF-8. Каждый ID кодируется как JSON-строка UTF-8 с одним LF. В публичную форму входят длительность, вид и единица измерений, количество, хеш перечня ID, хеш ID сеанса и хеши обоих приватных файлов.

Вторая команда проверяет пять смен и остальные оригиналы. Публикуйте только заполненную форму и её свидетельство штатным процессом аттестации или SSH-подписи. Файлы `run.json`, сырые NDJSON, USB-пути, координаты и данные операторов остаются у владельца. Ответственный оператор проверяет физическое происхождение файлов и точные хеши перед одобрением. Для исследования прежней формы версии 1 у команды `check` предусмотрен `--historical`. Новое одобрение, платформенный RC и стабильный выпуск требуют версию 2.
