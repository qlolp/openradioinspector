# Публичные пакеты OpenRadioInspector 0.4.0

У каждого пакета есть SHA-256, Git SHA и контрольные суммы встроенных компонентов. В серии `v0.4.0` первым публикуется принятый macOS DMG. Затем можно отдельно принять и опубликовать Windows NSIS и Pi DEB в любом порядке. Стабильный тег `v0.4.0` объединяет три ранее принятых файла. Debian amd64 выпускается самостоятельно под тегом `linux-amd64-v0.4.0` после приёмки своего DEB. Внутренняя версия публичных пакетов — `0.4.0`. Идентификаторы установок, службы и каталоги данных совместимы с инженерными кандидатами. Персональный Mac RC, unsigned Windows и обычный Pi RC доступны через прежние сборки.

## Построение

Из Actions запустите **Freeze native 0.4.0 candidate** (`signed-candidates.yml`) для нужной платформы. Для девяти окружений, настроенных 22 ноября, выбирайте защищённую ветку `main`. Все workflow поставки должны входить в выбранный SHA. Код также поддерживает фиксированную защищённую ветку `release/0.4.0` на коммите из истории `main`. Для её применения администратору потребуется отдельно разрешить её во всех задействованных окружениях сборки, приёмки и публикации и проверить правила развёртывания. Для используемых внешних служб задайте полномочия только на проект и выбранное окружение.

| Платформа | Штатный hosted runner и учётные данные | Уже настроенный signer |
|---|---|---|
| Mac arm64 | В `release-build-macos` задать vars `MAC_CERTIFICATE_SHA1`, `MAC_TEAM_ID`, `NOTARY_KEY_ID`, `NOTARY_ISSUER` и secrets `MAC_CERTIFICATE_P12_B64`, `MAC_CERTIFICATE_PASSWORD`, `NOTARY_PRIVATE_KEY_B64`. Нужны Developer ID Application, ключ команды для notarytool и образ с Xcode 27.2. Временная keychain удаляется после сборки. | Repo variable `MACOS_RELEASE_RUNNER` выбирает существующий arm64 runner с нужным Xcode, разблокированной keychain и заранее сохранённым профилем `NOTARY_KEYCHAIN_PROFILE`. Задайте те же fingerprint и team ID. |
| Windows x64 | В `release-build-windows` задать `WINDOWS_SIGNING_PROVIDER=azure`, `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_SIGNING_ENDPOINT`, `AZURE_SIGNING_ACCOUNT`, `AZURE_SIGNING_PROFILE`, точный `WINDOWS_CERT_SUBJECT`, `WINDOWS_TIMESTAMP_URL` (для Azure штатный адрес `http://timestamp.acs.microsoft.com`). Для Microsoft Artifact Signing нужен профиль публичного доверия и Azure OIDC для этого environment с правом подписывать в выбранном профиле. | Repo variable `WINDOWS_RELEASE_RUNNER` выбирает Windows runner с SDK SignTool, зарегистрированным сертификатом в CurrentUser/My и доступным закрытым ключом, в том числе через аппаратный provider. Задать `WINDOWS_CERTIFICATE_SHA1` и `WINDOWS_TIMESTAMP_URL`. |
| Pi arm64 | Hosted `ubuntu-24.04-arm` собирает serial core, supervisor и React WebUI в Debian 12. Суффикс версии пакета при первой публичной сборке — `0.4.0-1`. | Физический Pi участвует на этапе испытаний. |
| Linux amd64 | Запустите **Debian amd64 package** (`linux-amd64.yml`) на том же SHA. В **Freeze native 0.4.0 candidate** передайте `platform=linux-amd64` и ID успешного запуска в `linux_ci_run`. | `release-build-linux-amd64` замораживает тот же DEB, который CI установил и обновил без сети в Debian 12 и 13. |

На своих runner ограничьте доступ группы доверенным workflow на защищённой ветке. Пароли и ключи Apple хранятся в защищённом environment или в keychain, ключ Microsoft остаётся у провайдера. После проверки Apple для приложения и образа отдельно прикрепляются билеты, проверяются подпись Developer ID, hardened runtime, timestamp и Gatekeeper. На Windows подписываются оба Rust helper, основной EXE и NSIS. Signtool и WinVerifyTrust проверяют доверие, а разбор CMS проверяет RFC 3161 и SHA-256. Подписи helper входят в их хеши внутри манифеста.

Сохраните Actions artifact `release-<platform>-<Git SHA>-<attempt>`. В каталоге находятся один пакет, `<platform>-manifest.json` и `SHA256SUMS`. Для Mac сохраните отдельно `macos-engineering-<Git SHA>-<attempt>` с комплектом для именно этого приложения. Внутри DMG есть внешний инвентарь приложения, нужный комплекту. Офлайн-инструкция со снимками входит в каждый пакет. [Руководство оператора](../operator-guide/index.html)

## Что свидетельствует о приёмке

Из распакованного артефакта можно создать незаполненную форму. Команды выполняются из соответствующего исходного checkout. В примерах переменные `PLATFORM`, `CANDIDATE`, `BUILD_RUN` обозначают фактическую платформу, каталог скачанного пакета и номер успешного запуска упаковки.

```sh
python -m tools.release.bench_receipt template --platform "$PLATFORM" --candidate "$CANDIDATE" --build-run "$BUILD_RUN" --receipt receipt.json
python -m tools.release.bench_receipt check --platform "$PLATFORM" --candidate "$CANDIDATE" --build-run "$BUILD_RUN" --receipt receipt.json --private-reports "$PRIVATE_REPORTS"
```

Первая команда подставляет идентичность пакета, а для Linux amd64 также ID запуска из манифеста. Поля наблюдений заполняет оператор из журналов стенда. Вторая проверяет заполненную форму. Параметр `--private-reports` дополнительно сверяет исходные файлы на машине владельца. Публикуемая форма имеет закрытую схему. В неё входят агрегаты и хеши. Серийные номера, USB-пути, архивы радиоизмерений, личные заметки и полные журналы сохраняйте в приватном каталоге.

| Поле формы | Обязательные доказательства |
|---|---|
| `software_runs` | ID успешных workflow на этом Git SHA и доверенной ветке. Для Mac, Windows и Pi нужны `windows-core.yml`, `modern-core.yml`, `desktop-packages.yml`. Для Linux amd64 нужен `linux-amd64.yml` с нативной сборкой и обоими заданиями установки в той же попытке. Для Windows дополнительно `modern-clients.yml`, для Pi — `modern-clients.yml` и `pi-rc.yml`. Проверяются принадлежность исходному репозиторию, точный путь workflow, итог и все ожидаемые jobs. При фильтрации push по пути выполните workflow вручную на том же SHA. |
| `installation` | Чистая машина, установка с отключённой сетью, запуск офлайн-руководства, обновление, откат на отдельно сохранённый пакет и сохранность новых измерений. Для Windows `deploy/windows/smoke-installed.ps1 -RequireOffline` с фактическим предыдущим установщиком сохраняет хеши, обе ревизии и фазу завершённого отката. |
| `loads.three-clients` | 1800 секунд, 18 000 предложенных и архивированных панорам по 4096 точек, 18 000 наблюдений. Windows, Pi и Linux amd64 также сверяют 86 400 000 исходных mono PCM samples при 48 кГц. Все три одновременно работающих клиента должны каждый показать ровно 18 000 уникальных исходников. Для каждой строки `displays` вычислите SHA-256 одного и того же канонического перечня ID из offered ledger и фактически показанных ID конкретного окна. Команда `python -m tools.release.bench_receipt displays --ledger three-client-ledger.sqlite` делает это из закрытого offered/rendered ledger, открытого только для чтения. Хеш вычисляется по UTF-8 JSON-массиву отсортированных ID без пробелов или ASCII-экранирования. Сохраните журналы отображения каждого клиента. |
| `loads.binary-v1`, `loads.sse` | На Mac дополнительно нужны два разных полных нативных прогона с тем же приложением, комплектом и отдельным фактически показавшим все исходники окном на каждом транспорте. Три Mac-прогона охватывают приём и наблюдения без аудио (`pcm_samples=0`, `pcm_rate_hz` и `pcm_channels` равны JSON `null`). Приёмка аудиозахвата из этой формы не следует. |
| Показатели каждого прогона | p95 реакции UI ≤100 мс, очереди ≤200 мс, commit→показ ≤250 мс, pan ≥30 fps. Первые 100 прогретых строк истории из миллиона панорам ≤500 мс. Наблюдайте совмещённую нагрузку, историю, export, online backup, проверяйте восстановление в отдельном каталоге. |
| `hardware` | На соответствующей ОС одновременно измеряют физические tinySA Ultra и AR-DV1 не менее 28 800 секунд. Положительные счётчики обоих источников, ноль необъяснённых пропусков/дубликатов, полные наблюдения сбоев и восстановления. |
| `scan` | Для RBW 10 и 30 кГц сравните не менее десяти полных проходов на той же сетке 10 кГц и том же приборе/подтверждённом тракте с прямым USB-обзором. Сохраните SHA оригинального reference, экспорта и результата `scan_rate`, пределы и оба elapsed seconds. Проверка сравнивает одинаковый охват в Гц за время, порог ≥90% напрямую измеренной скорости. Хеш профиля вычисляет `bench_receipt.scan_profile_digest(reference)` после сверки настроек и устройства. |
| `storage` | На сетках 290 и 4096 точек — нативное сравнение 512 одинаковых панорам, исходных SHA-256 и воспроизведённых событий v6/v7. По обеим сеткам требуются экономия ≥30% по логическому росту на панораму и размеру checkpointed основного файла. |
| `protocol_report_sha256` | Хеш итогового приватного протокола со всеми обязательными результатами платформы, включая ошибки/восстановление, анализ исходных измерений, нагрузку, лицензионный состав, приемлемость для оператора. На Mac также используйте полный native protocol с faults/ENOSPC, миллионной историей, KPI памяти и проверкой доступности. Доказательство недельной эксплуатации требует отдельного недельного прогона. |

Для `--private-reports` скопируйте необходимые файлы в приватный каталог. Общие файлы — `hardware.json`, `protocol.json`, `load-three-clients.json`, `three-client-ledger.sqlite`. Для Mac, Windows и Pi нужен `installation.json`, на Mac ещё `load-binary-v1.json` и `load-sse.json`. Для Linux amd64 нужны два файла установки, описанные ниже. Для каждого RBW нужны `direct-10000.json`, `export-10000.ndjson`, `scan-10000.json`, `stream-10000.txt` со значением stream ID и аналогичная группа для 30000. Для обеих сеток нужны результаты `panorama_storage --enforce-rc` под именами `storage-290.json` и `storage-4096.json`. Проверяющий повторяет расчёт сканирования по исходному экспорту, проверяет байты обеих баз из нативного отчёта и использует штатную проверку двух Mac load reports. ## Подтверждение оператором и публикация

При штатном пути запустите **Review installed platform evidence**. Передайте идентификатор native build и base64 точных байтов UTF-8 `receipt.json`. В summary появятся его SHA и приватно сверяемые результаты. Включите required reviewers в Environment `release-acceptance`, ограничьте deployment branches. Владелец доступа к стенду сверяет оригиналы и подтверждает это задание через GitHub. Workflow проверяет факт одобрения в GitHub API и выпускает GitHub artifact attestation на точные байты формы с привязкой к SHA/ветке/пути workflow. Для этого пути оператору достаточно учётной записи GitHub.

Альтернатива для изолированного стенда — использовать существующий SSH Ed25519 ключ уполномоченного оператора. Заранее сохраните только публичную часть в соответствующей protected environment variable `MACOS_ACCEPTANCE_PUBLIC_KEY`, `WINDOWS_ACCEPTANCE_PUBLIC_KEY`, `PI_ACCEPTANCE_PUBLIC_KEY` или `LINUX_AMD64_ACCEPTANCE_PUBLIC_KEY`. Укажите пространство подписи для проверенной платформы.

```sh
ssh-keygen -Y sign -f "$OPERATOR_KEY" -n "openradioinspector-0.4.0-acceptance/$PLATFORM" receipt.json
```

В **Publish accepted immutable 0.4.0 packages** передайте `platform`, `build_run`, `receipt_b64` и номера RC. Для подписанной SSH формы добавьте `signature_b64` из `receipt.json.sig`. Для GitHub attestation оставьте поле подписи пустым. Однострочный base64 на любой машине можно получить командой `python -c "import base64,pathlib,sys; print(base64.b64encode(pathlib.Path(sys.argv[1]).read_bytes()).decode())" receipt.json`. Тело формы содержит только публичные данные.

Включите **Settings → General → Releases → Release immutability**. Проверка выполняет чтение `GET /repos/OWNER/REPO/immutable-releases` перед выпуском. GitHub требует Administration: read для этого запроса. Используйте обычный job token для публикации и `RELEASE_POLICY_READ_TOKEN` узкого доступа для проверки настройки, либо имеющийся доверенный `RELEASE_PUBLISH_TOKEN` с Contents: write, Actions: read, Attestations: read и Administration: read. При использовании выделенного GitHub App задайте `RELEASE_APP_ID` и secret `RELEASE_APP_PRIVATE_KEY`; workflow создаёт краткоживущий installation token. В правилах репозитория для тегов `v0.4.0`, `v0.4.0-*.rc.*`, `linux-amd64-v0.4.0*` и `android-field-v*` разрешите назначенному издателю создание и ограничьте изменение и удаление тегов. Издатель резервирует имя через GitHub Create a reference на принятом коммите, сверяет его непосредственно перед открытием черновика публике и ещё раз после. Серверное ограничение перемещения защищает интервал между чтением тега и публикацией. Правила применяет владелец репозитория.

Перед созданием черновика, тега или загрузкой файлов native workflow запрашивает историю одобрений текущего запуска и требует положительного решения пользователя для `release-publication`. Ручное одобрение этого окружения нужно также для повтора прерванной публикации.

Номера `rc_numbers` — JSON с полями `macos`, `windows`, `pi`. При первом наборе используются единицы. Каждая последующая попытка с другими принятыми байтами получает новый номер соответствующего платформенного тега. Для публикации Windows и Pi укажите номер уже принятого Mac на этом же коммите. Для stable выберите `platform=stable` на том же SHA и укажите принятые номера трёх платформ. Workflow скачивает уже опубликованные неизменяемые prerelease assets, повторно проверяет подписи, хеши, исходный SHA тегов и отчёты, загружает те же байты. Все файлы, включая `release.json` и доказательства приёмки, входят в `SHA256SUMS`. Штатный повтор после прерванной загрузки дополняет свой черновик, проверяя уже загруженные файлы. Опубликованные теги и посторонние черновики защищены от замены.

## Самостоятельная поставка Debian amd64

1. Возьмите `release-linux-amd64-<Git SHA>-<attempt>` из успешного запуска **Freeze native 0.4.0 candidate**. Сохраните номер этого запуска как `BUILD_RUN`. Сверьте `SHA256SUMS`. В `linux-amd64-manifest.json` раздел `native_ci` указывает ID и попытку исходного `linux-amd64.yml`, а также SHA-256 файлов `environment.json` и `lifecycle.jsonl` для каждой ОС. Заморозка проверяет имя, архитектуру и версию пакета через `dpkg-deb`, его SHA-256 и результаты чистой установки, обновления, отката, перезапуска и открытия существующего v6.
2. На чистых Debian 12 и Debian 13 amd64 проверьте этот DEB с отключённой сетью. Для `installation["12"]` и `installation["13"]` отдельно заполните установку, просмотр встроенного руководства, обновление с сохранённого предыдущего DEB и откат с сохранением новых измерений. В приватных `installation-debian-12.json` и `installation-debian-13.json` сохраните фактические `os_id`, `os_version` и `architecture` (например, `"debian"`, `"12"`, `"amd64"`), `source_revision`, хеши обоих пакетов и все логические поля записи установки. В каждую запись формы перенесите SHA-256 её приватного файла как `report_sha256`.
3. На физическом компьютере с Debian 13 amd64 установите те же байты, подключите tinySA Ultra и AR-DV1 и запишите оба потока не менее восьми часов. В приватном `hardware.json` сохраните `source_revision`, `os_id`, `os_version`, `architecture`, `artifact_sha256`, длительность, состав приборов, признак физического прогона и счётчики из `hardware`. Заполните форму по журналу и добавьте его SHA-256. Для этой платформы действуют все пороги таблицы по скорости прямого обзора, размеру и воспроизводимости архива, трём одновременно показывающим клиентам, исходному PCM, истории, экспорту и восстановлению резервной копии.
   Сохраните результаты совмещённого прогона, исходный `producer/report.json`, отдельный `history/report.json` для миллиона панорам и журнал показа интерфейса. В строке `loads.three-clients` хеши двух исходных отчётов записываются в `producer_report_sha256` и `history_report_sha256`. Для восьмичасового прогона сохраните приватный NDJSON-экспорт исходных измерений в `hardware-coverage.jsonl` и запишите его SHA-256 в `hardware.coverage_sha256`. Проверяющий сопоставляет перекрытие наблюдений обоих приборов и реальные счётчики нагрузки с формой. [Форматы оригиналов Linux-стенда](linux-bench-evidence.md)
4. Запустите `bench_receipt check` с `--private-reports` и передайте точные байты формы на **Review installed platform evidence** с `platform=linux-amd64`, либо подпишите их авторизованным ключом в пространстве `openradioinspector-0.4.0-acceptance/linux-amd64`. Сверьте SHA-256 пакета в обеих записях установки и в записи восьмичасового прогона с хешем замороженного DEB.
5. В **Publish accepted immutable 0.4.0 packages** выберите `platform=linux-amd64`, передайте `build_run` заморозки, форму и `linux_rc=N`. После появления неизменяемого `linux-amd64-v0.4.0-rc.N` выберите `platform=linux-amd64-stable` на том же коммите с тем же `linux_rc`. Издатель повторно проверяет тег, байты, нативный CI и подтверждение оператора, затем копирует DEB, манифест и подписанную форму в `linux-amd64-v0.4.0`. Оба тега публикуются с `make_latest=false`. Номер `linux_rc` относится только к этой серии.
