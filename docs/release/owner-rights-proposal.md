# Проект решения владельца о 160 исторических объектах

**Статус на 23 ноября 2026 года — проект, ожидает решения владельца.** В реестре происхождения зафиксировано сообщение владельца о лицензированной копии. Тексты договора и разрешений на анализ и распространение в распоряжении проекта отсутствуют. Приведённые ниже проверки устанавливают технические факты. Основание для каждого использования подтверждает владелец по документам правообладателя. [Реестр происхождения](provenance.md) · [Форма решения для приватного контура](owner-rights-form.md)

## Предлагаемое решение

1. **Исключить все 160 известных объектов из публичной истории, поставок, документации и иллюстраций.** Вновь найденные копии, переводы, перепечатки и спорные производные материалы направлять в тот же закрытый реестр. Общий пустой Git blob сохранять. Пути с общими пустыми файлами проверять отдельно.
2. **Ограничить частное хранение и исследование подтверждённым объёмом прав.** Лицензия на экземпляр, передача экземпляра на другое устройство, резервное копирование, извлечение, исследовательский доступ и передача третьим лицам требуют отдельной отметки в реестре. Когда основание для дальнейшей операции неизвестно, приостановить её до проверки. Для уже хранящихся материалов зафиксировать место, ответственного и условия хранения.
3. **Допускать исключения по перечисленным байтам и каналам.** Потребовать документированное основание, точную версию, аудиторию, территорию, срок и исполнение условий. Предпочесть заново полученный официальный компонент с применимыми уведомлениями. Для собственного текста или изображения сохранить исходник и историю создания. Сохранение объекта в полной публичной истории требует основания на такой доступ и отдельной записи. Одобрение вложения установщика само по себе охватывает только согласованную поставку.
4. **Перед публичным выпуском закрыть обе проверки** — происхождение фактической поставки и доступность исключённых материалов через связанные публичные каналы. Для их закрытия нужны записи проверяющих и утверждение владельца выпуска. Изменение истории GitHub требует второго, отдельного разрешения на конкретную операцию. Пустая форма, техническая репетиция, решение по составу пакета и разрешение на хранение такого разрешения не дают. [Условия серверного применения](history-cleanup.md#условия-серверного-применения)

| Выбор владельца | Условие применения | Результат |
|---|---|---|
| Исключить неподтверждённое, допустить документированные исключения **(рекомендуется)** | Для каждого исключения проверить полномочия выдавшей стороны, условия и фактические байты | Работы над собственным продуктом продолжаются. В публичный канал попадает только одобренный состав после проверок. |
| Исключить всю группу без исключений | Проект обходится без этих материалов, дальнейшее использование не требуется | Самый простой состав для проверки. Остаются проверка собственных производных материалов и обработка уже опубликованной истории. |
| Отложить конкретный канал | Документы, разрешение на резервную копию, доступ к остаточным refs или проверка содержимого ещё в работе | Указать ответственного, требуемое доказательство и дату следующего рассмотрения. Канал остаётся закрытым. |

```sh
python -m tools.release.check_public_tree --history-from "$SOURCE_SHA" --summary-only
python -m tools.release.check_public_tree --history --summary-only
```

## Как заполнить закрытый реестр

Сделайте по одной строке на каждый уникальный объект действующего списка. Добавьте строки для дополнительных заимствований и копий независимо от списка. При совпадении содержимого сохраняйте все известные пути, носители и каналы доступа. Связь с Git blob, SHA-256 проверенных байтов, оригиналами документов и приватными местами хранения ведите только в разрешённом хранилище владельца. Имена, хеши объектов, серийные номера, договоры и скриншоты в PR и CI не включаются. [Приватная форма и заполнение исходных 160 строк](owner-rights-form.md)

| Категория реестра | Что требует проверки | Предложение при отсутствии основания |
|---|---|---|
| Коммерческая программа, библиотеки, установочные ресурсы | Договор для точной версии и состава, право на нужную операцию и способ доставки. У поставщика может быть несколько правообладателей | Исключение из публичных refs, исходников и установщиков. |
| Руководства, справка, тексты, подписи и изображения интерфейса | Авторство иллюстрации или текста, разрешение на воспроизведение и производную форму, объём цитирования и канал | Исключение оригинала. Для руководства и магазина подготовить собственные тексты и кадры работающей ORI. |
| Базы, справочники, шаблоны, конвертеры | Отдельно проверить права на ПО, структуру, данные и возможные персональные сведения. Отсутствие пользовательских записей само по себе не устанавливает происхождение | Исключение. Для испытаний использовать собственные схемы и синтетические данные с указанным происхождением. |
| Движки БД, драйверы ключей и прочие сторонние компоненты | Сверить версию и состав с официальным первоисточником. Зафиксировать лицензию, требования к исходникам и уведомлениям, условия поставщика каждой вложенной части | При необходимости комплектовать из проверенного официального источника после исполнения условий. Лицензия одного компонента не охватывает весь прежний диск. |
| Заметки, методики, схемы, производные таблицы и самостоятельный код | Исходники, авторство, история изменений, границы цитат и сопоставление на предмет воспроизведения оригинала. Описать происхождение вклада и разрешение автора | Убрать спорные фрагменты, получить подтверждение или выполнить новое самостоятельное описание и повторную проверку. |
| Неидентифицированный объект, переименование, копия с изменённым содержимым | Сопоставить историю путей, размеры, формат и источники. В спорном случае привлечь профильного специалиста | Занести как нерешённый. Для выбранного канала применяется исключение. |

Для всех 160 строк приватная сверка должна установить полное покрытие списка без пробелов и дублей. Одна лицензия может относиться к группе с одинаковыми условиями. Владелец перечисляет каждую строку такой группы и её каналы. У каждого разрешённого действия должны быть точная ссылка на доказательство, ответственный проверяющий и действующий срок. Итоговая публичная сводка содержит количества по категориям и решениям и дату проверки.

## Состав фактически распространяемых байтов

Ответственный за сборку фиксирует полный SHA исходников, SHA-256 **готового** файла, платформу и канал. В изолированной среде он проверяет подпись и извлекает вложения штатными средствами для данного формата. Архивы внутри установщика, ресурсы внутри приложений, отчёты, примеры, карты, иллюстрации и руководство входят в состав проверки. Для символьных ссылок проверяются цель и границы пакета. Для каждого файла инвентаря указывается собственное происхождение или компонент с версией, источником и условиями. Установленный состав сравнивается с ожидаемым, включая дополнительные компоненты, которые установщик предлагает получить. Проверяющий фиксирует обязательные уведомления и, если применимо, выдачу исходников или предложение исходников.

| Канал | Что предъявить владельцу выпуска |
|---|---|
| Git и архив исходников | Именованный снимок refs и результата для их истории, архив точного коммита и проверка содержимого. Для CLI/wheel/sdist проверить отдельные готовые архивы и включённые WebUI-ресурсы. |
| macOS, Windows | Реальные байты DMG и содержащегося в нём приложения, установщик Windows и его вложения. Проверить нативные помощники, runtime, библиотеки, ресурсы и вложенные уведомления. |
| Raspberry Pi и Debian amd64 | Для каждого отдельного DEB проверить полезную нагрузку и управляющие файлы, unit-файлы, WebUI и уведомления Rust/npm. Офлайн-комплект с зависимостями проверяется по собственному составу. Системные зависимости учесть отдельно от вложенных байтов. |
| Android или другой магазин при включении в выпуск | Отдельно приложить перечень конечных APK/AAB или другого магазинного пакета, его встроенных компонентов и уведомлений. Руководство, иконка, скриншоты и рекламные материалы имеют собственные строки с источниками. |

Для распакованного набора применяют `python -m tools.release.check_public_tree --directory "$UNPACKED" --summary-only`, для ZIP/TAR — режим `--artifact`. Перед проверкой раскрывают каждый вложенный контейнер. Нулевое число известных совпадений дополняют ручной проверкой изменённых материалов и сверкой лицензий. Списки `runtime-notices.json`, `frozen-files.json`, инвентари Rust/npm и мобильные уведомления служат источниками сверки. Проверяющий подписывает привязанный к байтам перечень и передаёт владельцу исключения и открытые вопросы. Замена пакета, канала, исходников или условий требует новой сверки. ## Резервная копия, разрешение на сервер и проверка результата

1. **Хранитель архива** документирует основание для частного хранения, создания копии и разрешённого назначения. Перед изменением сервера он получает свежий снимок объёмов и refs, HEAD, тегов и PR-ссылок, зависимостей PR, настроек защиты и доступных негитовых вложений. Содержимое с ограниченными правами передаётся только одобренному получателю по разрешённому каналу. На принадлежащем владельцу автономном носителе проверить шифрование, доступ и возможность восстановления ключа. Зафиксировать сроки и круг доступа. Отсутствующий канал хранения оставляет серверную операцию заблокированной.
2. **Хранитель и проверяющий** закрывают автономное восстановление на заведомо пустом приватном месте. Сверяют SHA-256 архива с отдельно сохранённой ведомостью, проверяют и клонируют bundle, выполняют `git fsck --full`, сравнивают HEAD, полный перечень включённых refs и их цели. Для отдельных файлов проверяют число, длину и хеш каждого после восстановления. Записывают недоступные PR/вложения и план их обработки. Старые репетиции восстанавливали 234 refs, другая проверяла 195 refs. Эти числа относятся к прежним срезам. [Предыдущие репетиции](history-cleanup.md)
3. **Инженер репозитория** на отдельной разрешённой копии повторяет фильтрацию текущего зафиксированного снимка. Для каждой оставленной вершины сверяет все собственные пути, режимы, содержимое и общие пустые файлы, проверяет новую достижимую историю и тесты свежего клона. Приватно сохраняет сопоставление старых и новых refs, затронутых PR и подписей. По недоступным PR refs, кэшам, Pages, LFS, releases и Actions artifacts назначает ответственного и способ проверки. Форки и чужие клоны учитываются отдельно.
4. **Владелец решения и уполномоченный администратор** оформляют отдельную запись на серверную операцию с идентификатором приватного снимка, точными старыми и ожидаемыми новыми refs, полномочиями, окном, исполнителем и условиями остановки. Один человек может совмещать роли владельца и администратора при наличии полномочий. Решение о правах и поручение на сервер остаются самостоятельными записями. Перед началом сравниваются актуальные серверные refs и защита. Сдвиг любой цели требует обновлённой репетиции и авторизации. При нехватке прав, расхождении или отказе проверки операция останавливается. Регламент задаёт точные leases и атомарное обновление управляемых refs. [Порядок серверного применения](history-cleanup.md#условия-серверного-применения)
5. **Администратор и владелец выпуска** сверяют опубликованные refs, полный свежий клон, доступные PR-ссылки и каждое фактическое вложение. Провайдерские остатки учитывают до подтверждения обработки. Отдельное разрешение требуется для обращения к провайдеру или сообщения участникам. Восстановление старого архива проводят исключительно в закрытом контуре. Публичное исправление строят из проверенной очищенной истории. Итоговый статус по каналу закрывают датированной записью с результатами и перечнем остаточных ограничений.
