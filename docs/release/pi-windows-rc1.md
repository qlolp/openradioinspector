# Raspberry Pi и Windows · 0.4.0-rc.1

Кандидаты предназначены для самостоятельного узла с двумя USB-приборами. Raspberry Pi 5 с 8 ГБ и SSD обслуживает WebUI. Windows 11 x64 запускает тот же интерфейс в Tauri, со своим локальным ядром или с сопряжённым Pi. Рабочее пространство выбирается отдельно в каждом окне. Состояние записи и владельцев приборов отображает подключённое ядро.

Для Pi используйте офлайн-пакет arm64 и его SHA-256. Для Windows используйте установщик NSIS текущего пользователя со встроенным WebView2 и каталогом компонентов. Перед обновлением сверьте SHA исходной ревизии в манифесте и выдаче `ori-core --build-info`. При первом запуске укажите узел, SSD, порты обоих приборов и проект. Подключение и постановка на охрану требуют действия оператора. [Установка Pi](../pi-rc1.md) · [Установка Windows](../windows-standalone-rc.md) · [Рабочее место оператора](../pi-windows-operator-ui.md)

## Проверка оператора

1. Открыть «Радиомониторинг» и выбрать tinySA Ultra и AR-DV1. Проверить модель, прошивку, антенны, RBW, фактическое время возврата и резерв SSD с учётом backup.
2. Выбрать план обзора. Для общей сетки от 100 000 до 1 300 000 000 Гц с шагом 10 000 Гц полный проход включает 129 991 измеренную частоту. Частота выше 800 МГц требует подтверждения подходящей ревизии и прошивки. Для быстрого обзора задать RBW 30 кГц, для детального — 10 кГц. Сохранить выбранный профиль и версию плана вместе с результатом.
3. Собрать и подтвердить совместимый эталон. На каждой сетке окна нужны как минимум 20 полных свипов и 60 секунд наблюдения. Проверить регистрацию значений обоих приборов, приостановку широкого покрытия в узком поиске и возврат к обзору. По выбранному событию открыть исходную панораму и результат приёмника максимум за два действия.
4. Перейти в «Исследование», открыть историю, закрыть окно. После повторного открытия проверить владельца, ID сеанса, новые временные метки и непрерывность архива. На Windows повторить при блокировке и после входа по настроенному заданию. На Pi повторить после перезапуска службы и перезагрузки.
5. Проверить 1366×768 и Full HD, масштаб Windows 125–200%, Tab/Shift-Tab и Enter, заметный фокус, читаемые единицы, светлую, тёмную и системную темы. Потерю USB, занятый порт и полный тестовый том воспроизводить по отдельности. Для допуска 4 из 5 новых операторов должны самостоятельно завершить подготовку, начать запись, найти событие и открыть его исходник.

## Измерить скорость на каждом узле

Запустите отдельный прямой приёмный прогон на том же USB-порту после штатного освобождения прибора. Зафиксируйте систему, прошивку, антенну, тракт, версию приложения и скорость порта. Подготовьте файл одной полосы, например

```json
{"id":"vhf","name":"VHF","start_hz":98500000,"stop_hz":101390000,"step_hz":10000,"points":290,"rbw_hz":30000,"max_revisit_seconds":10}
```

Соберите измерительный пример из той же ревизии и выполните его с путём своего порта и **новым** именем результата

```sh
cargo build --locked --release -p ori-core --features serial --example scan_reference
target/release/examples/scan_reference PORT band.json 9600 10 reference.json
```

В Windows программа называется `scan_reference.exe`. После завершения верните прибор ядру. В новом сеансе запустите ту же единственную полосу и дождитесь первых десяти проходов и первого окна одиннадцатого. Экспортируйте сеанс через `/api/v1/sessions/{session_id}/archive/export.ndjson`. На машине проверки выполните

```sh
python -m benchmarks.ori_bench.scan_rate --reference reference.json --export session.ndjson --stream ANALYZER_STREAM_ID
```

Числитель — реальные точки десяти полных проходов. Интервал от начала первого окна до начала контрольного окна включает паузы, запись и переключения. Проверка сверяет каждую частоту и конечность каждого уровня, ID источников и последовательность с первого свипа, версию плана, прошивку и скорость порта. Прямой прогон и архивное окно должны содержать одинаковый обезличенный идентификатор прибора и одинаковые подтверждённые командами настройки входа, LNA, аттенюатора, расчёта, Ultra и RBW. При несовместимом источнике или неполном проходе сравнение завершается ошибкой. Поздние свипы считаются отдельно. Цель — не менее 90% скорости прямого прохода при том же профиле. Повторите с RBW 10/30 кГц, несколькими окнами и переходом через 800 МГц. В протокол внесите задержки опроса, записи и возврата, состояние очереди и разрывы. Времена обновления экрана измеряйте на клиенте.

## Проверить долговечность и место

Сравните один и тот же набор исходников при одинаковых seed, размере пакета и checkpoint. Оцените основной файл, логический рост на панораму и WAL до и после checkpoint. На машине проверки соберите производственный пример Rust и укажите его путь. В Windows добавьте суффикс `.exe`. Каждая команда печатает JSON с результатом.

```sh
cargo build --release --locked -p ori-archive --example panorama_storage
python -m benchmarks.ori_bench.panorama_storage --sweeps 512 --points 290 --batch 8 --native target/release/examples/panorama_storage --enforce-rc
python -m benchmarks.ori_bench.panorama_storage --sweeps 512 --points 4096 --batch 8 --native target/release/examples/panorama_storage --enforce-rc
```

Для приёмки на каждой сетке требуется экономия от 30% как по логическому росту на одну панораму, так и по итоговому размеру основного файла. Проверка снова открывает обе базы, сверяет количество исходников, размеры сеток, число событий и SHA-256 исходных значений и метаданных. Она сохраняет показатели даже при провале порога. В CI отчёты доступны как artifacts `panorama-storage` для arm64 Linux и Windows x64. В отчёте проекта `mean_stored_sweep_bytes` измеряет байты двух исходных массивов без индексов и журнала. `projected_bytes_per_day` — прогноз с учётом консервативного потока и наблюдаемого роста архива. `wal_bytes` — текущий размер отдельного журнала. Доступное место и оставшееся время учитывают настроенный резерв, включая резерв backup, когда он включён. При пустой выборке неизвестная скорость остаётся неизвестной.

В отдельном каталоге восстановите резервную копию. Сверьте ID, UTC, целочисленные Гц, единицы, исходные отсчёты, полный повтор событий с прежнего курсора и контрольные суммы закрытых аудиосегментов при их наличии. Для старого ядра создайте отдельную совместимую копию через `ori-core archive-materialize SOURCE NEW.sqlite`. Проверяйте откат на ней. Рабочая база сохраняется. [Формат архива и контрольные измерения](../compact-panorama-events.md)

## Условия публикации

| Проверка | Критерий |
|---|---|
| Установка и обновление | Чистый Pi OS arm64 и Windows 11 x64 офлайн, запуск установленного приложения, повторный запуск и откат с исходными данными |
| Полная программная проверка | Штатный release runner и CI из проверяемого SHA, журналы ошибок и причины пропусков |
| 30 минут совмещённой нагрузки | 18 000 предложенных панорам по 4096 точек, 18 000 наблюдений и 86 400 000 отсчётов mono PCM при 48 кГц. Три клиента, история, экспорт и backup работают одновременно. Архив и доставку сверяют со всем предложенным потоком |
| Отзывчивость | p95 реакции ≤100 мс, постановки команды ≤200 мс, commit → фактический показ ≤250 мс. Панорамирование ≥30 кадров/с. Первые 100 строк прогретого архива из миллиона панорам по 290 точек ≤500 мс |
| Аппаратный прогон | По 8 часов с tinySA Ultra и AR-DV1 на каждой целевой платформе. Сбой приёмника, сна, питания, USB или SSD должен оставлять наблюдаемый результат и сохранные исходники |
| Работа 24/7 | Отдельный недельный автономный прогон на целевой конфигурации |

Для прогона на установленной автономной платформе соберите из этой ревизии пример `benchmark_background` со штатным интерфейсом и задайте локальные Node, Playwright и Chromium. Вариант `paged-history` пишет исходный PCM в новый тестовый архив v7. Три независимых клиента получают поток. Во время записи проверяются постраничная история, экспорт и согласованная резервная копия. После закрытия ядра контроллер восстанавливает копию в отдельный каталог и проверяет её версию. Команда для подготовленного стенда использует абсолютные пути

```sh
python -m benchmarks.ori_bench.concurrent --candidate /absolute/path/benchmark_background --history-profile paged-history --output-dir /new/isolated/run
```

Параметр `--smoke-seconds 60` включает короткую проверку. Полный прогон использует расписание на 1800 секунд. Для Windows выберите путь к `benchmark_background.exe`. При отдельном испытании научного worker используйте профиль `research` с настроенной средой и зарегистрированными ограничениями. [Подготовка Windows и примеры команд](../windows-standalone-rc.md) · [Проверка тяжёлой аналитики](../modernization-concurrent-load.md)

При обрыве HTTP сверяйте исходный ID в `transport_failure_samples` и итогах проверки архива. Отчёт сохраняет этап обмена, время ожидания, класс исключения и доступный код ошибки ОС для первых 32 таких исходников. Счётчик `transport_unknown` учитывает все неподтверждённые запросы с транспортной ошибкой. Каждый исходник входит в нагрузку один раз.

Сведения о RSS, задержках, потерях очереди и фактически показанных кадрах берите из отчёта соответствующего узла. Отдельно сверяйте его SHA с проверяемой версией и журналами установки. У быстрого прогона и профиля Mac RC1 с исключённым аудио свои критерии. Публикация стабильной версии зависит также от принятого macOS RC.
