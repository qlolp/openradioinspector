# Аудио по сети: трансляция демодулированного сигнала

Hub ядра раздаёт принятые блоки аудиопотока сетевым клиентам как PCM
16 бит little-endian моно — та же кодировка, что в WAV-файлах фонограмм.
Это режим RemoteMD из оригинала: демодулированное аудио уходит по сети
тем, кто подключён к трансляции. Raspberry Pi WebUI ведёт непрерывное
чтение потока, Windows Tk — непрерывную трансляцию с остановкой по
кнопке, macOS SwiftUI — ограниченную пробную выборку из открытой
трансляции.

Это десятый срез функционального бэклога: передача демодулированного
аудио по сети. Реализована доставка со счётчиком потерь: каждый
подписчик получает блоки по мере того, как рекордер принимает отсчёты,
и, отставая, теряет только собственную очередь — запись и другие
клиенты не блокируются. Не реализовано: прослушивание аудио в клиентах,
отдельный UDP/RTP-транспорт, шифрование потока и привязка трансляции к
конкретному приборному аудиопотоку в device workers.

## Доставка

1. Подписка ограничена: не более 4 подписчиков на поток сеанса
   (`MAX_SUBSCRIBERS`). Очередь каждого подписчика — не более 64 блоков
   (`MAX_QUEUED_BLOCKS`); при переполнении старые блоки отбрасываются и
   потеря считается (`dropped_blocks`). Медленный клиент не влияет на
   рекордер и на остальных подписчиков.
2. Блок — не более 48 000 отсчётов (`MAX_BLOCK_SAMPLES`); отсчёты
   кодируются в PCM16LE тем же кодом, что и WAV-сохранение фонограммы.
   Исходные отсчёты не изменяются: трансляция — доставка, а не запись.
3. Без подписчиков блоки не копятся: hub ничего не хранит сверх очередей
   активных подписчиков.

## API и клиенты

`GET …/audio/status?stream_id=…` возвращает состояние трансляции
(`subscribers`, `max_subscribers`, `queued_blocks`, `dropped_blocks`).
`GET …/audio/stream?stream_id=…` открывает ответ `audio/pcm` без
Content-Length: блоки дописываются по мере поступления, подключение
удерживается самим ответом, клиент читает до отключения или закрытия
сервером. Заголовки ответа: `X-Sample-Rate: 48000`,
`X-Sample-Format: pcm16le`. Отсчёты поступают через
`POST …/phonogram/frames` или из приборных потоков; панели клиентов их
не генерируют и не пишут архив.

Raspberry Pi WebUI держит поток открытым и считает байты и блоки до
отключения. Windows Tk открывает трансляцию фоновым потоком и читает
блоками по 8 КиБ до кнопки «Отключить»; смена сеанса или потока
останавливает чтение. macOS SwiftUI берёт ограниченную выборку (до
64 КиБ по умолчанию) и отпускает подключение: непрерывное потребление —
цикл клиента, а не отдельный протокол. Возможность заявлена в
`capabilities()` как `remote_audio_stream`.

## Совместимость и ограничения

Старый сервер без маршрута отвечает 404; превышение числа подписчиков —
409 `audio_stream_unavailable`; неизвестный поток — 400/404 как у
смежных аудиомаршрутов фонограммы. Воспроизведение PCM в клиентах не
реализовано нигде: клиенты подтверждают доставку счётчиками байтов и
блоков. Аппаратная проверка с реальным прибором не выполнялась; поведение
проверено на синтетических отсчётах.

## Отмена и освобождение ресурсов

Смена сеанса/потока инвалидирует ответы и счётчики прежней трансляции.
Windows отменяет чтение через shutdown и закрытие отделённого дескриптора сокета;
повторная отмена безопасна, закрытие буфера
выполняет worker, а не Tk-поток. Тайм-аут обычного запроса ограничивает получение
заголовков; принятый поток ждёт PCM, EOF или явной отмены без idle-тайм-аута.
Одного shutdown на Windows недостаточно для ожидающего `recv`; владение
дескриптором перед закрытием отделяется от буфера. Небольшие доступные блоки
возвращаются сразу через `read1`.
Сервер проверяет EOF и освобождает подписку
при отключении даже без поступающих PCM-блоков. Регрессии используют настоящие
сокеты и повторные подключения сверх лимита подписчиков.
