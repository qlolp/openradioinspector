# Время жизни таймеров Windows Tk GUI

База: PR #90, `c2b57715f0cd83833b698ac909a21fb9c564ec64`.
API, исходные измерения, схема архива и WebUI/macOS-контракты не меняются.
Отдельный аппаратный PR #89 не включён в этот срез.

`after()` создаёт Tcl-таймер и отдельную Python-команду. Уничтожение Tk root
удаляет команду, но само по себе не отменяет таймер. Поэтому проверка
`_closed` внутри callback не предотвращает `invalid command name`: до Python
выполнение уже не доходит.

GUI и панели теперь хранят идентификаторы своих таймеров:

- Основной GUI имеет по одному таймеру обновления и обработки ответов.
  Прямой вызов `_drain_messages()` или `_poll()` заменяет ожидающий таймер,
  а не создаёт дополнительный бесконечный цикл.
- Каждая панель и каталог опорных sweeps владеют своим таймером ожидания
  результата. Файловый I/O имеет отдельный таймер.
- Закрытие отменяет только таймеры данного владельца. Сторонние callbacks
  и таймеры других панелей не затрагиваются.
- Прямой `root.destroy()` также освобождает ресурсы. Обработчик отличает
  уничтожение root от событий дочерних виджетов. Cleanup не обращается
  к уже уничтоженным кнопкам, canvas или текстовым полям.
- Повторное закрытие безопасно; executors завершаются без ожидания рабочего
  потока. Поздний ответ не применяется к закрытому GUI и не запускает таймер.
  Проверки revision/generation при смене подключения или источника сохранены.
- Публикация ответа и переход в закрытое состояние синхронизированы. Lock
  не удерживается во время отмены Future или shutdown executors, поскольку
  отмена может синхронно вызвать callback.
- Completion callback Future хранит только очередь, lock, закрытое состояние
  публикации и захваченные параметры запроса. Он не удерживает GUI и не
  освобождает последнюю ссылку на него в рабочем потоке после закрытия.

Тесты `tests.test_windows_tk_lifecycle` используют настоящий Tcl без загрузки
Tk для проверки очереди `after info` и перехвата `bgerror`. Это отдельная
проверка от `report_callback_exception`, который не видит отсутствующую
Tcl-команду. Набор также проверяет владельцев панелей, повторное закрытие,
смену подключения, поздние Future и закрытие внутри callback.

При `ORI_WINDOWS_RELEASE_TK=1` выполняется дополнительная проверка настоящего
`SchedulerWindowsApp` с withdrawn root в отдельном ограниченном по времени
дочернем процессе. Профили Tk не читаются, native dialogs заблокированы,
Tcl background errors записываются без диалогового окна.
Единый `tests.run_release_checks` включает этот opt-in и изолирует HOME/TMP.

Исправление воспроизведённых stale-timer ошибок не является доказательством
причины отдельного зависания `root.update()` на hosted macOS. Полный прогон
и CI нужной версии проверяются отдельно. Реальные приборы и архивы для этой
проверки не используются.

До исправления 7 из 8 первых регрессий воспроизводили дефект. Финальный
набор включает 23 lifecycle-регрессии и отдельный ограниченный ownership
subprocess; также проверены 23 прежних hidden Tk release-flow сценария.

Единая команда `python -m tests.run_release_checks --swift` прошла:
1060 Python/Node/Tk, 164 Swift SDK и 108 native тестов без пропусков;
unsigned Xcode BUILD SUCCEEDED. В полном логе нет stale Tcl command warnings.
Семь полных logical dump SHA-256 совпали, собственные серверы остановлены,
временный корень удалён. Это локальная синтетическая проверка на Python
3.12.15 / Tcl-Tk 9.0.4; hosted CI остаётся отдельным критерием.


На базе `c2b5771` Linux/Windows CI прошёл 1036 тестов, но
[hosted macOS job](https://github.com/qlolp/openradioinspector/actions/runs/42486149651/job/128748336250)
на Python 3.12.10 и Tcl/Tk 8.6.16 заблокировался в первом `root.update()`
сравнения усреднённых sweeps. Восемь стеков одинаковы; файловый диалог ещё
не открывался, HTTP-потоки были свободны. Совпадение с оставшимися Tcl-таймерами
не заменяет проверку исправленного дерева в hosted CI.

Отдельный полный прогон выявил ошибку владения новым Tcl-only test fixture:
после удаления команд Python-цикл ещё удерживал интерпретатор, и сборка
мусора в следующем HTTP-потоке завершала процесс с `Tcl_AsyncDelete`.
Минимальный дочерний процесс воспроизвёл этот сбой без загрузки Tk.
Теперь fixture явно освобождает обе ссылки на native interpreter в создавшем
его потоке. Закрытый владелец таймеров также удаляет ссылки на root и callback,
сохраняя только безопасную неактивную Destroy-команду до удаления root.

`tests.test_windows_tk_ownership` проверяет последовательность lifecycle suite
→ worker-thread GC → synthetic HTTP в отдельном процессе с private HOME/TMP,
контролем времени и очисткой собственных дочерних процессов. Обнаруженные
старые циклы variable traces в полном GUI не переписываются этим срезом;
полное освобождение native-графа по одному `close()` не заявляется.
