# Приём и непрерывное наблюдение tinySA

Реализованы шесть дополнений к macOS workbench: диагностика приёма, панель
приёмного тракта, повторное измерение участка/центрирование по маркеру,
Zero Span и триггер, многополосное наблюдение, управление VBW через проверенный
эквивалент прошивки. Измерения, расписание полос и обнаружение выполняет
существующий исполнитель Python-ядра. SwiftUI не открывает последовательный порт.
Это дополнение к существующему ядру; паритет нового функционала с Rust Core,
Windows GUI и Pi WebUI пока не заявляется.

## Работа оператора

1. Запустите serial-сеанс и откройте **«Тракт / Наблюдение»**.
2. В разделе тракта задайте аттенюатор, LNA, Ultra, число точек, повторения,
   минимальное время свипа, точность, spur и триггер. Частоты Start/Center/Stop/Span
   и RBW остаются в основной панели. Пакет настроек проверяется до отправки.
   При частичном аппаратном отказе уже подтверждённые шаги не откатываются фиктивно.
3. Масштабирование графика меняет видимую область. **«Измерить»** повторно
   измеряет видимый диапазон либо центрирует прежнюю ширину по маркеру/курсору.
   **«Следить»** перемещает курсор на текущий пик; это не автоматическая перестройка
   приёмника вслед за передатчиком. Изменение сетки пересчитывает шкалу уровня.
4. **Zero Span** показывает последовательность уровней на одной частоте.
   Доступны одиночный захват, непрерывная запись и возврат к первой полосе.
   Ось — индекс отсчёта. Общий интервал UTC получен на стороне USB-хоста;
   индивидуальные времена отсчётов неизвестны и не выдумываются.
5. В **«Наблюдение и события»** задайте 1–8 полос, фиксированный RBW, число точек,
   пороги превышения и известные частотные области. Запустите сбор фона.
   Пока наблюдение активно, изменение тракта/частот блокируется ядром.
6. Из события откройте **«Исходный свип»**. Полный журнал и фон доступны через
   **«Журнал архива»**, включая страницы более ранних записей.

Счётчики измерений/ошибок, возраст последнего измерения и состояние исполнителя
помогают отличить свежие данные от остановившегося приёма. Пауза отображения
не является остановкой устройства. После потери USB или ошибки журнала требуется
восстановить приём и явно запустить новое наблюдение с новым фоном.

## Значение «неизвестного сигнала»

Это **изменение относительно изученного фона**, а не идентификация источника,
протокола или незаконности передачи. Сигнал, присутствующий во время обучения,
войдёт в фон. Известные области исключаются из обнаружения по целым Гц.

Для каждой полосы независимо собираются не менее 20 полных свипов за минимум
60 секунд. Применяется общий `monitoring.detector` (`robust-city-v1`): p95/MAD,
порог превышения, подтверждение в 3 из 5 свипов; сильный импульс фиксируется сразу.
Широкополосное изменение объединяется в событие. Гистерезис 3 дБ и три тихих
свипа завершают событие; длительный сигнал не создаёт новую запись на каждом
свипе. Пропуски разрывают накопление подтверждений и помечаются `data_gap`.
Изменение сетки или настроек запрещает продолжение со старым фоном.

Количество сохранённых образцов фона ограничено 256 на полосу, окно детектора —
20, видимая история событий — 32. Исходные измерения и полный журнал хранятся
в SQLite и продолжают занимать диск: ограничение оперативной памяти не является
бесконечным архивом. Применяются существующие средства контроля ёмкости архива.
Сканирование последовательно: короткий сигнал вне измеряемой сейчас полосы
может быть пропущен. Это не широкополосный IQ-приёмник.

## Аддитивный API v1

База: `/api/v1/sessions/{sid}/streams/{stream}/instrument`.
Сохраняются существующие асинхронные jobs, revision, request_id и scope-проверки.
Новый контракт доступен любому клиенту общего ядра.

| Операция / маршрут | Данные |
|---|---|
| `POST operations`, `receive.configure` | `parameters` содержит выбранные приёмные настройки; генератор запрещён |
| `POST operations`, `watch.start` | `parameters.document` — JSON-строка плана ниже; нужен постоянный SQLite-архив |
| `POST operations`, `watch.stop` | Пустые параметры; прекращение расписания/обнаружения, обычный приём остаётся |
| `GET settings` | Кэш без USB I/O: `watch`, `watch_band`, revision/settings/provenance |
| `GET artifacts/{id}/json` | JSON в стандартном API-envelope; проверка sid/stream и MIME; оригинальные байты остаются в `/content` |

Общий [синтетический контракт](../contracts/fixtures/tinysa-watch-v1.json) проверяет
план и событие со ссылкой на исходный свип. Пример
`watch.start.parameters.document` после декодирования строки:

```json
{
  "bands": [{"name": "FM", "start_hz": 88000000, "stop_hz": 108000000,
             "rbw_hz": 30000, "points": 201}],
  "margin_db": 6, "impulse_db": 12,
  "confirmations": 3, "window_sweeps": 5,
  "baseline_sweeps": 20, "baseline_seconds": 60,
  "allowed": [{"start_hz": 99500000, "end_hz": 100500000}]
}
```

JSON-артефакты `spectrum-watch-start.json`, `spectrum-baseline.json`,
`spectrum-events.json`, `spectrum-watch-stop.json` содержат план/run_id,
версию детектора, ссылки на исходные свипы и время. Анализ вызывается только
**после сохранения исходного свипа**. При отказе анализа или записи производного
журнала исполнитель останавливается, исходный свип остаётся в архиве; ошибка
не маскируется следующим удачным измерением. Атомарная транзакция свип+журнал
и восстановление состояния детектора после падения процесса не заявляются.

## Прошивка и VBW

Профиль по-прежнему ограничен ZS405 HW0.4.5.1 / `tinySA4_v1.4-235-gea71dfd`.
Управление VBW использует проверенный код этой версии: `auto` и `1` → repeat1,
`1/3` → repeat3, `1/10` → repeat10, `1/30` → repeat30, `1/100` → repeat100.
Это эквивалент механизма повторений, а не независимый аналоговый фильтр и не
физический readback полосы. `repeat` и `vbw_ratio` в одном пакете запрещены.
Источник настроек остаётся `command_acknowledged`, `settings_readback=false`.

Zero Span читает фактический offset через `zero`. В ea71dfd `usage_printf`
добавляет `usage: `; разбор принимает этот точный префикс и прежний формат,
сохраняя отказ при неоднозначном ответе. Offset не подставляется константой.

Источники: [официальная wiki](https://tinysa.org/wiki/),
[cmd_zero в sa_cmd.c](https://github.com/erikkaashoek/tinySA/blob/ea71dfd9e53d6dec95256ac70914659cf260d48d/sa_cmd.c),
[usage_printf в main.c](https://github.com/erikkaashoek/tinySA/blob/ea71dfd9e53d6dec95256ac70914659cf260d48d/main.c),
[set_VBW в sa_core.c](https://github.com/erikkaashoek/tinySA/blob/ea71dfd9e53d6dec95256ac70914659cf260d48d/sa_core.c).

## Воспроизводимые проверки

```sh
TMPDIR=/private/tmp python -m unittest tests.test_tinysa_watch tests.test_tinysa_instrument_api tests.test_tinysa_controller tests.test_tinysa_protocol tests.test_tinysa_modes tests.test_device_workers
swift test --package-path macos/SpektrKomandy --filter ReceiveOperationTests
swift test --package-path macos --filter NativeReceiveDraftTests
python -m tests.run_release_checks
```

Аппаратный smoke-test не следует запускать параллельно с рабочим ядром:
последовательным портом должен владеть один процесс. Результаты аппаратных
и общих тестов этого изменения приведены в отдельном отчёте
[проверка непрерывного наблюдения](continuous-spectrum-validation.md).
