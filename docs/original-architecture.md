# Архитектура исходного комплекса

Документ описывает архитектуру коммерческого комплекса *RadioInspector*
(ООО «Лаборатория радиоизмерений») по десяти техническим документам,
проанализированным при подготовке OpenRadioInspector. Он нужен, чтобы
сопоставление «функция оригинала → модуль OpenRadioInspector» в
[`feature-map.md`](feature-map.md) опиралось на фактическую структуру
исходной системы, а не на отдельные описания функций.

## 1. Подсистемы комплекса

| Подсистема | Назначение | Тип поставки |
|---|---|---|
| **БД частотных назначений** | Центральное хранилище сведений о РЭС, владельцах, частотах и режимах работы, антеннах и разрешительной документации; фильтрация, географический фильтр, планирование | ПО |
| **I_MasterDevice** | Управление средствами измерений: сценарии, монопольная резервация прибора, калибровка антенн и трактов, приём координат | ПО |
| **InspectorRC / InspectorRT** | Контроль диапазона: сканирование, база данных панорам, линии порога, реестр сигналов, загрузка диапазона | ПО |
| **InspectorDC** | Исследование одного сигнала: прямое управление анализатором, измерение параметров излучения, отложенный анализ | ПО |
| **InspectorRP** | Радиопеленгование: анализ сохранённых панорам, выборка по частоте, экспорт результатов | ПО |
| **Планирование заданий** | Подсистема отложенного выполнения работ: задания, статусы, файлы заданий и результатов | ПО |
| **Правила формирования отчётов** | Протоколы измерений: 317 ключевых слов, префиксы, маркеры таблиц | ПО |
| **ГИС и антенный компас** | Географическая привязка результатов, карты MapInfo и OpenStreetMap с офлайн-кэшем, ориентация антенны | Опции RC-Geo, RP-Geo, I_MD-Geo |
| **I_RemoteCheck** | Удалённый контроль рабочих мест операторов | ПО |
| **RInspectorWiFi** | Аппаратный модуль перехвата трафика сетей 2,4 и 5 ГГц | Оборудование + ПО |
| **IQ_ProcessPRO** | Обработка записанных IQ-сигналов: фильтрация, децимация, демодуляция | ПО |
| **ISBDViewer** | Просмотр баз данных | ПО |

Опции **DTest**, **RT-Group** и **RP-DB** относятся к отдельным лицензиям
на тесты, групповой режим и базу данных радиопеленгования.

## 2. Федерация баз данных

Комплекс баз данных — не одна база, а набор взаимосвязанных файлов на
сервере **FireBird 2.1**. Это ключевая архитектурная особенность
оригинала: приложения работают не с единым хранилищем, а с набором
связанных баз, между которыми переход выполняется по уникальным полям,
идентифицирующим частоту.

| База | Расширение | Содержимое | Связи |
|---|---|---|---|
| **Частотных назначений РЭС** | `.ifixdb` | РЭС, владельцы РЭС, частоты и режимы работы, антенны, разрешительная документация | Основа комплекса |
| **Норм** | `.inrms` | Нормы на отклонения частоты, маски спектра, методики измерений | По уникальным полям частоты → к базе назначений |
| **Результатов измерений** | `.imeas` | Результаты измерений | По уникальным полям частоты → к базе назначений |
| **Средств измерений** | `.imeasdev` | Перечень устройств, используемых комплексом | Самостоятельная |
| **Сотрудников** | `.imembs` | Сотрудники, работающие с ПО | Открывает форму авторизации |
| **Планирования заданий** | `.itaskdb` | Плановые задания: вид, цель, основание, сроки, оборудование, исполнители, результат | Самостоятельная; связана с файлами панорам |
| **Частотных запросов** | `.ifrqdb` | Частотные запросы: полоса, позывной, канал, местоположение, владелец, модуляция, радиослужба | Связана с базой назначений |

Дополнительно в составе дистрибутива Light 32314 присутствуют файл списка
сигналов формата Радиосканера `RadioScanner.fcsvs` и файлы результатов
измерений параметров DVB-T(H) `*.i_dvb`.

Восемь баз против пяти — результат разбора дистрибутива RadioInspector
Light 32314; в документации по архитектуре 2008–2009 годов описаны только
пять основных баз.

### Наполнение баз

БД частотных назначений **не создаётся вручную**: она получается
конвертированием исходной базы **ФАИС** программой «Конвертор БД»
(`.ifixdb`). Сведения о технических параметрах РЭС подтягиваются из
**ЕТС** — единого технического справочника, который конвертируется из
формата Access в формат FireBird.

После конвертации доступно добавление записей вручную; при этом функция
«Добавить записи из другой базы» блокируется — она доступна только один
раз и только если ручные записи ещё не добавлялись.

Открытие базы сопровождается формой авторизации по базе сотрудников:
дальнейшая работа ведётся от имени выбранного сотрудника либо без
авторизации.

### Принятие решений в OpenRadioInspector

Связанность баз по частоте воспроизведена на уровне модели данных: база
панорам (`panorama.py`) хранит измерения с привязкой к частоте и времени,
база присвоений (`assignments.py`) — назначения, а модуль сопоставления
выполняет сверку по частоте. Отдельные файлы баз не воспроизводятся —
это упрощение, прямо зафиксированное в
[`limits.md`](limits.md). При этом сохраняется главное свойство
архитектуры оригинала: **результаты измерений остаются в открытом формате
и пригодны для обработки сторонними средствами**.

## 3. Географический фильтр и радиовидимость

Фильтр по географии задаётся прямоугольной областью, чувствительностью
приёмника (мкВ/м) и высотой подвеса приёмной антенны. Расчёт перебирает
все частоты базы назначений и для каждой проверяет критерий видимости —
сможет ли приёмник принять сигнал, находясь внутри заданного прямоугольника.

Дальность видимости определяется по формуле радиовидимости

```
Rм = 4,12 · (H^0,5 + h^0,5), км,
```

где H — высота подъёма передающей антенны, м; h — высота подвеса приёмной
антенны, м. Коэффициент 4,12 соответствует нормальной рефракции
(k = 4/3); геометрический горизонт (k = 1) даёт коэффициент 3,57.

Дополнительно учитываются мощность передатчика (dBkW) и коэффициент
усиления передающей антенны — то есть за пределами радиовидимости
применяется ограничение по бюджету линии.

В OpenRadioInspector это реализовано в `geoloc.py`:
`radio_horizon_km()`, `link_budget_range_km()`, `visibility_radius_km()`.

## 4. Планирование заданий

Подсистема планирования реализует отложенное выполнение работ. Задание
содержит описательную часть (название, цель, вид работы, основание, кто и
где выполняет), дату, время и длительность, а также прикреплённый файл
задания на выполнение измерений.

| Файл | Содержание |
|---|---|
| `*.itskfcs` | Задание на контроль фиксированных частот |
| `*.fcs` | Файл панорам фиксированных частот — результаты и одновременно источник задания |

При наступлении времени задание из статуса «В очереди на выполнение»
переходит в работу: загружается файл задания, выполняется сканирование,
результаты пишутся в `*.fcs`. Если прибор зарезервирован другим заданием,
выполнение прекращается с соответствующим статусом.

Ограничения на количество измерений и фонограмм задаются в самом файле
задания. При продолжении записи ранее сохранённого задания счётчики
восстанавливаются; при загрузке нового `*.itskfcs` — сбрасываются.

### Состав записи задания

База планирования `TASKPLAN.ITASKDB` содержит таблицу `TASKPLAN` примерно из
сорока колонок. Значимые группы полей:

| Группа | Поля |
|---|---|
| Идентификация | `TASKID`, `NAME`, `TYPE`, `PURPOSE`, `RKP`, `OTDEL`, `OTDEL_GRUPPA`, `OSNOVANIE`, `DRIVE` |
| Даты и время | `CREATED`, `PREPARED`, `REALSTART`, `REALSTOP`, `DATETIME`, `TIMESTART`, `DURATION` |
| Прерывания | `BREAKMEASDATETIME`, `OP` |
| Операции | `CREATEOP`, `PREPAREOP` |
| Оборудование и исполнители | `DEVICESIDS`, `HUNTERSIDS`, `DOPINFO` (BLOB), `SIZE` |
| Состояние | `STATUS`, `RESULTCODE`, `RESULTSTR`, `INFOSTR`, `PROCESSPOSITION` |
| Файлы и периодичность | `FILENAME`, `FCS`, `MOBILITY`, `NEXTTIMES`, `ATTACHMENT`, `VID`, `WEEP_INTERVAL`, `PROTOCOL` |

Вид задания, цель, предприятие, отдел, группа подразделения, основание и
носитель вынесены в отдельные таблицы-справочники; записи справочников
получают идентификаторы от генераторов базы.

В OpenRadioInspector этот состав полей перенесён в модель задания
(`radioinspector/tasks.py`): `ControlTask` хранит справочные идентификаторы,
служебные даты, состав оборудования и исполнителей, результат, мобильность и
вложения; `ReferenceBook` воспроизводит справочники с генераторами
идентификаторов.

Формат файла задания на контроль фиксированных частот отличается: оригинал
использует `*.itskfcs`, проект — JSON (`FixedFrequencyList`).

### Статусы задания

| Статус | Смысл |
|---|---|
| Сформировано | Задание создано, но файл задания не выбран; к выполнению не допускается |
| В очереди на выполнение | Ожидает назначенного времени |
| Отменено | Зарезервирован и не применяется |
| Выполняется | Идёт выполнение |
| Выполнено | Отработало заданное время |
| Снято с выполнения | Остановлено до истечения заданного времени |

Дополнительные статусы выделяются цветом: **ошибки** (красный) — «файл
задания (на сканирование частот) не найден», «аварийное завершение
приложения»; **предупреждения** (синий) — «принудительно завершено
оператором», «принудительно завершено другой задачей».

Реализовано в OpenRadioInspector: `tasks.py` (`ControlTask`, `TaskBook`,
`FrequencyControlProfile`).

## 5. Профиль контроля фиксированных частот

Рекомендации по параметрам сканирования, применяемые к каждой
контролируемой частоте:

| Параметр | Значение |
|---|---|
| Точек измерения на одну частоту | 7–11 |
| Динамический порог для записи фонограммы демодулированного аудиосигнала | не менее 6 дБ |
| Динамический порог для измерения частоты | не менее 20 дБ |
| Динамический порог для измерения контрольной полосы и внеполосных излучений | не менее 30 дБ |
| Полоса пропускания | не более 1/10 от необходимой полосы занимаемых частот |
| Полоса обзора | 1,5–3 от необходимой полосы |
| Уровень сигнала на экране | размах не менее половины экрана, без перегрузки |

## 6. Протоколы измерений

Отчёты формируются по шаблону. Значения подставляются по 317 ключевым
словам; синтаксис — `#Имя#`, регистрозначимый. Ключевые слова объединены
в группы по префиксам:

| Префикс | Содержание |
|---|---|
| `Tr_` | Сведения о передающей радиостанции |
| `Meas_`, `MER_`, `ME_`, `MERT_` | Результаты измерений напряжённости поля |
| `EstFc_` | Оценка частоты сигнала |
| `MOFBN_` | Измерение полосы по уровню −N дБ |
| `MOFBB2_` | Измерение полосы по критерию β/2 |
| `MCntr_` | Результаты контроля |
| `MEMO_`, `MES_` | Служебные и измерительные данные |
| `M1902_`, `M1902T_` | Данные по контрольной полосе частот (Нормы 19-02) |
| `MAltGeo_` | Данные альтернативной географии |
| `SbRng_` | Статистика занятости поддиапазона |
| `DVBT_` | Параметры DVB-T |
| `MOFBN` / `MOFBB2` | Различаются регистром: `MOFBN_` и `MOFBB2_` — разные ключевые слова |

Табличные блоки в шаблоне обрамляются маркерами `#D1# … #1D#`,
`#D2# … #2D#`, `#D3# … #3D#`: содержимое между маркерами — шаблон строки,
повторяемый по числу записей.

Справочник ключевых слов — [`report-keywords.md`](report-keywords.md).

## 7. Геоинформационная система и антенный компас

Опции RC-Geo, RP-Geo и I_MD-Geo добавляют к программам контроля
диапазона, радиопеленгования и управления приборами работу с
картами. Поддерживаются форматы MapInfo и OpenStreetMap с офлайн-кэшем;
координаты поступают от навигационного приёмника по протоколу NMEA
(4800 бод, 8 бит, без чётности) от GPS и GLONASS.

**Антенный компас** определяет направление на передатчик по максимуму
диаграммы направленности при повороте антенны в горизонтальной плоскости
на 360°. Дополнительно измеряются углы наклона в трёх плоскостях: азимут,
тангаж и крен. Показания магнитного компаса требуют поправки на
магнитное склонение — в северных районах ошибка достигает 25 градусов и
выше; поправку необходимо уточнять **не реже двух раз в год**, в
программе даны ссылки на онлайн-сервисы.

В OpenRadioInspector реализовано: `geoloc.antenna_compass()` — азимут
максимума, направления нулей, отношение вперёд/назад и перечень
кандидатных азимутов (±90° от нуля) для ненаправленной антенны.

## 8. Удалённый контроль (I_RemoteCheck)

Подсистема удалённого контроля рабочих мест операторов. Подключение
выполняется по TCP-порту **47383**. Программа контроля периодически
обращается к операторам — интервал обращения 20–30 секунд, поэтому
возникают задержки обновления. Состояние оператора отображается кружком:
голубой, зелёный или красный; в режиме контроля выводится идентификатор
и номер антенны. При наступлении контрольного события включается
звуковая тревога.

Протокол не документирован в открытом виде, поэтому в OpenRadioInspector
реализован родственный механизм — веб-интерфейс с потоком событий SSE и
REST API, — но **не совместимый на уровне протокола** с оригиналом.

## 9. Обработка IQ-данных (IQ_ProcessPRO)

Исходные данные — WAV-файлы с парными отсчётами I/Q в формате Int16 или
Float32, до 100 млн пар отсчётов. Записи **не калиброваны по амплитуде**,
поэтому абсолютные уровни по таким файлам не определяются. Поддерживаются
цифровой сдвиг (digital shift), цепочка фильтров (до 15 фильтров) и
децимация.

## 10. Модуль перехвата Wi-Fi (RInspectorWiFi)

Аппаратный модуль перехвата трафика сетей 2,4 и 5 ГГц. Четыре режима
канала: NoHT, HT20, HT40−, HT40+. Интерфейс Ethernet 10/100. Габариты
190 × 100 × 45 мм, масса не более 400 г. Данные сохраняются в
энергонезависимую память модуля в виде архива `*.IWArch` и автоматически
передаются на персональный компьютер; срок хранения архива — не менее
месяца при типовых условиях эксплуатации. Заводской адрес модуля —
192.168.200.201, адрес компьютера в той же подсети —
192.168.200.200/24.

Физическая часть (перехват 802.11 на частотах 2,4 и 5 ГГц, офлайн-архив,
прошивка) не воспроизводится; анализ перехваченных кадров реализован в
`wifi.py` на уровне библиотеки разбора 802.11.

## 11. Вариант RadioInspector Light

RadioInspector Light — не сокращённая версия InspectorRC, а вариант
InspectorRT: та же программа с тем же интерфейсом и тем же набором задач, но
без управления анализаторами спектра — только сканирующими приёмниками.

Особенности варианта, зафиксированные в руководстве «Состав и назначение
комплекса программ»:

* работа с приборами локально, без программы I_MasterDevice;
* геоинформационная система не поддерживается;
* управление средствами измерений по сети невозможно;
* одновременно может быть запущена только одна программа InspectorRT;
* запись и анализ фонограмм и управление сканирующим приёмником-аудиоконтролем
  встроены в программу.

Фактический набор возможностей пакета определяется пересечением трёх
множеств: документированные возможности RT-Light, включённые опции и класс
приборов «только сканирующие приёмники». Подробный разбор пакета 32314 —
в [`capabilities-light-32314.md`](capabilities-light-32314.md).
