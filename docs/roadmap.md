# Дорожная карта OpenRadioInspector

Рабочий план развития проекта. Документ отвечает на вопрос «что делается
сейчас, что делается дальше и чем проверяется готовность», и опирается на
контракт общей платформы, зафиксированный в `docs/platform-architecture.md`
(входит в PR #5) и на инвентарь коммерческого оригинала
(`docs/commercial-app-inventory.md`).

Правила работы с планом:

* каждый этап имеет проверяемый критерий приёмки; «почти готово» не считается;
* один срез — одна ветка — один PR; крупные изменения не смешиваются с мелкими;
* порядок слияния: контракт → архив → целостность → исполнители → клиенты;
* нереализованная функция не документируется как реализованная: расхождения
  фиксируются в [`limits.md`](limits.md).

## 1. Целевая архитектура

```text
AR-DV1 / tinySA Ultra / другие приборы
                    │
        независимые device workers
                    │
      общее ядро и единственный писатель
                    │
          REST /api/v1 + события SSE
                    │
      ┌─────────────┼──────────────┐
      │             │              │
 Raspberry Pi     Windows        macOS
 WebUI            GUI             SwiftUI GUI
```

Три сценария развёртывания: локальный (приборы и ядро на одном компьютере),
автономный (ядро на Raspberry Pi, управление браузером) и удалённый (Windows
или macOS подключаются к ядру на Raspberry Pi как клиенты).

Ядро — единственный владелец последовательных портов и единственный писатель
измерений. Клиенты не открывают приборные порты напрямую.

Вершина стека (`feature/windows-workflows`, 83 коммита впереди `main`) проходит
218 тестов. Слияние стека с текущим `main` проверено и проходит без
конфликтов. Новые модули стека: `contracts.py` (версионированный доменный
контракт), `session_service.py`, `session_store.py`, `device_workers.py`,
`automatic_detection.py`, `automatic_handoff.py`, пакет `windows/`
(Tkinter-оболочка, HTTP-клиент `/api/v1`, спектр, сценарии) и веб-панели
платформы `web/static/platform.*`.

Два отклонения от исходного плана, которые следует учитывать:

* Windows-клиент сделан на **Tkinter**, а не как оболочка с общим WebUI:
  интерфейс нарисован отдельно, общая только прикладная часть через `/api/v1`.
* Исполнители приборов — **программный стенд**: физические порты не открываются,
  аппаратные команды не заявляются реализованными. Реальные приборы и
  автоопределение устройства остаются за пределами стека.

## 3. Этапы

### Этап 0. Контракт ядра

Цель: зафиксировать доменную модель, API и правила обмена между клиентами и
ядром.

Срезы: версионированные модели сеанса, потока, свипа, наблюдения, кандидата и
исследования; служба жизненного цикла сеансов; журнал событий и SSE без окна
потери между replay и live; разделение команд управления и телеметрии;
формат экспорта сеанса.

Критерий приёмки:

1. `/api/v1/health` и `/api/v1/capabilities` отвечают и сообщают версию схемы,
   режим хранения и перечень поддерживаемых команд.
2. Частоты во всех ответах — целые Гц; все метки времени — UTC с интервалом
   начала и окончания.
3. `dBm` и `s_meter_count` не преобразуются друг в друга автоматически ни в
   одном маршруте и ни в одной сериализации.
4. Переподключение клиента с `Last-Event-ID` не теряет и не дублирует события.
5. Устаревший `/api/*` продолжает работать; веб-интерфейс не ломается.

Состояние: PR #5, ожидает слияния.

### Этап 1. Автономный узел и WebUI

Цель: Raspberry Pi как самостоятельный сервер наблюдения с управлением из
браузера.

Срезы: постоянный архив SQLite; два независимых приборных потока; восстановление
сеансов после перезапуска; WebUI с панелями «Обзор», «Сигнал», «Архив»,
«Задания», «Система»; автозапуск службы; ограничение объёма архива; UTC во
внутренних метках; экспорт сеанса.

Критерий приёмки:

1. Сеанс переживает перезапуск ядра: состояние, история событий и измерения
   восстановлены из архива.
2. Остановка одного приборного потока не останавливает второй.
3. Архив записывается одним писателем; параллельные записи двух потоков не
   приводят к ошибкам целостности.
4. Ограничение объёма архива срабатывает с предупреждением; молчаливое удаление
   измерений исключено.
5. WebUI открывает сеанс, показывает трассы обоих приборов и их водопады,
   отдаёт в браузер только отображаемый диапазон данных.
6. Служба стартует после перезагрузки и восстанавливается после кратковременной
   потери USB-устройства.
7. Один сеанс одновременно наблюдается двумя клиентами; команды идут через
   серверную очередь.

Состояние: PR #6 (архив) и PR #8 (исполнители) открыты; PR #7 закрывает
целостность. WebUI-панели отсутствуют — это ближайшая работа этапа.

### Этап 2. Windows-оболочка

Цель: рабочее место оператора на Windows без ручной установки Python.

Срезы: desktop-оболочка поверх общего WebUI (Tauri или иной вариант с
переиспользованием веб-интерфейса); локальное ядро; выбор COM-порта и
определение устройства; обработка исчезновения порта; выбор аудиоустройства;
автоматическое переподключение к удалённому серверу; переносимые пути;
диагностический журнал.

Критерий приёмки:

1. Установщик разворачивает приложение с работающим локальным ядром.
2. Локальный режим: оба прибора на COM-портах, ядро запускается автоматически.
3. Удалённый режим: подключение к Raspberry Pi даёт те же сеансы, трассы,
   архив и очередь исследований; локальные приборы не обязательны.
4. Исчезновение порта приводит к понятному состоянию в интерфейсе и
   восстановлению без перезапуска приложения.
5. Обе режима используют один и тот же формат архива и один API.

Состояние: не начат.

### Этап 3. Общая координация приборов

Цель: очередь исследований кандидатов, реализованная один раз в ядре и
доступная всем клиентам.

Срезы: реестр кандидатов; очередь исследований; ручная и полуавтоматическая
проверка; обратный переход AR-DV1 → детальный свип tinySA; устранение
повторов; приоритеты и тайм-ауты; аудио и результаты декодирования; связанная
временная шкала.

Критерий приёмки:

1. Кандидат, найденный потоком tinySA, ставится в очередь и обрабатывается
   потоком AR-DV1 без остановки спектрального обзора.
2. Обратный переход с детальным свипом tinySA не прерывает запись потока
   AR-DV1.
3. Повторный кандидат в пределах окна дедупликации не создаёт второго
   исследования.
4. Приоритет и тайм-аут исследования соблюдаются; зависшее исследование
   освобождает прибор.
5. Связанная временная шкала показывает события обоих приборов в единой шкале
   UTC.

Состояние: модели `Candidate` и `Investigation` объявлены в контракте (PR #5),
исполнители и очередь не реализованы.

### Этап 4. Задания, измерения, отчёты

Цель: планирование работ и оформление результатов на общем формате данных.

Срезы: планировщик; фиксированные частоты; автоматические совместные сеансы;
известные и разрешённые сигналы; занятость; измерения; протоколы и экспорт;
синхронизация настроек между клиентами.

Критерий приёмки:

1. Задание задаёт диапазоны и фиксированные частоты, расписание и условия
   запуска; статус задания виден всем клиентам.
2. Результаты измерений сохраняются в архив с привязкой к методике, прибору и
   сеансу; методика определяется явно, а не выводится из формата хранения.
3. Отчёт воспроизводится на любой платформе из экспортированного сеанса.
4. Экспорт сеанса открывается в другой платформе без потери привязки ко
   времени и прибору.

Состояние: PR #3 (планировщик и DOCX) открыт; схема базы результатов измерений
оригинала разобрана и может служить образцом — см.
[`commercial-app-inventory.md`](commercial-app-inventory.md), раздел 6.2.

### Этап 5. Специализированные функции

Цель: функции, требующие отдельных подсистем и отдельного оборудования.

Очередь по убыванию отдачи: эталонная панорама и разность панорам; динамический
(адаптивный) порог; измерение параметров DVB-T; геоинформационная система;
удалённое аудио; IQ и цифровые стандарты; Wi-Fi и специальное оборудование.

Критерий приёмки (для каждой функции отдельно): функция описана в
[`limits.md`](limits.md) как реализованная, имеет тест на эталонном примере
и не меняет формат архива без версии миграции.

## 4. Сквозные инварианты

* частоты хранятся в целых Гц;
* время — UTC, у измерений есть интервал начала и окончания;
* исходные уровни неизменяемы, производные калиброванные значения хранятся
  отдельно;
* `dBm` tinySA и отсчёты S-метра AR-DV1 не смешиваются;
* каждая запись содержит идентификатор прибора и сеанса;
* API и схема базы версионированы, изменения требуют миграции;
* ядро — единственный владелец портов и единственный писатель архива;
* один экземпляр ядра владеет каждым прибором; несколько клиентов наблюдают,
  но команды проходят через очередь;
* экспортированный сеанс открывается на любой платформе.

## 5. Критерии первого общего выпуска

Релиз считается первым общим, когда один и тот же сценарий проходит во всех
трёх вариантах:

1. К Raspberry Pi, Windows или Mac подключены оба прибора.
2. Запускается общий сеанс.
3. tinySA и AR-DV1 пишут независимые архивы.
4. Оператор видит трассы и состояние устройств.
5. Кандидат tinySA передаётся на AR-DV1 без остановки спектрального обзора.
6. Сеанс сохраняется и открывается после перезапуска.
7. Windows и macOS подключаются к сеансу на Raspberry Pi.

Пункты 1–4 и 6 покрываются этапами 0–1, пункт 5 — этапом 3, пункт 7 — этапами
2–3. Первым общим выпуском, таким образом, является срез этапа 3.

По стеку: пункт 1 — PR #5 и #8, пункт 2 — PR #6, пункт 3 — PR #8, пункт 4 —
PR #10, пункт 5 — PR #9, #11, #12 и #13, пункт 6 — PR #6 и #7, пункт 7 — PR #2,
#4, #14 и #16.

## 7. Решение по коммерческому диску в публичной ветке

Вопрос формулируется так: **какие категории файлов коммерческого диска остаются
в публичной ветке `main` репозитория?** Он распадается на четыре независимых
решения с разным риском и разной ценой, поэтому решать их нужно по
отдельности, а не одним «оставить или удалить».

### 7.1. Что лежит в публичной ветке

| Категория | Файлов | Объём |
|---|---|---|
| Исполняемые модули программы и библиотеки | 103 | 53,0 МБ |
| Установщик: загрузчик, MSI, ресурсы | 3 | 4,5 МБ |
| Драйверы ключей Guardant | 2 | 10,0 МБ |
| Сторонний сервер FireBird 2.5 | 2 | 16,0 МБ |
| Документация правообладателя и инструкция Guardant | 28 | 49,1 МБ |
| Пустые базы данных комплекса | 9 | 10,3 МБ |
| Конвертер базы Радиосканера | 3 | 4,2 МБ |
| Просмотрщик списка сигналов | 3 | 10,2 МБ |
| Прочее: datasheet, справка, ресурсы, конфигурация | 10 | 11,3 МБ |
| **Всего** | **163** | **168,6 МБ** |

Наш собственный код и документация — 67 файлов, 0,8 МБ. То есть коммерческая
часть занимает 99,5 % объёма публичной ветки, и клон репозитория весит
169 МБ против менее чем мегабайта нашего кода.

### 7.2. Что установлено о правах и что осталось неизвестным

Установлено:

* программа и документация принадлежат правообладателю — ООО «РадиоСофт»;
* лицензия пакета — электронный ключ Guardant, номер ключа совпадает с
  номером пакета 32314; драйверы Guardant и инструкция по их применению
  распространяются компанией «Актив» и самостоятельного права на
  перепубликацию не дают;
* FireBird 2.5 распространяется по MPL-1.1, то есть перепубликация
  допустима, но обязывает сохранить уведомление о лицензии — и это не наш
  объект;
* MIT-лицензия проекта распространяется на наш код и не даёт прав на
  коммерческое программное обеспечение и документацию правообладателя.

Не установлено:

* публичных лицензионных условий самого RadioInspector найти не удалось —
  это пробел, а не повод додумывать;
* договор, по которому диск получен, и условия его передачи неизвестны.

Отраслевой контекст: типичные лицензионные условия российского ПО запрещают
копирование и перенос носителей, декомпиляцию и инженерный анализ, передачу
права третьим лицам и раскрытие программного обеспечения. Применимость этих
формулировок к конкретному изделию определяется договором с правообладателем,
а не нашим проектом.

### 7.3. Четыре независимых решения

| Решение | Предмет | Варианты | Цена каждого варианта |
|---|---|---|---|
| D1 | Исполняемые модули, установщик, ключевые драйверы (67,5 МБ) | оставить / вынести / удалить | Оставить — публикация защищённого ПО правообладателя. Удалить — сверять больше не с чем, но все факты уже извлечены |
| D2 | Документация правообладателя и справка (49,1 МБ) | оставить / вынести / заменить выжимкой | Оставить — публикация чужих руководств. Заменить — останется наш собственный текст со ссылками на функции |
| D3 | Пустые базы комплекса (10,3 МБ) | оставить / вынести / заменить DDL-схемой | Заменить DDL — сохраняется вся модель данных, теряется готовый файл базы |
| D4 | Сторонний FireBird и Guardant (26,0 МБ) | оставить / удалить | Удалить — ничего не теряется, лицензии сторонних правообладателей не распространяются на наши цели |

### 7.4. Рекомендация

D1 — удалить, D2 — заменить выжимкой, D3 — заменить DDL-схемой, D4 — удалить.
Итог: публичная ветка содержит только наш код и нашу аналитику.

Обоснование: инженерная ценность коммерческих файлов для нас уже извлечена.
Формы, надписи, реестр приёмников, состав баз и каталог методик лежат в
[`commercial-app-inventory.md`](commercial-app-inventory.md) и
[`measurement-methods.md`](measurement-methods.md), а программы разбора — в
[`tools/analysis/`](../tools/analysis/README.md). Удаление файлов из публичной
ветки отнимает у проекта ровно то, что мы уже зафиксировали в своих
документах, и снимает правовой риск целиком: ни чужих бинарников, ни чужих
руководств, ни сторонних лицензий.

Если нужна возможность сверки с оригиналом, копия диска переносится в
приватное хранилище; тогда публичная ветка содержит ссылку на архив и
инструкцию, как сверить конкретный факт, но не сами файлы.

### 7.5. Исполнение решения

Три технических детали, которые меняют трудоёмкость:

1. **Удаление из ветки не удаляет файлы из истории.** Блобы остаются в репозитории
   и доступны по хэшам, пока репозиторий существует. Полная очистка требует
   переписывания истории: `git filter-branch --index-filter` с удалением
   каталога из индекса и последующим `push --force`. Утилиты `git filter-repo`
   в окружении нет, `git filter-branch` доступна.
2. **История короткая и диск добавлен одним коммитом** (`33cae7f`, PR #1), вся
   публичная ветка — девять коммитов. Переписывание затрагивает один коммит и
   технически выполняется за несколько минут.
3. **После удаления меняются ссылки в документации:** раздел воспроизводимости
   инвентаря и README инструментов должны ссылаться на приватный архив, а
   тесты разбора — оставаться работоспособными в режиме пропуска.
4. **Общей базой стека из двенадцати PR служит коммит `33cae7f` — тот самый,
   что добавил коммерческий диск.** Удаление диска с переписыванием истории
   уничтожает эту базу, и все двенадцать веток стека придётся перебазировать.
   Проверено при этом: сам стек коммерческого диска не требует — вершина стека
   проходит 218 тестов без него, а слияние стека с текущим `main` не даёт
   конфликтов. Отсюда порядок: **решение по диску принимается до слияния
   стека**; после слияния цена удаления вырастет, потому что переписывать
   придётся уже слитое.

Порядок работ: решение по D1–D4 → создание приватного архива при необходимости
→ переписывание истории и принудительная отправка → правка ссылок в
документации → повторный прогон тестов и проверка клона.
