# Продвижение дорожной карты

## 8 ноября 2026: встроенный частотомер

База этого среза — `feature/measurement-results`, PR #91. Это продолжение
открытого стека, не утверждение о наличии этих возможностей в `main`. Ни
одна ветка или PR этим срезом не объединяется, не закрывается и не
удаляется.

Взят седьмой пункт функционального бэклога: встроенный частотомер,
измерение частоты с погрешностью прибора. Реализован ограниченный,
законченный сценарий: измерить частоту пика архивного dBm свипа в явном
окне с заданным разрешением частотомера и получить оценку с честной
границей погрешности.

Параболическая интерполяция трёх бинов применяется только при равномерной
локальной сетке и пике внутри окна; иначе измерением считается сам бин
пика. Погрешность — граница `max(разрешение, сетка)/2`: измерение не
обещает лучше разрешения прибора и записанного растра. Это производная
оценка по записанным данным, не показание аппаратного счётчика. Результат
несёт готовые `values` для записи через базу результатов измерений
(методика `frequency_counter` в каталоге). Raspberry Pi WebUI, Windows Tk
и macOS SwiftUI показывают форму измерения и результат. Контракт:
[frequency-counter.md](frequency-counter.md).

Это срез измерения, а не полная реализация оригинального счётчика:
аппаратное измерение прибором, стандартизованный сдвиг
(`MEAS_COUNTER_FC_STDOFFSET`) и калибровка остаются отдельной работой.
Исходный
[план проекта](https://github.com/qlolp/openradioinspector/blob/main/docs/roadmap.md)
содержит историческое состояние стека; реальные возможности следует проверять
по конкретной ветке и её API-контракту.

## 8 ноября 2026: база результатов измерений с раздельными методиками

База этого среза — `feature/frequency-raster-rounding`, PR #88. Это
продолжение открытого стека, не утверждение о наличии этих возможностей
в `main`. Ни одна ветка или PR этим срезом не объединяется, не закрывается
и не удаляется.

Взят шестой пункт функционального бэклога: база результатов измерений с
раздельными методиками. Реализован ограниченный, законченный сценарий:
записать результат измерения с явной методикой из каталога реализованных
(β/2, −N дБ, контрольная полоса, мощность над порогом, центральная частота,
отношение сигнал/шум, координаты) и отдельным кодом результата
(`norm` / `not_norm` / `not_measured`).

Методика — поле результата, а не свойство формата хранения; код результата
хранится отдельно от числовых значений, как таблицы `*_RESULT` и
`*_RESULTCODE` оригинала. Запись привязана к сеансу, потоку прибора и
интервалу UTC; исходные измерения архива не изменяются. Каталог методик
отдаётся через `GET /api/v1/measurement-catalog`. SQLite-архив: аддитивная
миграция схемы v3 → v4, таблица `measurement_results` с индексами по
сеансу/методике. Raspberry Pi WebUI, Windows Tk и macOS SwiftUI показывают
каталог, форму записи и список результатов. Контракт:
[measurement-results.md](measurement-results.md).

Это база результатов, а не полный этап 4: автоматический расчёт результатов
из свипов, нормативные вердикты, оставшиеся методики каталога (DVB,
частотомер, модуляции, НДБ) и сущность заказчика (MEASCLIENT) остаются
отдельной работой. Исходный
[план проекта](https://github.com/qlolp/openradioinspector/blob/main/docs/roadmap.md)
содержит историческое состояние стека; реальные возможности следует проверять
по конкретной ветке и её API-контракту.

## 8 ноября 2026: округление частот обнаруженных сигналов

База этого среза — `feature/sweep-context-window`, PR #77, вершина открытого
стека. Это продолжение открытого стека, не утверждение о наличии этих
возможностей в `main`. Ни одна ветка или PR этим срезом не объединяется, не
закрывается и не удаляется.

Проверены открытые PR (#39 и стек #37–#77): срезов округления частот среди
них нет. Взят пятый приоритет функционального бэклога: округление частоты
обнаруженных сигналов по таблицам. Реализован ограниченный, законченный
сценарий: загрузить или набросать переносимую таблицу частотной сетки
(диапазоны с шагом), отметить кандидатов сеанса и получить округлённые
центральные частоты.

Ядро округляет до ближайшей точки сетки своей записи (`start_hz + k·step`,
полувверх при равном расстоянии, с ограничением последней точкой записи);
исходная `center_frequency_hz` возвращается из архива без изменений.
Частоты вне всех записей не округляются и попадают в `unmatched_count`.
Raspberry Pi WebUI, Windows Tk и macOS SwiftUI показывают исходное и
округлённое значения и позволяют сохранить проверенную таблицу.
Контракт и ограничения: [frequency-raster.md](frequency-raster.md).

Это пятый пункт бэклога, а не завершение этапа: автоматическое применение
при обнаружении, привязка к БД присвоений («Шаг сетки частот»), правка
кандидата и нормативная сверка сетки каналов остаются отдельной работой.
Исходный [план проекта](https://github.com/qlolp/openradioinspector/blob/main/docs/roadmap.md)
содержит историческое состояние стека; реальные возможности следует проверять
по конкретной ветке и её API-контракту.
