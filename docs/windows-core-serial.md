# COM-порты общего ядра Windows

Срез добавляет транспорт Windows к существующим `tinysa-serial` и
`ardv1-serial`. Протоколы, безопасный setup, очередь команд и измерительная
логика общие с Linux/macOS. Только ядро открывает порт; ОС HTTP-клиента
не влияет на выбор транспорта. API v1 и исходные единицы не меняются.

## Установка и запуск

На компьютере ядра установите Python 3.10+ и пакет с дополнительной
зависимостью pySerial 3.5:

```powershell
py -m pip install ".[serial]"
py -m radioinspector serve --session-database sessions.sqlite
```

Команды выполняются из корня исходников. Это запуск из Python, а не готовый
Windows installer. Путь архива выбирает оператор; для проверки используйте
отдельный тестовый архив.

Создайте serial-профиль через WebUI `/platform`, Windows GUI или macOS GUI.
Укажите два разных порта **компьютера ядра**, например `COM3` и `COM12`.
Создание оставляет сеанс в `draft` и не открывает порты.
Устаревшая или закрытая Tk-форма после смены подключения не может отправить
профиль прежнему серверу; повторные ожидающие действия блокируются. Сначала запустите
сеанс, затем явно запустите приборные потоки.

Windows GUI имеет отдельный переключатель физических приборов. Симуляторы
и serial взаимно исключаются; без обоих переключателей сохраняется прежний
профиль без исполнителей. WebUI и macOS создают отдельный serial-профиль;
их начальные настройки — обзор 88–108 МГц, 201 точка, RBW 10 кГц и receiver
FM 145,5 МГц. Они не объявляют цифровое декодирование.

## Поведение транспорта

- На Windows ядро использует pySerial; на POSIX сохраняется транспорт
  `termios` без этой зависимости. Симулятор никогда не открывает COM-порт.
- Принимаются ASCII-имена `COM1`, `COM12`, а также `\\.\COM12` без пробелов.
  Регистр нормализуется; URL вроде `socket://…` и `loop://…` запрещены.
  Новый explicit serial-сеанс не может назначить одному COM-порту два потока
  через разные aliases: ядро возвращает 400 до события/записи/открытия порта.
  Исторические архивы не переписываются, POSIX пути вне COM-синтаксиса
  сравниваются точно.
- Raw 8N1, 9600/19200/38400/57600/115200 baud, без flow control; DTR/RTS
  отключаются до открытия. Драйвер USB может кратковременно переключить линии
  при открытии — это отдельно проверяется на оборудовании.
- Запись ограничена общей секундой, частичная запись дописывается в пределах
  того же срока. Чтение ожидает один байт, затем забирает уже доступные байты;
  полный короткий ответ не ждёт заполнения 4096-байтного буфера.
- Перед каждой записью остатки непрочитанного ответа в stash или входном
  буфере вызывают отказ, а не flush/игнорирование. Уже накопленный лишний ACK
  не должен подтвердить следующую команду. Закрытие COM во время I/O
  не выдаётся за успешное чтение/запись.
- Разбор CRLF и `ch>` общий с POSIX. Неподтверждённый setup tinySA и поздние
  ответы по-прежнему блокируют продолжение соединения; требуется stop/start.
- Ошибки открытия, записи, чтения и закрытия превращаются в `WorkerError`;
  существующие API и три клиента показывают состояние конкретного потока.
  Второй прибор продолжает работать. Автоматического переподключения нет.
- Отсутствие pySerial даёт понятную инструкцию установки на компьютере ядра.
  Производные dB и исходные dBm/S-meter остаются раздельными.

## Проверка

```sh
python -m unittest tests.test_windows_serial_transport tests.test_serial_instruments tests.test_tinysa_setup_guard
python -m unittest tests.test_windows_workflows tests.test_webui_serial_session
# На компьютере с Tk desktop:
ORI_WINDOWS_RELEASE_TK=1 python -m unittest tests.test_windows_release_flows
```

Тесты используют поддельный COM backend, реальные адаптеры и настоящий
локальный HTTP. Проверяются отдельные соединения, safe setup, исходные
единицы, независимость AR-DV1 после сбоя tinySA и закрытие дескрипторов.
Дополнительный тест использует настоящий pySerial `loop://` только внутри
тестового процесса, без устройства. WebUI проверяется исполнением JavaScript,
Windows-форма — скрытыми Tk widgets на Mac.

Workflow `.github/workflows/windows-core.yml` запускает синтетические тесты
на Windows. Workflow закреплён на проверенных commit SHA официальных actions, проверяет
точный head PR и не сохраняет Git credentials. Наличие workflow не означает
успешный удалённый прогон.
**Windows OS с реальными COM-портами, USB unplug/replug и оба физических
прибора ещё не проверены.** `hardware_validation=not_run` сохраняется.

Официальная документация зависимости: [pySerial API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html).


В исходном Windows CI PR #85 выявлены ошибки переносимости UTF-8/CRLF,
незакрытых SQLite/lock handles и MIME JavaScript. Интеграция устраняет причины,
а не отключает эти тесты; фактический итог последнего Windows run указывается
в PR и не выводится из результатов Mac.


SHA-256 потокового импорта/экспорта теперь включает исходные переводы строк.
Старые checkpoints от CRLF/CR файлов могут получить checkpoint_mismatch
после обновления; автоматической миграции нет. Отказ происходит до ingest
POST и перезаписи checkpoint, в том числе для completed и dry-run. Сохраните
исходный файл и checkpoint и согласуйте ранее подтверждённые batches перед
перезапуском. LF checkpoints и обычные серверные LF exports не меняются.
Слепое начало импорта заново в уже заполненное назначение не является миграцией.


Итог локальной интеграционной проверки после исправлений CI: 981 Python/Node, 163 Swift SDK и
108 native-тестов без пропусков, unsigned Xcode build успешен. Семь временных
SQLite сохранили полный logical dump, серверы остановлены. Независимый review
закрыт без блокеров. Истинный Windows CI проверяется отдельно после публикации
точного head; физические COM/USB не проверялись.


Первый Windows run интеграции #87 (c3d86eef, run 42478842777) исполнил
977 тестов и выявил четыре оставшихся CRLF-сравнения и гонку DOCX replace.
Проверки assets теперь сравнивают точные UTF-8 bytes; отдельный тест создаёт
временные CRLF-копии и проверяет HTTP body и Content-Length.

Запись DOCX повторяет только атомарный replace того же закрытого staging-файла
при Windows winerror 5/32/33: начальная попытка и не более 10 повторов с паузой
50 мс. Destination не удаляется, fallback на копирование отсутствует. При
постоянной блокировке/ACL исходная ошибка возвращается; чужие временные файлы
не затрагиваются. POSIX и остальные ошибки не повторяются. Это ограниченная
защита от краткого contention, а не гарантия записи в открытый другим
приложением или защищённый от записи файл.
