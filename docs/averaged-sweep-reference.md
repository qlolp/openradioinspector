# Усреднённый архивный эталон

Общее ядро строит производную эталонную панораму из 2–16 выбранных архивных
свипов и сравнивает с отдельным свипом того же потока. WebUI, Windows Tk и
macOS SwiftUI запрашивают расчёт только по кнопке. Исходные измерения и
именованный каталог не меняются; результат и закреплённая выборка живут
только в окне клиента.

## Метод

Усредняется **линейная мощность**, а не численные значения dBm. Для каждого
индекса частоты и N свипов:

```text
reference_dbm = 10 * log10(sum(10 ** (source_dbm / 10)) / N)
delta_db = target_dbm - reference_dbm
```

Каждый свип имеет одинаковый вес независимо от длительности и промежутков
между измерениями. Например, −100 и −90 dBm дают примерно −92,596373 dBm,
а не −95 dBm. Эта формула описывает смысл, а реализация использует устойчивый
log-sum-exp относительно максимального уровня. Она не возводит 10 напрямую
в степень огромного исходного уровня. Очень малый вклад относительно
максимума может округлиться до нуля в арифметике double. Окончательный
округлённый уровень ограничивается минимумом и максимумом исходных уровней:
это устраняет выход на один ULP за физическую границу среднего.

Это не временное интегрирование, не «чистый шум», не оценка доверительной
вероятности и не метрологическая калибровка. Сильный или длительный сигнал в
выборке поднимает эталон. Пригодность выбранного фона определяет оператор.

Обязательны:

- один сеанс, один поток, исходная единица dBm;
- 2–16 различных ID эталонных свипов и отдельный target ID;
- точное совпадение частотной сетки, порядка и числа точек, без интерполяции;
- 1–16 384 точки, целые частоты 0–9 007 199 254 740 991 Hz;
- одинаковые известные записанные настройки, кроме верхнего поля sequence.

Проверка настроек общая со [сравнением двух свипов](sweep-comparison.md).
Пустые настройки, null вне игнорируемого sequence и несовместимые единицы
отклоняются. true не равно числу 1; численные 1 и 1.0 эквивалентны. Полные
настройки, включая sequence, остаются в происхождении каждой исходной записи.
Совпадение метаданных не доказывает одинаковые антенну, тракт или условия.

API не требует, чтобы эталонные интервалы предшествовали target: он вычисляет
явно указанную выборку. Это не автоматический сценарий N1/N2. Сводный UTC
интервал эталона от минимального начала до максимального окончания является
охватывающим интервалом, а не непрерывным временем наблюдения. Отдельные
исходные интервалы возвращаются полностью. Порядок источников совпадает с
порядком ID в запросе. Повторить один ID ради увеличения его веса нельзя.

## HTTP API

```text
POST /api/v1/sessions/{session_id}/sweep-average-comparison
```

```json
{"reference_ids":["reference-1","reference-2"],"target_id":"target-3"}
```

Ровно два поля. ID — непустая строка до 128 Unicode code points; пробелы
внутри ID не меняются. Параметров URL нет, в том числе пустого `?`.
Повторные ключи JSON, некорректный UTF-8 и неоднозначное HTTP framing
отклоняются. Тело ограничено 8192 байтами до чтения; нужен один десятичный
Content-Length, Transfer-Encoding не поддерживается. Ограничение относится
к новому маршруту и не изменяет старые API.

Оболочка ответа стандартная: contract, contract_version и data. Пример data:

```json
{
  "session_id": "session-1",
  "stream_id": "spectrum-1",
  "frequencies_hz": [100000000],
  "reference": {
    "method": "mean_power",
    "count": 2,
    "source_ids": ["reference-1", "reference-2"],
    "sources": [
      {"id":"reference-1","interval":{"started_at":"2026-11-08T00:00:00Z","ended_at":"2026-11-08T00:00:01Z"},"settings":{"rbw_hz":10000,"sequence":1}},
      {"id":"reference-2","interval":{"started_at":"2026-11-08T00:00:02Z","ended_at":"2026-11-08T00:00:03Z"},"settings":{"rbw_hz":10000,"sequence":2}}
    ],
    "interval": {"started_at":"2026-11-08T00:00:00Z","ended_at":"2026-11-08T00:00:03Z"},
    "levels": [-92.59637310505757],
    "level_unit": "dBm"
  },
  "target": {
    "id": "target-3",
    "interval": {"started_at":"2026-11-08T00:00:04Z","ended_at":"2026-11-08T00:00:05Z"},
    "levels": [-80.0],
    "level_unit": "dBm",
    "settings": {"rbw_hz":10000,"sequence":3}
  },
  "delta_levels": [12.59637310505757],
  "delta_unit": "dB",
  "max_increase": {"frequency_hz":100000000,"delta_db":12.59637310505757},
  "min_change": {"frequency_hz":100000000,"delta_db":12.59637310505757},
  "points": 1
}
```

Производный эталон не получает фиктивный ID исходного Sweep. В sources
передаются происхождение и настройки, но не дублируются массивы уровней всех
N свипов. Исходные свипы доступны прежним архивным API. Клиенты уже держат
замороженные копии выбранных источников.

max_increase — алгебраический максимум разности, в том числе отрицательный;
min_change — минимум. При равенстве выбирается первая точка в порядке массива.
Неконечная итоговая разность отклоняется; промежуточная разность двух
эталонных источников не вычисляется и не является условием совместимости.

Ошибки:

- 400 invalid_request: структура, ID, дубликаты, параметры URL или framing;
- 404 session_not_found / sweep_not_found: сеанс или ID отсутствует в этом сеансе;
- 409 average_reference_incompatible: несовместимые источники, слишком большая
  сетка или не представимый конечным числом результат;
- 413 request_too_large: превышен предел тела запроса.

features.averaged_sweep_reference сообщает поддержку в capabilities.
HTTP POST здесь означает передачу параметров вычисления, а не изменение
архива. Нет автоматических повторов; старое ядро возвращает ошибку в отдельной
панели, остальные функции клиента продолжают работать.

## Сценарий трёх клиентов

1. Выберите сеанс и спектральный поток с архивными dBm sweeps.
2. Задайте N от 2 до 16, по умолчанию 3. Нужны как минимум N+1 подходящих
   свипов в полученном клиентом окне.
3. Явно закрепите N предыдущих свипов: из текущего окна берутся N записей
   непосредственно перед последней. Последняя оставлена для сравнения.
4. Сверьте показанные ID и UTC, задайте порог прироста и минимальный размер
   области. Нажмите сравнение и обнаружение изменений.
5. Рассмотрите исходный target и средний эталон в dBm, разность отдельно в dB,
   затем список областей, прошедших заданный порог.

«Предыдущие» означает порядок записей в полученном окне API, а не обещание
непрерывности или сортировки по времени измерения. Не хватает N+1 записей —
выборка не создаётся; число N не уменьшается молча. При необходимости сначала
накопите нужные архивные измерения обычным разрешённым сценарием. Панель сама
не запускает приборы и не создаёт фиктивных измерений.

Закрепление локальное, без сетевого POST. Последующие sweeps не меняют
закреплённые источники и готовый результат. Ядро читает выбранные точные ID,
даже если они уже вышли из окна последних свипов. Новый расчёт выполняется
только по кнопке. Target не может входить в выборку эталона.

Изменение N, очистка, смена сервера/сеанса/потока или отключение сбрасывает
выборку и результат, отменяет или обесценивает ожидающий ответ. Повторные
клики не создают очередь вычислений. Ожидание ограничено 8 секундами в WebUI
и Windows, 6 секундами в macOS. Windows не гарантирует принудительное
прерывание urllib: поздний результат игнорируется, новый запрос не ставится
в очередь за устаревшим транспортом.

Все клиенты ограничивают ответ 2 000 000 байтами до JSON-декодирования.
Необычно большие метаданные могут превысить предел даже при разрешённом
числе точек. Ответ отклоняется целиком, без усечения. Принятый график
содержит все точки, включая одиночную и повторяющиеся частоты. Клиенты
проверяют происхождение, единицы и согласованность ответа; алгоритм
усреднения существует только в ядре.

## Хранение и ограничения

Чтение SQLite идёт по точным ID под одной блокировкой службы. Нет загрузки
всего архива; memory backend ищет в уже имеющемся списке. Размер работы
ограничен N × число точек. Нет записи измерений, событий, кандидатов, задач,
команд приборам или изменения именованного каталога. Срез доступен при
заполненном архиве и не меняет schema v3. Старая миграция v2→v3 из PR70
по-прежнему требует резервной копии остановленного архива перед обновлением.

Не реализованы сохранение усреднённого эталона в каталог, экспорт производного
результата, временное взвешивание, сравнение разных потоков/сеансов, применение
результата в runtime detector и нормативная оценка. Read-only обнаружение
непрерывных областей изменений описано отдельно в
[sweep-change-detection.md](sweep-change-detection.md). Односвиповые именованные
ссылки и переносимая маска сохраняют собственные независимые сценарии.

## Воспроизводимая проверка

```bash
python -m unittest discover -s tests -t .
swift test --package-path macos/SpektrKomandy
swift test --package-path macos
xcodebuild -project macos/DvoynoyObzor.xcodeproj -scheme DvoynoyObzor \
  -configuration Debug -destination 'platform=macOS' \
  -derivedDataPath macos/DerivedData CODE_SIGNING_ALLOWED=NO build
```

Для локального синтетического HTTP smoke, без пользовательского архива:

```bash
python -m tests.average_smoke_server --port 56037
# В другом терминале:
ORI_AVERAGE_SMOKE_BASE_URL=http://127.0.0.1:56037 \
  swift test --package-path macos/SpektrKomandy
```

Фикстура создаёт временный SQLite: average-one / spectrum-one, источники
one-sweep-1…3 и target one-sweep-4, 101 точку 100–110 MHz. Ожидаемый эталон
на первой частоте примерно −94,3179827593 dBm, максимальное изменение
+20 dB на 103 MHz, минимальное −10 dB на 107 MHz. После Ctrl-C сервер
сравнивает SHA-256 полного логического dump до/после и очищает временный
каталог. Это синтетическая программная проверка, не работа с приборами.

Опциональные live HTTP тесты пропускаются без соответствующих переменных
окружения. Визуальная проверка, Windows OS, аппаратная и метрологическая
проверки учитываются отдельно и не подменяются успешными unit-тестами.

Проверка среза 8 ноября 2026: 617 Python/Node, 113 Swift API и 63 native
теста прошли; Xcode собрал приложение без подписи. Все три клиента проверены
на реальном локальном HTTP с синтетическими данными. Дополнительно среднее
сверено с независимым NumPy oracle на 300 выборках; проверены округление на
границе double, микросекунды UTC, потеря соединения и совпадающие точки графика.
Независимое ревью не оставило замечаний. Визуальный осмотр браузера/SwiftUI,
Windows OS, приборы и метрологическая пригодность не проверялись.
