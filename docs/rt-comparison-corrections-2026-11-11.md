# Скорректированное сопоставление RadioInspectorRT — 11 ноября 2026

Запись фиксирует поправки к [`rt-comparison.md`](rt-comparison.md) по
прочитанному коду и более свежим материалам проекта. Она не повторяет
сравнение, а уточняет его оценки и приоритеты.

Состояние при проверке: `main`, HEAD `15b700b` (11 ноября, 12:18 UTC) — на
момент записи в репозитории `origin/main` уже указывал на `80c549c` (история
переписывалась); поправки ниже сверены по файлам текущего дерева `main`.

## 1. Главная поправка: общий протокол ≠ поддержка прибора

`rt-comparison.md` формулировал разрыв в числе приборов как «мнимый» и
предлагал считать большинство приборов работающими через общие драйверы.
Прочитанный `radioinspector/devices/scpi.py` этого не подтверждает: там
фиксированная последовательность команд (PRESET/STAR/STOP/RESB/VBW/POIN/
REFL/ATT/INIT/TRAC:DATA?) без выбора командного профиля по модели или
производителю. Наличие TCP/VXI-11-транспорта и чтения `*IDN?` не доказывает,
что конкретный прибор выполнит набор команд с нужной семантикой RBW/VBW,
детектора, единиц, частотной сетки и завершения измерения.

Корректное позиционирование:

> «Есть универсальные интерфейсы подключения и несколько целевых приборных
> профилей; совместимость и полнота функций подтверждаются отдельно для
> каждой модели».

Некорректное:

> «Поддерживаем почти те же 200 приборов, просто через SCPI и SoapySDR».

## 2. Поправки, внесённые в `rt-comparison.md`

| Строка | Было | Стало |
|---|---|---|
| Передача аудио по сети (RemoteMD) | «нет» | PCM-доставка реализована (`audio_stream.py`), сквозной аппаратный тракт не подтверждён — «частично» |
| Покрытие оборудования | «паритет по протоколу, нет по quirks» | универсальные транспорты; совместимость по модели не подтверждена |

## 3. Где проект уже сильнее, чем показывает сравнение

* **Сетевое аудио на уровне транспорта реализовано.** `radioinspector/audio_stream.py`
  содержит PCM 16-бит LE mono, до четырёх подписчиков, ограниченные очереди,
  отбрасывание старых блоков при отставании клиента, счётчики потерь и разделение
  по сеансу/потоку; проверялся настоящими сокетами (см. `docs/repository-audit.md`).
* **Двухприборная архитектура существует.** Независимые исполнители, перестройка
  приёмника, исследования и отдельные opt-in политики detection/handoff/completion
  описаны в `docs/limits.md`; там же честно зафиксировано
  `hardware_control=true`, `hardware_validation_not_run=true`. Программный контур
  есть — эквивалентность SoundScaner на стенде не подтверждена.

| Сетевое аудио | сравнение — «нет»; код и аудит — транспорт реализован |

| Количество API | в документах встречаются разные итоговые числа маршрутов |
| Тесты | разные числа на разных SHA и в разных окружениях |

Это не дефекты кода, а проблема качества сведений о готовности продукта.

## 5. Где разрыв с RT остаётся принципиальным

1. **Архивный анализ ≠ непрерывное обнаружение.** Сравнение панорам, маска,
   адаптивный порог и окно N1/N2 запускаются явно, анализируют ограниченный
   набор, не создают кандидатов и не запускают исследование. Связка
   «свип → анализ → событие → контекст → кандидат → исследование →
   аудио/измерения → архив → отчёт» ещё не сквозная.
2. **«Realtime» и «24/7» не доказаны измерениями.** Ограниченный объём свипов
   детектора, ограниченная память обработанных идентификаторов, клиентские
   лимиты, runtime-политики с повторным включением после рестарта и незавершённая
   длительная приёмка — пока нельзя утверждать отсутствие пропусков при очереди,
   переподключении USB или рестарте. Нужны: время полного обзора, задержка
   обнаружения, минимальная длительность уверенно обнаруживаемого события,
   пропуски/дубликаты, восстановление, рост RAM/очередей/архива.
3. **`iq.py` — планировщик, а не анализатор.** Модуль рассчитывает достаточность
   частоты дискретизации и памяти (`M = F_d·L`, доступную длительность записи),
   но не захватывает IQ и не декодирует стандарты; часть величин каталога
   требований — оценочные. DTest заявляет собственно обработку и демодуляцию —
   это другой уровень. Формулировку «декодеры закрыты и не воспроизводимы» стоит
   смягчить до «нужных декодеров в проекте нет».
4. **Расчётная методика ≠ метрологическая готовность.** Проект не аттестованное
   СИ, не проверяет погрешность тракта и не загружает приборные калибровки
   автоматически (`docs/limits.md`). Это честная граница, но не паритет.

## 6. Приоритеты (по убыванию)

| Приоритет | Работа | Критерий готовности |
|---|---|---|
| P0 | Синхронизировать документы | один статус на функцию: расчёт / архивный анализ / runtime / аппаратно проверено |
| P0 | Приёмка tinySA + AR-DV1 | точный SHA, модели и прошивки, два потока, перестройка, отключение USB, восстановление |
| P0 | Длительный прогон | сначала 8 часов, затем отдельная проверка круглосуточного сценария |
| P1 | Сквозной детектор по эталону и маске | создание кандидата, фиксация контекста N1/N2, воспроизводимость по архиву |
| P1 | Сохранение политик | явная политика восстановления после рестарта, без неожиданного включения аппаратных действий |
| P1 | Реестр аппаратной совместимости | на модель: команды, ограничения, прошивка, журнал испытаний |
| P1 | Сквозной аудиотракт | источник → PCM → сеть → воспроизведение/фонограмма, с учётом потерь |
| P2 | Захват IQ и один цифровой сценарий | реальная запись/воспроизведение IQ, затем один проверяемый стандарт |
| P2 | Калибровки и измерительный тракт | происхождение коэффициентов, единицы, погрешность, настройки прибора в результате |

## 7. Итоговая оценка

OpenRadioInspector сейчас — развитая открытая платформа радиомониторинга с
существенным пересечением функций RT, но ещё не подтверждённый эксплуатационный
эквивалент. Для сценария «собственная система на Pi с tinySA/AR-DV1, удалёнными
клиентами, архивом и постепенной автоматизацией» основа убедительная; для
«готовая замена профессиональному комплексу с широким перечнем аппаратуры,
цифровыми декодерами и доказанной непрерывной работой» подтверждений недостаточно.
