# Адаптивный порог архивного свипа

Оператор явно рассчитывает порог для одного записанного `dBm` свипа.
Общее ядро возвращает локальную медиану, линию порога и области превышения;
Raspberry Pi WebUI, Windows Tk и macOS SwiftUI показывают один и тот же
результат. Это отдельный read-only анализ, не изменение политики
`automatic-detection`, реестра кандидатов или состояния приборов.

## Расчёт

Для точки с индексом `i` и нечётного окна `w` берутся исходные уровни с
индексами от `max(0, i - (w - 1) / 2)` до
`min(n - 1, i + (w - 1) / 2)` включительно. Центральная точка входит в окно.
На краях окно обрезается, значения не дополняются и не отражаются. Окно может
быть шире свипа. Медиана чётного обрезанного окна равна среднему двух средних
значений, с защитой от переполнения промежуточной суммы.

- `baseline_levels[i]` — медиана исходных `dBm` в окне.
- `threshold_levels[i] = baseline_levels[i] + margin_db`, единица `dBm`.
- `excess_levels[i] = sweep.levels[i] - threshold_levels[i]`, единица `dB`.
- Превышение отмечается только при `excess_levels[i] > 0`. Равенство порогу
  не считается превышением.

Область состоит из максимальной непрерывной последовательности индексов с
положительным превышением. Начальный и конечный индексы включены. Пик области
выбирается по максимальному превышению, при равенстве — первый индекс.

Пример: уровни `[-90, -90, -60, -90, -90] dBm`, окно 3, запас 6 dB.
Медиана во всех пяти точках равна −90 dBm, порог −84 dBm, превышение
`[-6, -6, 24, -6, -6] dB`. Единственная область — точка с индексом 2.

Окно задаётся в **точках**, не в герцах. Неравномерная сетка и повторяющиеся
частоты сохраняются; между соседними индексами не проверяется расстояние
по частоте. Границы областей являются координатами записанных точек, а не
оценкой занимаемой полосы или интерполированными границами сигнала.

## Ограничения интерпретации

Локальная медиана может следовать плавному фону, но не доказывает, что фон
является шумом. Широкий сигнал, занимающий большую часть окна, поднимает
медиану и может исчезнуть из областей превышения. На краях число точек в
оценке меньше. Запас 6 dB и окно 21 — начальные настройки интерфейса, а не
нормативные или калиброванные значения.

Алгоритм не оценивает вероятность ложной тревоги, не реализует CFAR, не
усредняет несколько свипов и не ищет изменения во времени. Он не переводит
`s_meter_count` в `dBm`. Результат не подтверждает наличие помехи, тип сигнала
или соответствие нормативам. Аппаратная и метрологическая валидация остаются
отдельными проверками.

## HTTP API

```text
GET /api/v1/sessions/{session_id}/sweep-threshold?sweep_id=...&window_points=21&margin_db=6
```

Все три query-параметра обязательны ровно один раз. ID сеанса кодируется как
один сегмент URL, ID свипа — как query value. Сервер не выбирает «последний»
свип: клиент фиксирует его ID при нажатии кнопки.

- `window_points`: нечётное целое от 3 до 101.
- `margin_db`: конечное число от 0 до 120 включительно.
- Источник: от 3 до 16 384 точек, исходные `dBm`, непустые известные записанные
  настройки. Проверка настроек совпадает с [сравнением свипов](sweep-comparison.md):
  `sequence` не является настройкой измерения, `null` в остальных полях
  означает неизвестное значение и отклоняется.

Обычная оболочка `api_payload`, `contract_version: 1`; объект `data`:

```json
{
  "session_id": "session-1",
  "stream_id": "spectrum-1",
  "sweep": {
    "id": "sweep-1",
    "interval": {"started_at": "2026-11-08T00:00:00Z", "ended_at": "2026-11-08T00:00:01Z"},
    "levels": [-90, -90, -60, -90, -90],
    "level_unit": "dBm",
    "settings": {"rbw_hz": 10000}
  },
  "frequencies_hz": [100000000, 101000000, 102000000, 103000000, 104000000],
  "parameters": {
    "method": "rolling_median", "window_points": 3, "margin_db": 6,
    "edge_policy": "clip", "comparison": "strictly_greater"
  },
  "baseline_levels": [-90, -90, -90, -90, -90],
  "threshold_levels": [-84, -84, -84, -84, -84],
  "level_unit": "dBm",
  "excess_levels": [-6, -6, 24, -6, -6],
  "delta_unit": "dB",
  "regions": [{
    "start_index": 2, "end_index": 2,
    "start_frequency_hz": 102000000, "end_frequency_hz": 102000000,
    "peak_index": 2, "peak_frequency_hz": 102000000,
    "peak_excess_db": 24, "points": 1
  }],
  "points": 5,
  "exceedance_points": 1,
  "region_count": 1
}
```

- `400 invalid_request`: отсутствующий, повторный, пустой или неизвестный
  query-параметр, неверное число или значение вне допустимого диапазона.
- `404 session_not_found` / `sweep_not_found`: отсутствующий сеанс или свип;
  запись другого сеанса не раскрывается.
- `409 threshold_incompatible`: единица, число точек, неизвестные настройки
  или неконечный производный результат не позволяют выполнить анализ.

`features.adaptive_sweep_threshold` сообщает поддержку. У старого сервера
`404` показывается только в этой панели. Успехом считается HTTP 200.

## Три клиента и жизненный цикл

1. Выберите сеанс и спектральный поток с записанным `dBm` свипом.
2. Задайте размер окна и запас, явно запустите анализ последнего доступного
   свипа выбранного потока.
3. Сверьте ID, UTC-интервал и параметры рассчитанного результата. Линии
   исходного уровня и порога имеют единицу `dBm`, превышение — `dB`.
4. Повторный расчёт для нового свипа или других параметров запускается по
   кнопке. Новые polling/SSE снимки сами анализ не выполняют.

Результат относится к зафиксированному свипу, а не автоматически к новому
live-кадру. Смена сервера, сеанса или потока, отключение и закрытие отменяют
ожидание или обесценивают ответ. Одновременно выполняется один запрос.
Ожидание ограничено восемью секундами в WebUI/Windows и шестью в macOS.
Windows не может прервать уже выполняющийся `urllib` транспорт: поздний
результат отбрасывается, следующая попытка доступна после его завершения.

WebUI и Windows выводят в списке первые 200 областей с явным указанием
общего числа. macOS использует прокручиваемый список с ленивым созданием
строк. Графики во всех клиентах содержат все точки принятого ответа.

Основные спектры, водопад, сравнение и именованный каталог остаются отдельными
сценариями. Анализ не создаёт кандидатов, исследований, задач или команд
прибору и не включает автоматическое обнаружение.

## Архив и производительность

SQLite получает одну запись по точному ID, в том числе вне окна последних
свипов. В memory-режиме поиск идёт по уже имеющимся данным. Обрабатываются все
точки или запрос отвергается целиком. Окно ограничено 101 точкой, свип —
16 384 точками. Расчёт не сканирует весь архив и не загружает соседние свипы.

Новая схема, миграция, таблица или записанное событие не требуются. Версия
SQLite остаётся 3, введённой [каталогом эталонов](named-sweep-references.md).
Успех и отказ не меняют исходные измерения, каталог, курсор событий и лимит
приёма. Анализ доступен и при заполненном архиве. Наследуемая миграция 2 → 3
при запуске ядра остаётся отдельным эффектом базового PR #70: новая функция
не отменяет требование резервной копии перед обновлением старого архива.

Результат существует только в ответе и в окне клиента; экспорта и сохранения
производной линии нет. Большие записанные метаданные или множество областей
могут превысить лимит HTTP клиента даже при допустимом числе точек. Например,
16 384 чередующихся точек на частотах около 1 ТГц дают 8 192 области и ответ
около 2,41 МБ, что больше предела ответа 2 000 000 байт. Клиент отказывает
целиком, не показывает усечённый анализ. Сервер не обрезает ни точки, ни области.

## Воспроизводимая проверка

```bash
python -m unittest tests.test_sweep_threshold
python -m unittest discover -s tests -t .
swift test --package-path macos/SpektrKomandy
swift test --package-path macos
xcodebuild -project macos/DvoynoyObzor.xcodeproj -scheme DvoynoyObzor \
  -configuration Debug -destination 'platform=macOS' \
  -derivedDataPath macos/DerivedData CODE_SIGNING_ALLOWED=NO build
```

Все тестовые архивы синтетические и временные. Реальные пользовательские
архивы, порты приборов и режим генератора не используются.

Итоговый прогон 8 ноября 2026: 520 Python/Node-тестов, 88 Swift API-тестов
и 39 native-тестов прошли; Xcode собрал приложение без подписи. Swift API
включал дополнительный живой тест с явно заданным
`ORI_THRESHOLD_SMOKE_BASE_URL` временного синтетического сервера; без этой
переменной только этот необязательный smoke-тест пропускается.

Реальные HTTP-запросы WebUI-модуля, Windows/Tk и Swift DTO проверены на
синтетическом наклонном фоне из 101 точки: две области (индекс 30 и индексы
69–71), четыре превышения. Полный логический dump временного SQLite до и
после проверок совпал по SHA-256, включая каталог именованных эталонов.
Независимая сверка 300 случайных примеров подтвердила медианы, непрерывные
области и выбор первого пика при равенстве. Независимое ревью завершено без
оставшихся блокирующих замечаний.

Визуальный осмотр WebUI/SwiftUI недоступен из-за блокировки Mac. Проверка
Tk выполнена на macOS, не на Windows OS. Проверка на приборах и
метрологическая валидация не выполнялись.
