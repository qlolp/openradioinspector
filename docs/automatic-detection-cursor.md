# Очередь автоматического обнаружения

Детектор читает новые sweeps по внутреннему номеру приёма, а не по времени измерения. Один проход получает не более 1000 записей после курсора в возрастающем порядке. Полная страница планирует следующий проход без обычной задержки; отдельные сеансы сохраняют независимые исполнители. Фильтр потока применяется до лимита. Поздние и задним числом датированные sweeps не теряются; чужой поток не вытесняет выбранный из окна последних измерений.

## Архив и совместимость

Schema 6 добавляет `sweep_ingestion`: монотонный номер, точные ID sweep, сеанса и потока. Составной внешний ключ предотвращает рассогласование владельца. Исходный sweep, запись журнала и производный monitoring_sweep_index сохраняются одной транзакцией, в том числе для пакетов и записи без события. Откат вместимости или ошибка любой из этих вставок либо события откатывает все изменения. Пропуски номеров допустимы.

При переходе со старой схемы существующие строки получают номера в детерминированном порядке ID. Это не восстановление неизвестного исторического порядка приёма. Исходные измерения, единицы и временные метки сохраняются. Все прежние записи предшествуют границе нового opt-in. Миграция и номер версии транзакционны; повторное открытие не перенумеровывает журнал. Memory-only режим хранит индексы приёма независимо от ограниченного журнала событий. SQLite не загружает этот журнал целиком в память; детектор хранит один числовой курсор на сеанс. Текущий детектор мониторингового проекта сохраняет собственный независимый rowid-курсор; legacy-детектор его не сдвигает. Чтение и аналитические запросы не создают записи журнала.

Публичная сортировка `list_sweeps` по UTC/ID, HTTP-контракт и данные трёх клиентов не меняются. Параметр конструктора `history_limit` детектора принимается и валидируется для совместимости; он больше не ограничивает историю обработки.

## Политика и жизненный цикл

Включение и повторное включение фиксирует текущий конец журнала приёма под блокировкой службы. Старый архив не анализируется. После restart политика выключена, курсор не восстанавливается. Изменение порога не перематывает обработку.

Курсор общий для сеанса. Смена `stream_id` применяет новый фильтр после последнего подтверждённого номера, без сброса. Если прежний выбранный поток не дал новых записей, курсор не сдвинулся: переключение может сделать доступными записи другого потока, принятые после включения. Записи до границы opt-in и уже пройденные номера не воспроизводятся.

Применение настройки и обработка сериализуются отдельно для каждого сеанса. Валидация PATCH выполняется до этой блокировки; затем только переданные поля сливаются с актуальной политикой. Поэтому задержанная проверка параметра не блокирует выключение и не возвращает старое значение enabled. Глобальная блокировка детектора не удерживается при чтении архива или ожидании прохода. Выключение ждёт допущенный проход, затем запрещает новые. `close()` сохраняет ограниченное ожидание фоновых потоков: это не отмена уже допущенного прохода или зависшего внешнего вызова.

## Ошибка и повтор

Каждый успешно обработанный либо намеренно исключённый sweep подтверждается отдельно. Ошибка оставляет проблемную запись для повтора, не откатывая предыдущие подтверждения. Защищённые состояния кандидатов и cooldown сохраняют прежнюю дедупликацию.

Гарантии exactly-once нет. Создание кандидата, обновление cooldown и событие `automatic_detection.candidate_created` не образуют общей транзакции. Ошибка публикации после создания оставляет кандидата без этого события; повтор может подавиться защищённым состоянием, но событие не восстанавливает. Если состояние изменилось и cooldown истёк до повтора, отсутствие дубликата не гарантировано. Счётчики неуспешного прохода могут не учитывать уже выполненную часть. Это ограничения существующего создания кандидатов, не устранённые курсором.

## Проверка

`python -m unittest tests.test_detection_cursor tests.test_automatic_detection tests.test_persistence tests.test_listening_duration` проверяет синтетические memory-only/SQLite сценарии. Реальные архивы и оборудование не используются. Аппаратная приёмка не заявляется.

## Последовательность версий и обновление

База `aa23f1a` использует schema 4 с `measurement_results` и `sweep_references`.
Коммит `dc0a278` добавляет `listening_started_at` как schema 5; этот срез
добавляет журнал приёма как schema 6. Прямой переход 4→6 и последовательный
4→5→6 сохраняют результаты, эталоны, индексы и исходные данные. Ошибка любой
стадии прямого перехода откатывает обе добавки и версию; ошибка 5→6 сохраняет
timestamp прослушивания. Проверки используют собственные синтетические архивы
и фиксированные SQL-проекции.

При интеграции с текущим архивом независимая вспомогательная схема мониторинга остаётся версии 4. Миграции сохраняют проекты, версии эталонов, события, очередь уведомлений с попытками/арендой, webhook-настройки, связи сеансов, производные индексы и байты инструментальных аудиоартефактов. Общий декодер исследований сохраняет listening_started_at в чтении по ID, истории и восстановлении; последующее состояние interrupted/failed не стирает эту отметку. Проверены rollback после обеих стадий прямого обновления и отдельный rollback 5→6, повторное открытие и точность микросекунд. Синтетические SQLite-соединения в проверках закрываются явно до очистки временного каталога на Windows.

Перед реальным обновлением следует сохранить отдельную проверенную резервную
копию архива. Ядра с максимальной поддерживаемой версией ниже 6 не открывают
обновлённый архив; автоматическое понижение версии не реализовано. Для возврата
к прежнему ядру нужна совместимая резервная копия: изменения, записанные после
её создания, в ней отсутствуют. Не следует вручную менять `user_version` для
обхода проверки. Реальные архивы при разработке этой правки не открывались.
