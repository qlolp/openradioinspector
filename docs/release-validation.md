# Воспроизводимая проверка релиза без приборов

Runner объединяет проверку общего ядра, Raspberry Pi WebUI, Windows Tk и
macOS SwiftUI в одном изолированном запуске. Он не запускает рабочий сеанс,
не ищет подключённые приборы и не принимает путь к пользовательскому архиву.

## Подготовка

Из корня checkout установите Python 3.12, зависимости проекта и Node 24.
Для Tk нужен доступный desktop; Linux CI использует Xvfb.

```sh
python -m pip install '.[serial,test]'
python -m tests.run_release_checks --report-dir release-reports
```

На macOS с Xcode:

```sh
python -m tests.run_release_checks --swift --report-dir release-reports
```

С `--swift` дополнительно выполняются оба Swift package test suites и
unsigned Xcode build. Приложение не запускается. Runner рассчитан на исходный
checkout, а не на установленный wheel без каталога tests.

Отсутствующие Node, NumPy, pySerial или Tk являются ошибкой подготовки,
а не основанием для зелёного прогона с пропусками. Это не установка драйверов,
службы, GUI-пакета или аппаратная приёмка.

## Собственные fixtures и жизненный цикл

Runner поднимает семь HTTP fixtures: адаптивный порог, маску, усреднение,
обнаружение изменений, три порога, архивное окно и округление частоты.
Каждый использует отдельный временный SQLite и свободный порт loopback.
Дочерние Python/Tk процессы получают собственные TMPDIR/TMP/TEMP и пустой
HOME, чтобы не загружать пользовательские Tk-профили или старые временные
TaskBook. В окружение тестов передаются фактически выделенные URL, поэтому
вручную запускать серверы или назначать фиксированные порты не требуется.

Каждый fixture печатает SHA-256 полного логического dump до чтения и после
закрытия всех сервисов. Успех требует реального совпадения, успешного
завершения процессов и очистки собственных ресурсов. Проверка не ограничена
числом строк или размером файла.

Остановка передаётся только через закрытие приватного stdin pipe дочернего
процесса. Публичного HTTP shutdown endpoint нет. Runner следит только за
созданными им процессами, не ищет и не завершает чужие серверы. При ошибке,
тайм-ауте или прерывании он выполняет cleanup; принудительное завершение
собственного зависшего процесса не считается доказательством неизменности
архива. Контроль охватывает собственные группы процессов/Windows jobs и
явно зарегистрированные вложенные Python helpers. HTTP-fixture Swift имеет
отдельную stdin lifeline. Это не общий надзор за любыми detached-процессами
или системными build services Xcode; чужие службы не завершаются.

Отдельные fixture-модули сохраняют ручной запуск и Ctrl-C. Параметры
`--port 0 --shutdown-stdin` предназначены для автоматического владельца
процесса. stdin EOF не заменяет подтверждение результата в финальном JSON.

## Пропуски и CI

Workflow в `.github/workflows/windows-core.yml` проверяет точный head PR,
а не неявный результат объединения веток. Он использует закреплённые SHA
официальных actions, read-only repository permissions и не сохраняет Git
credentials. Матрица включает Linux, Windows и macOS.

На POSIX ожидается полный Python/Node/Tk набор без пропусков. На Windows
допустимы только явно перечисленные тесты POSIX PTY и permission bits.
Пропущенный live HTTP/Tk сценарий или отсутствующая зависимость приводят к
ошибке проверки. На macOS также проверяется отсутствие пропусков Swift.

Полный успешный CI подтверждает синтетические программные сценарии конкретного
коммита. Он не доказывает работу native COM/USB, реального tinySA/AR-DV1,
отключения питания, калибровки, метрологическую точность или пригодность к
длительной автономной записи. Внешний вид и системные диалоги требуют отдельной
ручной проверки. macOS CI не означает проверку на Raspberry Pi ARM.

## Hosted macOS: обратный DNS loopback

Первый CI 42482443812 прошёл на Linux (1026/0 skips) и Windows
(1026, 21 POSIX skips), но hosted macOS не дождался первого fixture.
Стандартный HTTPServer вызывает getfqdn перед ready. Известная
[проблема hosted macOS 15/26](https://github.com/actions/setup-python/issues/1223)
может задерживать этот обратный lookup более чем на 30 секунд.

Синтетические fixtures и отдельный процесс unittest теперь используют
scoped helper только для точных numeric loopback `127.0.0.1` и `::1`.
Остальные имена, включая `localhost`, передаются исходному resolver вместе
с его ошибками. Вложенные контексты и исключения восстанавливают resolver.
Собственный Swift HTTP fixture задаёт информационное имя после numeric bind
без обратного DNS. Производственные DNS/bind, deadlines и assertions
не изменены. Успех новой hosted macOS проверки должен подтверждаться CI,
а не выводиться только из совпадения с внешним issue.


## Повторный CI и диагностика зависаний

[CI 42483687163](https://github.com/qlolp/openradioinspector/actions/runs/42483687163)
на `1107381` прошёл Linux (1031 тест, без пропусков) и Windows
(1031 тест: 1010 прошли, 21 допустимый POSIX skip). Hosted macOS успешно
поднял все семь fixtures, затем достиг 600-секундного ограничения Python
набора. Последним начатым был
`AverageActualTkHTTPTests.test_hidden_live_detection_regions_and_parameter_traces`.
Все семь серверов штатно остановились, полные логические SHA-256 совпали.

Лог содержал 39 сообщений `_drain_messages` и 23 `_poll` после уничтожения
Tk-окон. Это подтверждённый отдельный дефект владения таймерами; его
причинная связь с зависанием ещё не установлена. Буферизованный лог без
стека не позволяет отличить заблокированный `root.update()` от другой
операции или накопленной задержки. Следующая проверка добавляет диагностику
точного теста, времени выполнения, версий Python/Tcl/Tk и стеков потоков.
Периодический faulthandler dump — только диагностический снимок, не отдельный
провал теста; окончательный результат по-прежнему определяется assertions,
кодом выхода, проверкой пропусков и общим deadline.
Тайм-ауты, assertions и правила пропусков не ослабляются, фоновые Tcl-ошибки
не подавляются. До успешного полного hosted macOS прогона CI остаётся
незавершённой проверкой, а не зелёным релизным критерием.

## Совместимость watchdog с CPython

В CI `ec755e7` минимальный watchdog-процесс на Windows/Python3.12.10
завершился с access violation0xC0000005; GUI и приборы в нём не создавались.
В CPython зарегистрирован [gh-140815](https://github.com/python/cpython/issues/140815):
нативный поток `dump_traceback_later` может читать освобождённый Python frame.
Исправления вошли в3.13.10/3.14.1; для3.12 backport отсутствует. Это подходящее
объяснение класса сбоя, но без native dump конкретный стек не установлен.

На более старых версиях runner использует периодический Python-поток,
вызывающий `faulthandler.dump_traceback` с GIL; при завершении/ошибке потока
выполняется отмена и join. Если native код навсегда удерживает GIL, этот
вариант не сможет снять стек; внешний timeout собственного процесса
продолжает действовать. На исправленных версиях сохраняется независимый
от GIL C-watchdog. Тесты продукта, тайм-ауты приборов и критерии успеха
не ослабляются; регрессия проверяет реальный dump и отсутствие dump после отмены.

Hosted Tk8.6.12 дополнительно обнаружил `event ... application has been destroyed`
в новой lifecycle-фикстуре. Теперь она выполняет idle-инициализацию ttk до
сценария закрытия, сохраняя pending application timers; все ошибки bgerror
по-прежнему запрещены и сопровождаются Tcl errorInfo. Итоговый CI проверяет
эту адаптацию; пропуск теста или фильтрация сообщения не используются.


## Строгий результат изолированного Tk-теста в release-ветке

База follow-up: PR #96, `69f84cd69efc16d17eebbbf37f532d9cbe74f4ef`.
Она уже содержит точные commits PR #99 и #100. Их production изменения
не копируются повторно; новый delta ограничен runner, harness-регрессиями
и двумя проверками сочетания session/context guards с lifecycle.

Runner сохраняет шесть точных Windows skip IDs release-базы, пять классов
изолируемых actual-Tk случаев, Linux live-member/zombie checks, process
registry/groups/Windows Jobs, fixture ownership и общий deadline 600 секунд.
Намеренные lifecycle → worker GC → HTTP и повторные root остаются связными
проверками, а не разделяются на новые изолированные случаи.

Из PR #102 (`9595b6c`) перенесено строгое сопоставление запрошенного test ID,
целого count=1, отчёта, success и exit status. Неожиданный skip отклоняется
даже при ошибочно указанном нулевом exit. Missing/malformed report, timeout
и nonzero exit не превращаются в pass. Вывод ребёнка и 30-секундный watchdog
сразу сохраняются в общем журнале; case ограничен 90 секундами.
Вложенная структура suites и исходные ID сохраняются.

Реальный timeout-регресс отделяет до 20 секунд запуска до ready marker от
фактического 0,3-секундного timeout. Проверяются stdout/stderr, watchdog stack
и завершение только собственных потомков. Стабилизированный watchdog-тест
release-базы, реальные positive child и unknown-case проверки сохранены.
Две integration-регрессии проверяют смену сеанса, устаревшую форму/ответ,
переподключение, guards политики/потока и закрытие.

Предшествующее дерево на базе `ec755e7` прошло полный локальный source gate:
1157 Python, 168 macOS SDK, 108 SwiftUI тестов и unsigned Xcode build;
семь fixture cleanup подтверждены, skips отсутствуют. SHA256 журнала:
`6ddabc58074018b879a55e514409a472ea6f37a877af1615e59970a317f660dc`.
Это предварительный результат; итоговый gate нового дерева на `69f84cd` указан ниже.
После добавления Windows observability focused-проверка дерева: 56 harness и

## Диагностика неожиданного Windows exit

В [Windows job 128799138693](https://github.com/qlolp/openradioinspector/actions/runs/42502852975/job/128799138693)
на `3f3b15d` Python suite неожиданно завершился около второго периодического
дампа, без unittest failure summary. Supervisor сообщил `4294967295`.
Это не установленная причина падения: прежний Windows job на `6d678ee`
прошёл два полных дампа и все 1087 случаев за 172.033 секунды при тех же
версиях Python, NumPy, pySerial и runner image. Последний начатый тест
не является доказанным источником ошибки.

Windows supervisor теперь пишет исходный DWORD дочернего процесса в stderr
как decimal и восьмизначный hex, затем передаёт в `sys.exit` эквивалентное
signed32 значение. Это сохраняет биты native exit code: CPython 3.12
преобразует SystemExit через signed C long, поэтому прежняя передача
unsigned значений выше `0x7FFFFFFF` могла скрывать исходный код за `-1`.
Диагностический Python child также включает fatal faulthandler reporting.
Интервал периодических дампов, ownership, сроки и fail-closed проверки
не изменены. Это исправление наблюдаемости, а не исправление причины crash.

Pure regressions проверяют границы DWORD, точный журнал, signed32 mapping
и запрет запуска до приватного `go` handshake. В существующем bounded
owned-process тесте только на Windows добавлены synthetic `ExitProcess`
подслучаи: они завершают исключительно собственный child, не вызывают
реальный access violation и не расширяют skip allowlist. На других ОС
проверяется pure mapping, но Windows propagation требует Windows run.
Успешный повтор сам по себе не объясняет прежнее падение.

Существующая [watchdog policy](#совместимость-watchdog-с-cpython) базы
`69f84cd69efc16d17eebbbf37f532d9cbe74f4ef` сохранена без повторного переноса.
Это mitigation известного CPython дефекта, а не установленная атрибуция
Windows crash. Новые boundary × outcome проверки подтверждают выбор policy,
передачу `only_test`, fatal enable и cleanup при успехе, ненулевом результате,
исключении и прерывании. Отдельно проверены повторные дампы, ошибка дампа,
bounded join, настоящий Python thread и ошибка close, которая не может
превратить suite в успех. Существующий readiness-gated outer-timeout child
и стабилизированная проверка реального дампа/отмены сохранены.

Ruff fatal checks (`E9,F63,F7,F82`) пройдены. Полная существующая конфигурация
Ruff содержит прежние замечания в этих файлах; новых замечаний delta не добавляет.

## Сохраняемые отчёты и уровни проверки

--report-dir PATH сохраняет новый подкаталог run-* после cleanup даже при
ошибке подготовки, тестов или прерывании с выполненным cleanup. В нём
summary.json с исходной ошибкой/ошибками очистки, python-results.json
(если suite запускался) с причинами skips и журналы собственных процессов.
SQLite fixtures, их HOME и build-каталоги не копируются. Старые запуски
не перезаписываются. Ошибка сохранения отчёта делает gate неуспешным.
CI выгружает отчёты через always(), со сроком хранения 14 дней.

Быстрый unittest discovery и ./run_tests.sh могут пропускать opt-in
сценарии и не заменяют этот gate. На Windows дополнительно разрешены
ровно две конкретные проверки POSIX shell launcher с причиной
POSIX shell launcher; причина сама по себе не разрешает другие skips.
Исправления аудита, команды подготовки и отдельный протокол аппаратной
приёмки: [надёжность по аудиту](audit-reliability.md). Синтетический
результат никогда не маркирует hardware_validation как passed.
