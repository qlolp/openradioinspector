# Архивное окно сканирований N1/N2

Общее ядро возвращает ближайшие архивные свипы до и после выбранного точного
ID. Raspberry Pi WebUI, Windows Tk и macOS SwiftUI позволяют выбрать опорный
свип, задать число соседей и просмотреть исходный спектр каждой записи.
Запрос read-only: измерения, события, кандидаты и команды приборам не создаются.

Это первый срез четвёртого пункта функционального бэклога: воспроизводимый
просмотр контекста. N1 означает число предыдущих записей, N2 число следующих.
Автоматический захват при обнаружении, ожидание будущих сканов, сохранённые
наборы и привязка к кандидату не реализованы. В существующем Candidate нет
точного source_sweep_id, поэтому связь не угадывается по времени или частоте.

## Порядок и полнота

1. Ядро находит точный anchor в выбранном сеансе независимо от окна последних
   свипов и истории событий.
2. Среди записей того же сеанса и потока выбирает ближайшие N1 предыдущих и
   N2 следующих по паре (started_at UTC, ID). При равном времени ID сравнивается
   как точная последовательность UTF-8, без локализации или нормализации.
3. Результат отсортирован по той же паре. Отрицательные offset соответствуют
   предыдущим записям, 0 опорной, положительные следующим. ID уникальны.
4. Если соседей не хватает, возвращаются имеющиеся записи и отдельные missing
   для каждой стороны. complete означает только наличие запрошенного числа
   записей, а не полноту наблюдения эфира.

Интервалы могут перекрываться; «до/после» описывает положение в этом порядке,
не гарантию окончания предыдущего измерения до начала следующего. Повторный
запрос может дать другое окно после позднего импорта. Это снимок существующего
архива, не ожидание будущих N2 и не число аппаратных сканирований между ID.
Поле available считает возвращённых соседей, а не весь архив.

SQLite выбирает ограниченное число строк с LIMIT для каждой стороны в одном
read snapshot. Полный архив не загружается в память. Из-за нормализации времени
запрос может просматривать/сортировать строки потока в SQLite: постоянное время
или индексированный seek не обещаются. Нового индекса и миграции нет.

## Совместимость и ограничения

Сначала выбираются фактические ближайшие соседи, затем проверяется всё окно.
Несовместимый сосед не пропускается ради более далёкого подходящего свипа.
Все записи должны быть dBm, с одинаковой исходной сеткой и известными
непустыми записанными настройками. Только верхний settings.sequence не
участвует в сравнении настроек; он сохраняется в ответе. Boolean не равен
числу. Неизвестные настройки не восстанавливаются из профиля устройства.

- N1 и N2: целые JSON числа от 0 до 16; bool, строки и дроби недопустимы.
- От 1 до 33 записей, включая anchor. Нули с обеих сторон допустимы.
- От 1 до 16 384 точек на запись, максимум 131 072 точки на всё окно.
- Целые частоты 0…9 007 199 254 740 991 Hz, неубывающая сетка; повторяющиеся
  частоты сохраняются. Уровни конечные double. Уровни не усредняются.
- При превышении лимита точек или несовместимости весь запрос отклоняется
  с 409. Усечения, интерполяции, конвертации S-метра и частичного окна нет.

Настройки подтверждают только записанное происхождение. Их совпадение не
доказывает равенства антенны, калибровки и незаписанного состояния прибора.

## HTTP API

```text
POST /api/v1/sessions/{session_id}/sweep-context
```

```json
{"sweep_id":"one-sweep-4","before":2,"after":2}
```

Разрешены ровно три поля. sweep_id непустой, до 128 Unicode code points,
валидный UTF-8; содержимое не нормализуется. Нет URL-параметров, в том числе
пустого ?. Один десятичный Content-Length, без Transfer-Encoding. Повторные
JSON-ключи, некорректный UTF-8 и незавершённое тело отклоняются. Предел тела
8192 байта проверяется до чтения. Существующие API сохраняются.

Обычная оболочка contract / contract_version / data. Поля data:

- session_id, stream_id, anchor_id;
- order: started_at_then_id;
- requested, available, missing: объекты с before и after;
- complete: true, только если missing.before и missing.after равны нулю;
- frequencies_hz: общая исходная сетка; level_unit: dBm;
- points: число точек одной записи;
- items: записи с offset, id, interval (started_at/ended_at UTC), levels,
  level_unit: dBm и полными settings, включая sequence.

items содержит ровно available.before + 1 + available.after записей.
Offset идут подряд от -available.before до available.after, единственный 0
указывает на anchor_id. Каждый массив levels имеет points элементов.

Ошибки:

- 400 invalid_request: поля, типы, пределы счётчиков, ID, URL или framing;
- 404 session_not_found / sweep_not_found: сеанс или точный ID отсутствует
  в выбранном сеансе; чужая запись не раскрывается;
- 409 context_incompatible: несовместимый источник/сосед или лимит точек;
- 413 request_too_large: превышено 8192 байта HTTP-тела.

Capability features.sweep_context сообщает поддержку. Запрос POST только
передаёт параметры чтения и ничего не сохраняет. Он работает и при заполненном
архиве, не создаёт событий и не меняет SQLite schema v3. Предыдущая миграция
v2→v3 для именованных эталонов сохраняет свои требования резервного копирования.

## Три клиента

1. Выберите сеанс и поток dBm. В отдельной панели выберите опорный свип из
   текущего полученного списка, в том числе не последний.
2. Задайте N1/N2. Начальные 2/2 являются примером, не автоматической политикой.
3. Явно загрузите окно. Клиент фиксирует ID, UTC, настройки, исходные уровни
   и сетку anchor вместе со счётчиками.
4. Проверьте запрошенные, доступные и недостающие количества. Выберите строку
   контекста, чтобы увидеть её полный исходный спектр, UTC и настройки.

Обновление списка меняет только доступные варианты для следующего запроса,
не сохранённый ответ. Редактирование счётчиков, смена anchor, очистка,
смена сервера/сеанса/потока, отключение и закрытие отменяют или обесценивают
ожидающий ответ. Автоматических повторов и фоновой загрузки N2 нет.

В клиентах один запрос за раз. Тайм-аут WebUI/Windows 8 секунд, macOS 6 секунд;
Windows urllib нельзя принудительно прервать посреди чтения, поэтому поздний
ответ игнорируется. Все HTTP-ответы ограничены 2 000 000 байтами до декодирования,
принимается только статус 200. Слишком большой ответ отклоняется целиком:
предел ядра по точкам не гарантирует прохождение байтового предела клиента,
особенно при длинных метаданных. В таком случае уменьшите N1/N2.

Выбранный полный anchor остаётся доступен для явной повторной загрузки, даже
если ушёл из текущей страницы списка. Правка N1/N2 и очистка результата
не заменяют этот источник; смена области или отключение сбрасывают его.
Это позволяет вручную повторить запрос после прихода следующих свипов.

Клиенты проверяют область запроса, порядок, счётчики, уникальность, совместимость
настроек, интервалы UTC с точностью до микросекунды и совпадение полного anchor
с зафиксированным источником. ID сравниваются точно. Swift дополнительно
отклоняет повторные или канонически совпадающие ключи сырого JSON, потому что
Dictionary не может сохранить оба таких ключа без потери данных.

## Воспроизводимая синтетическая проверка

```sh
python -m tests.sweep_context_smoke_server --port 56039
```

Сервер создаёт собственный TemporaryDirectory и SQLite, не принимает путь к
пользовательскому архиву. Сеансы context-one/context-two, спектральные потоки
spectrum-one/spectrum-two, отдельные S-meter наблюдения и именованный эталон.
Свипы one-sweep-1…7 вставлены не по времени (7, 2, 5, 1, 6, 3, 4).

Для one-sweep-4, before=2, after=2 ответ содержит one-sweep-2…6 с offset
-2, -1, 0, 1, 2; complete=true. Для before=16, after=16 доступны по три,
недостают по 13; complete=false. В каждой записи 101 точка 100…110 MHz,
шаг 100 kHz, levels[i] = -100 + i/10 + номер свипа. Первый уровень anchor
-96 dBm. Начало UTC 2026-11-08T12:00:40.000001Z, окончание
2026-11-08T12:00:41.000002Z.

При остановке Ctrl-C сравнивается полный логический dump SQLite до/после.
Проверки оборудования, Windows OS и визуальный осмотр SwiftUI/браузера
в этот срез не входят; автоматические тесты не заменяют их.

### Команды проверки

При работающем синтетическом сервере:

```sh
export ORI_CONTEXT_SMOKE_BASE_URL=http://127.0.0.1:56039
python -m unittest tests.test_sweep_context tests.test_webui_sweep_context tests.test_windows_sweep_context
swift test --package-path macos/SpektrKomandy --filter SweepContextTests
swift test --package-path macos --filter SweepContextModelTests
```

Node должен быть в PATH для исполняемых WebUI-тестов. Для последнего Windows
теста нужен tkinter; он создаёт собственное скрытое окно и обращается только
к указанному синтетическому API. Он не доказывает работу на Windows OS.
Полный регрессионный прогон: `python -m unittest discover -s tests -t .`,
`swift test --package-path macos/SpektrKomandy`, `swift test --package-path macos`.
Опциональные HTTP-проверки прежних срезов включаются их переменными окружения
и серверами, описанными в соответствующих документах.

Финальный прогон этого среза: 729 Python/Node, 138 Swift API и 87 native-тестов,
без пропусков, плюс unsigned Xcode build. Пять синтетических API включены;
после остановки все пять временных SQLite сохранили идентичный логический dump.
Независимые 500 случайных окон дополнительно совпали с эталонной сортировкой
в памяти и SQLite. Ревью без оставшихся замечаний; найденный сценарий сохранения
старого anchor при обрыве Windows-связи исправлен и проверен повторным полным
прогоном. Это результаты программных проверок, не аппаратная аттестация.
