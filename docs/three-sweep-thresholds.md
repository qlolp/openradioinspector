# Три горизонтальные линии порога

Один архивный dBm свип можно явно проверить по трём независимым горизонтальным
линиям одновременно. Расчёт выполняет общее ядро; Raspberry Pi WebUI, Windows
Tk и macOS SwiftUI показывают исходную трассу, все три порога и отдельные
области превышения каждой линии. Нет записи в архив, команд приборам или
изменения действующих автоматических политик.

Это срез трёх **горизонтальных** линий. Табличная маска и локальный адаптивный
порог сохраняют свои отдельные панели. Смешивание трёх масок/адаптивных линий,
постоянный каталог конфигураций и автоматическое применение сюда не входят.

## Метод и единицы

Для каждой линии и каждого индекса:

```text
excess_levels[i] = sweep.levels[i] - level_dbm
превышение ⇔ excess_levels[i] > 0
```

Уровень линии и исходные измерения выражены в dBm, превышение со знаком в dB.
Равенство не считается превышением. Допустимы любой порядок уровней и
совпадающие уровни. Ядро не сортирует их: первый параметр всегда line-1,
второй line-2, третий line-3. Это идентичность линии, не степень опасности.

У каждой линии собственные максимальные непрерывные по **индексам** области
положительного превышения. Границы включительны, пик при равных превышениях
выбирается первым. Разрыв между соседними частотами не разделяет область;
её ширина в герцах не выдаётся за занимаемую полосу сигнала. Повторяющиеся
частоты сохраняются. Одна точка может превысить сразу несколько линий, поэтому
их счётчики нельзя складывать как число разных сигналов. Общего OR-детектора
или автоматических кандидатов нет.

Пример: исходные уровни −90 и −70 dBm при порогах [−90, −80, −70] дают
соответственно [0, 20], [−10, 10] и [−20, 0] dB. Первая и вторая линии
имеют по одной превышающей точке, третья не имеет превышений.

## Совместимость и границы

Источник должен принадлежать выбранному сеансу, иметь исходную единицу dBm,
известные непустые записанные настройки и 1–16 384 точки. Применяется общий
контроль совместимости архивного свипа; неизвестные настройки не выводятся
из профиля прибора. Верхний sequence может быть счётчиком, полные настройки
возвращаются без изменения.

Частоты целые, от 0 до 9 007 199 254 740 991 Hz, без интерполяции и усечения.
Три уровня должны быть конечными числами double. Булевы значения, строки,
null, NaN/Infinity и численные переполнения отклоняются. Если хотя бы для
одной линии разность выходит за конечный диапазон, весь анализ отклоняется,
а не выдаётся частичный результат. Перевода s_meter_count в dBm нет.

Уровни −90/−80/−70 в интерфейсе являются только примерами, а не нормативом
или рекомендацией для конкретного прибора. Это просмотр превышений,
не калибровка, не оценка помехи и не аттестованное измерение.

## HTTP API

```text
POST /api/v1/sessions/{session_id}/sweep-three-thresholds
```

```json
{"sweep_id":"source-1","levels_dbm":[-90,-80,-70]}
```

Разрешены ровно эти два поля. ID свипа — непустая строка до 128 Unicode code
points, без нормализации его содержимого; levels_dbm — массив ровно из трёх
чисел. Параметры URL, в том числе пустой ?, запрещены. Нужен один десятичный
Content-Length; Transfer-Encoding, повторные ключи JSON и некорректный UTF-8
отклоняются. Тело ограничено 8192 байтами до чтения. Старые API не изменяются.

Ответ в обычной оболочке contract / contract_version / data. Поля data:

- session_id, stream_id;
- sweep: id, interval с started_at/ended_at UTC, исходные levels, level_unit
  dBm и полные settings, включая sequence;
- frequencies_hz: исходная сетка всех точек;
- method: three_horizontal; comparison: strictly_greater;
- level_unit: dBm; delta_unit: dB; points;
- lines: ровно три объекта в порядке запроса.

Каждый объект lines содержит:

- id: line-1, line-2 или line-3;
- level_dbm: соответствующий переданный уровень;
- excess_levels: все подписанные разности dB;
- exceedance_points и region_count;
- regions: start_index, end_index, start_frequency_hz, end_frequency_hz,
  peak_index, peak_frequency_hz, peak_excess_db, points.

Линия постоянна: массив одинаковых threshold_levels не дублируется в ответе.
Исходный свип возвращается один раз. Частоты пиков всегда взяты из исходной
сетки, не округлены к ближайшему каналу.

Ошибки:

- 400 invalid_request: поля, типы, ID, число уровней, URL или framing;
- 404 session_not_found / sweep_not_found: сеанс или точный ID отсутствует
  в этом сеансе, чужая запись не раскрывается;
- 409 three_thresholds_incompatible: неподходящий источник, предел сетки
  или неконечная производная разность хотя бы одной линии;
- 413 request_too_large: превышен предел HTTP-тела.

features.three_sweep_thresholds сообщает поддержку в capabilities.
POST здесь передаёт параметры read-only вычисления. Нет автоматических
повторов запроса, частично сохранённых результатов или новых событий.

## Три клиента

1. Выберите сеанс и спектральный поток с записанными dBm sweeps.
2. В отдельной панели задайте три уровня dBm. Порядок полей задаёт номера
   линий, а не сортировку по уровню.
3. Нажмите анализ последнего архивного свипа. Клиент фиксирует точные
   ID, UTC, настройки, данные источника и все три переданных уровня.
4. Сверьте легенду, уровни и происхождение. Посмотрите отдельные счётчики,
   области и пики каждой линии в dB.

Редактирование любого уровня, очистка, смена сервера/сеанса/потока,
отключение или закрытие обесценивают ожидающий ответ и убирают старый
результат. Новые polling/SSE данные меняют только источник следующего действия;
готовый результат не пересчитывается автоматически. ID сравниваются точно,
без Unicode-нормализации. macOS отклоняет ответ, если разные ключи JSON
канонически эквивалентны в Unicode: Swift Dictionary не может сохранить
их одновременно без потери происхождения. Ключи не объединяются молча.
После восстановления
связи нужен новый явный анализ. Ошибка остаётся в этой панели.

WebUI и Windows ожидают не более 8 секунд, macOS — 6. Windows не гарантирует
принудительное прерывание urllib, но поздний ответ игнорируется и новые
устаревшие запросы не накапливаются в очереди. При одновременных/повторных
кликах действует один запрос.

Ответ каждого клиента ограничен 2 000 000 байтами до JSON-декодирования,
принимается только HTTP 200. Много раздельных областей трёх линий или большие
метаданные могут превысить клиентский предел даже при допустимом числе
исходных точек: результат отклоняется целиком, не обрезается. Например,
16 384 чередующихся точек с 8192 областями у каждой линии дают более
5 МБ JSON и не помещаются в клиентский предел. WebUI/Windows
показывают первые 200 областей **каждой** линии с общим счётчиком, SwiftUI
использует ленивый список. График принятого ответа сохраняет все исходные
точки. Одиночные и совпадающие точки/линии различаются по легенде и маркерам.

## Архив и пределы среза

Ядро читает ровно один свип по ID под блокировкой службы; полный архив не
загружается. Memory backend ищет в уже находящемся в памяти списке. Новых
измерений, событий, индексов, миграций, кандидатов или заданий нет. Анализ
доступен при заполненном архиве. Исходные данные, именованные эталоны,
маска и автоматические политики остаются неизменны.

Schema остаётся v3. Требование резервной копии остановленного v2 архива
перед миграцией из PR70 сохраняется. Нет сохранения/экспорта трёх линий,
объединённого детектора, комбинирования с адаптивным порогом или маской,
нормативной библиотеки и приборной валидации.

## Воспроизводимая проверка

```bash
python -m unittest discover -s tests -t .
swift test --package-path macos/SpektrKomandy
swift test --package-path macos
xcodebuild -project macos/DvoynoyObzor.xcodeproj -scheme DvoynoyObzor \
  -configuration Debug -destination 'platform=macOS' \
  -derivedDataPath macos/DerivedData CODE_SIGNING_ALLOWED=NO build
```

Реальный локальный HTTP smoke использует только собственный временный SQLite:

```bash
python -m tests.three_thresholds_smoke_server --port 56038
# В другом терминале:
ORI_THREE_THRESHOLDS_SMOKE_BASE_URL=http://127.0.0.1:56038 \
  swift test --package-path macos/SpektrKomandy
```

Фикстура three-one / spectrum-one / one-sweep-2 содержит 101 точку
100–110 MHz. При уровнях [−90, −80, −70] ожидаются [4, 2, 1] превышающие
точки и [2, 2, 1] области. Общий первый пик на индексе 30, 103 MHz:
[25, 15, 5] dB. Источник имеет ненулевые микросекунды UTC для проверки
точности происхождения. После Ctrl-C сервер проверяет неизменность полного
логического SQLite dump и очищает временный каталог.

Для WebUI smoke задайте ту же ORI_THREE_THRESHOLDS_SMOKE_BASE_URL при
запуске unittest. Для явного Tk smoke на машине с Tkinter задайте
THREE_THRESHOLDS_SMOKE_URL=http://127.0.0.1:56038. Он создаёт собственное
скрытое тестовое окно и обращается только к этой синтетической фикстуре.
Без соответствующих переменных окружения optional live HTTP/Tk тесты
пропускаются. Визуальный осмотр, Windows OS, оборудование и метрологическая
пригодность не подменяются программными синтетическими тестами.
