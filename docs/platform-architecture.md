# Архитектура платформы

В инженерных пакетах 0.4.0 узел Rust принимает команды от нескольких пультов, владеет приборными портами и пишет в общий архив SQLite. Окно выбирает проект, показывает исходники и запрашивает действия. Сеанс, занятость прибора, охрана и результат измерения принадлежат узлу и переживают закрытие окна. Для разработки из исходников остаются доступны Python-сервер, CLI и Tk. Состав реально испытанных пакетов приведён отдельно. [Состояние выпуска](release/status.md) · [Модель Python](architecture.md)

## Измерение, запись и отображение

Например, оператор настраивает AR-DV1 на частоту события, пока tinySA продолжает обзор.

1. Клиент обращается к API v1 выбранного узла. Для команды ядро проверяет режим, доступ клиента, права на конкретный сеанс и поток. Действие из очереди сохраняет разрешение исходного владельца, экземпляр исполнителя и соединение. После ожидания их проверяют снова перед обращением к прибору. Для асинхронного управления код HTTP 202 подтверждает постановку в очередь. Состояние и результат доступны по идентификатору операции. [Маршруты ядра](../crates/ori-core/src/http.rs) · [Привязка управления](../crates/ori-core/src/instrument_control/) · [Разрешения охраны](rust-guard-control-grants.md)
2. `DeviceManager` ведёт отдельный исполнитель, очередь и блокировку жизненного цикла для каждого потока. `TinySaActor` опрашивает очередное окно плана, `ArDv1Actor` настраивает приёмник и читает наблюдение. Ожидание ответа или остановка AR-DV1 оставляет очередь tinySA свободной. Для физического подключения штатному исполняемому файлу требуются сборка с `serial`, режим `live`, разрешение `--allow-serial` и явный запуск потока. При мониторинге tinySA проходит подготовку в режиме приёма с выключенным генератором. [Исполнители ядра](../crates/ori-core/src/devices/) · [Адаптеры и тайм-ауты](rust-instruments.md)
3. Исполнитель передаёт результат в `Archive::append_sweeps` или `append_observations`. Исходник несёт ID сеанса и потока, частоты в целых Гц, границы интервала в UTC и единицу прибора. Для tinySA это уровни в dBm, для S-метра AR-DV1 — исходные `s_meter_count`. Одинаковая частота позволяет связать два наблюдения. Для пересчёта уровня нужна калибровка конкретного тракта. [Приём исходников](../crates/ori-core/src/devices/mod.rs) · [Методы и единицы](measurement-methods.md)
4. Единственный писатель применяет транзакцию SQLite в режиме WAL с `synchronous=FULL`. В ней появляются исходник и запись `sweep.received` или `observation.received` с номером `sequence`. После COMMIT архив сообщает диапазон номеров, исполнитель обновляет счётчики и покрытие окна. При отказе по дисковому бюджету транзакция откатывается. Поток сообщает ошибку, отвергнутый исходник не прибавляет покрытия. Существующая база v6 сохраняет полное событие. В компактной v7 событие ссылается на массивы исходного свипа, которые читатель проверяет по SHA-256 при восстановлении ответа. Создание v7 выбирает программа установки или явная инициализация. [Писатель](../crates/ori-archive/src/writer.rs) · [Публикация после COMMIT](../crates/ori-archive/src/actor.rs) · [Форматы v6/v7](compact-panorama-events.md)
5. Ядро читает события из сохранённой последовательности и выдаёт их через SSE или согласованный WebSocket v1. У двоичного транспорта в полёте один кадр до подтверждения применения. После разрыва клиент продолжает с последнего применённого номера. График хранит ограниченную копию для показа. Карточка события открывает полный исходник по идентификаторам архива независимо от состава видимого окна. [Двоичный транспорт](../crates/ori-core/src/websocket.rs) · [Совместимость клиентов](client-core-interop.md) · [Исследование в пульте](operator-guide/index.html#research)

Нормальная остановка ядра закрывает приём новых операций, дожидается исполнителей, читателей и писателя и затем освобождает межпроцессную блокировку записи. Если закрытие не подтверждено, блокировка остаётся у процесса. Для восстановления используется отдельная проверенная копия. Выгрузка работающего архива читает согласованный снимок, пока новые измерения продолжают записываться. [Жизненный цикл ядра](rust-core.md) · [Онлайн-копирование](rust-core-backup.md) · [Экспорт снимка](rust-snapshot-export.md)

## Владельцы в Rust

В корневой Cargo workspace входят 15 крейтов. Отдельный пакет Tauri находится в `clients/windows`. В таблице указана граница, на которой следует вносить изменение или разбирать отказ. [Состав workspace](../Cargo.toml)

Режим `shadow` открывает только теневую службу, `replay` записывает в выбранный испытательный архив, `live` допускает явно подключённое оборудование. |

| [ori-automation](../crates/ori-automation/src/) | Включаемые по сеансу политики обнаружения, передачи и завершения. Проверяет исходное разрешение при применении результата. Восстановление и физические действия выполняет ядро. |
| [ori-tasks](../crates/ori-tasks/src/) | TaskBook и расписание включаемых заданий. По умолчанию планировщик ведёт программное состояние. Фактический сбор требует настроенного в ядре исполнителя и сохранённого результата. |
| [ori-audio](../crates/ori-audio/src/) | Ограниченный захват исходного моно PCM16 с явно выбранного входа, временными границами и привязкой к настройке приёмника. Доступность зависит от профиля сборки. |
| [ori-history](../crates/ori-history/src/) | Постраничное представление истории, снимки для анализа, владение фоновыми заданиями и производными выгрузками. Читает канонические данные через архив. |
| [ori-legacy](../crates/ori-legacy/src/) | Совместимость старого рабочего пространства панорам и его базы `.pan`. Выполняет исходные научные расчёты через изолированный Python-вызов. |
| [ori-contracts](../crates/ori-contracts/src/) | Типы, строгий JSON, UTC, маршруты и сгенерированные модели. Сохраняет точность и неизвестные поля на границе процессов. |
| [ori-stream](../crates/ori-stream/src/) | Кодирует и декодирует ограниченный Protobuf-кадр с номером и исходными массивами. Подписка, подтверждения и повтор из журнала принадлежат ядру. |

Контекст старой панорамы для `--database` и архив сеансов для `--session-database` задаются отдельно. При владении архивом сервер получает общую с Rust блокировку до открытия файла. Закрытие окна или смена сеанса отменяет применение запоздалого результата. [Tk-клиент](../radioinspector/windows/client.py) · [Жизненный цикл окна](windows-tk-lifecycle.md) |
| `radioinspector.research_rpc` | Дочерний процесс принимает один ограниченный JSON-запрос с отобранными ядром данными. Выполняет оригинальный алгоритм библиотеки и возвращает результат через stdout. | macOS SwiftUI | Окно связывает `RemoteDualModel`, модель проекта, навигацию, подписку и отрисовку Metal. «Наблюдение» и «Архив» используют соединение выбранного узла. Базовую схему API задаёт `radioinspector.web.openapi.document()`, расширения runtime — `runtime-extension-v1.json`, формат двоичных кадров — `measurement_stream.proto`. Генератор выпускает проверяемые OpenAPI, модели и операции Rust, TypeScript и Swift. Тестовые примеры связывают реализации по ID, целым Гц, битам float64, UTC и неизвестным полям. Наличие операции в схеме и возможности конкретного узла проверяются отдельно по `/api/v1/capabilities` и реальному запросу. [Источники и SDK](../contracts/) · [Проверка генерации](contracts-modernization.md) · [Сравнение Python и Rust по HTTP](api-parity.md)

Локальный режим использует loopback. На общей машине доступ к нему имеют также локальные процессы. Удалённый узел требует настроенного TLS, проверки Host/Origin и сопряжения. Браузер получает защищённую HttpOnly cookie того же origin. Нативные клиенты используют bearer в системном хранилище. Отзыв удостоверения прекращает доступ к защищённому потоку. Управление процессом supervisor использует отдельный приватный канал. Разрешение на работу с прибором дополнительно проверяет ядро для выбранного потока и действующего владельца. [Проверка запросов](../crates/ori-core/src/security.rs) · [Сопряжение Web/Tauri](../clients/web/SECURITY.md) · [Хранилище Mac](../macos/DvoynoyObzor/NativeCredentialStore.swift)

## Очередь небольших изменений

Сверка кода выполнена на интеграции [eb6873c1](https://github.com/qlolp/openradioinspector/commit/eb6873c104f004120a3b8361ab82edf5b38e7977). Приоритеты ниже относятся к последующей работе с кодом. Испытания на приборах ведутся по отдельному [протоколу выпуска](release/hardware-acceptance.md).

| Приоритет и граница PR | Наблюдение и ожидаемый эффект | Условие завершения |
|---|---|---|
| 1. Исправить описание чтения эталонов в API. | OpenAPI для `GET /api/v1/sessions/{id}/sweep-references` предлагает `limit` и `offset`. Python и Rust принимают только необязательный `stream_id`.
