# Общая платформа: Raspberry Pi, Windows и macOS

## Решение

OpenRadioInspector развивается как одно измерительное ядро с тремя пользовательскими оболочками:

- **Raspberry Pi WebUI** — автономный узел непрерывного наблюдения;
- **Windows GUI** — локальное рабочее место и клиент удалённого узла;
- **macOS SwiftUI GUI** — существующее нативное приложение и стенд проверки AR-DV1/tinySA Ultra.

Ядро владеет драйверами, сеансами, архивом, заданиями, обнаружением и отчётностью. Клиенты не открывают приборные порты напрямую при работе через общий сервер.

```text
AR-DV1 / tinySA Ultra / другие приборы
                    │
          независимые device workers
                    │
       общее ядро и единственный писатель
                    │
          REST /api/v1 + события SSE
                    │
       ┌────────────┼─────────────┐
       │            │             │
 Raspberry Pi     Windows       macOS
 WebUI            GUI           SwiftUI GUI
```

## Режимы развёртывания

1. **Локальный:** ядро и приборы находятся на Windows или macOS.
2. **Автономный:** ядро и приборы находятся на Raspberry Pi, управление ведётся браузером.
3. **Удалённый:** Windows/macOS подключается к ядру Raspberry Pi по сети.

Один экземпляр ядра является единственным владельцем каждого прибора. Несколько UI могут наблюдать один сеанс, но команды проходят через серверную очередь.

## Технологические решения первого этапа

- Сохраняется существующий HTTP/SSE-сервер на стандартной библиотеке Python. Дополнительная серверная зависимость на Raspberry Pi не требуется.
- Существующие маршруты `/api/*` сохраняются. Общие платформенные возможности добавляются в `/api/v1/*`.
- Доменный контракт не зависит от HTTP и может использоваться нативными клиентами, CLI и будущими адаптерами хранения.
- Служба поддерживает memory-only режим для тестов и SQLite-архив для работы. Параметр `serve --session-database` включает восстановление сеансов, событий, измерений, кандидатов и исследований после перезапуска; фактический режим виден через capabilities.
- Каждый приборный поток получает собственный исполнитель и очередь команд. Программные адаптеры `tinysa-sim` и `ardv1-sim` обеспечивают непрерывный двухприборный стенд; физическое управление отдельно обозначено как нереализованное.
- Автоматический handoff выделен в отдельный планировщик с runtime-политикой для каждого сеанса. Он выключен по умолчанию, не сохраняет политику и использует существующий жизненный цикл исследования вместо обхода блокировок или прямого доступа к приборам.
- Автоматическое обнаружение реализовано отдельным `AutomaticCandidateDetector`. Оно имеет собственный opt-in, обрабатывает только новые `dBm` sweeps и создаёт кандидатов через общий `SessionService`, не запуская handoff и не завершая исследования.
- Windows GUI реализован на Tkinter и `urllib.request` из стандартной библиотеки. Отдельный `PlatformClient` проверяет конверт и версию `/api/v1`; измерительное ядро и приборные драйверы в клиент не копируются.
- Существующее macOS-приложение не переносится и не переписывается в рамках серверного этапа.

## Общие сущности

- `MonitoringSession` — сеанс, объединяющий приборы и измерения;
- `DeviceStream` — независимый поток одного прибора;
- `Sweep` — спектральный свип с исходной единицей уровня;
- `ReceiverObservation` — настройка/наблюдение приёмника;
- `Candidate` — зафиксированный в исходных единицах кандидат на исследование;
- `Investigation` — приоритетная ручная, подтверждённая полуавтоматическая или явно разрешённая автоматическая проверка кандидата через выбранный receiver;
- `SessionEvent` — версионированное событие для SSE.

Частоты представлены целыми Гц. Все отметки времени UTC. Свип и наблюдение содержат интервал начала/окончания, поэтому потоки приборов связываются по времени, а не по номеру измерения.

## Raspberry Pi WebUI

Панель общего сеанса доступна по `/platform` и `/platform.html`. Корневой `/` по-прежнему открывает прежний интерфейс архива панорам. Панель является тонким клиентом `/api/v1`: она не открывает последовательные порты, не создаёт измерения в браузере и не подменяет ответы ядра локальным состоянием. Сеанс и его потоки создаются через API, после чего выбираются в панели.

Реализованы запуск и остановка сеанса, коллективное и независимое управление исполнителями, выбор потока спектрального обзора, отображение последнего спектра и водопада, журнал событий, создание и отклонение кандидатов, а также постановка, запуск, завершение, сбой и отмена исследования. Кнопка «Зафиксировать пик» создаёт кандидата из фактического максимума выбранного свипа и связывает его с ID этого измерения. Полоса берётся из `rbw_hz` либо оценивается по шагу частот; исходная единица уровня сохраняется. Отдельная зона полуавтоматического handoff запрашивает рекомендацию `/investigations/next`, показывает частоту, приоритет, receiver и режим, а затем отправляет ID рекомендации и `confirm=true` на `/investigations/start-next` только после действия оператора. Независимая форма автоматического handoff задаёт интервал, минимальный приоритет, receiver, задержку повтора и предел последовательных сбоев, отправляет явное `enabled=true` и отображает фактический runtime-статус; кнопка выключения не меняет остальные параметры политики. Отдельная форма обнаружения задаёт спектральный поток, порог `dBm`, интервал, частотный dedup, cooldown и лимит кандидатов на sweep. Обе политики независимы и требуют собственного opt-in.

Клиент использует только HTML, CSS, JavaScript и `<canvas>` без сетевых ресурсов и дополнительных серверных или JavaScript-зависимостей. Динамические серверные строки добавляются текстовыми DOM-узлами. Named SSE-события коалесцируются, а polling каждые 5 секунд служит резервом. Журнал запрашивает последние события относительно `health.last_event_id`; повторное обновление после занятого запроса планируется не чаще одного раза в секунду, измерительные SSE — с задержкой 1,5 секунды. Один запущенный refresh выполняет один проход, поэтому непрерывный поток свипов не блокирует отрисовку состояния приборов.

Водопад хранит до 40 последних свипов выбранного потока. Спектр отображает не более 1000 выбранных точек, обязательно сохраняя первую, последнюю и точку фактического пика; readouts показывают полные целые Гц. При построении водопада применяется max-агрегация по пиксельному столбцу, чтобы не потерять узкие пики. На узком экране три рабочие зоны складываются последовательно; цветовые состояния дублируются текстом, интерактивные цели имеют высоту не менее 44 px.

Проверен браузерный сквозной сценарий на реальном HTTP/SSE-сервере и симуляторах: запуск двухприборного сеанса, свип tinySA, фиксация пика `102500000` Гц с уровнем `−42 dBm`, постановка на AR-DV1 в `FM`, запуск и завершение с 85 связанными наблюдениями. Отдельно проверены независимая остановка каждого потока с продолжением измерений другого, отказ завершения без наблюдений, сохранение пользовательской причины сбоя, отмена, повторная постановка, отклонение кандидата и адаптивная вёрстка на ширинах 320–1180 px. Полуавтоматический сценарий дополнительно подтвердил отсутствие `started_at` до нажатия, запуск именно показанной рекомендации после подтверждения и переход рекомендации к следующему приоритету без ошибок браузера. Автоматический сценарий подтвердил состояние `queued` до opt-in, переход в `listening` после включения политики, один успешный dispatch, явное выключение и сохранение выключенного состояния после перезагрузки страницы. Сценарий обнаружения подтвердил отсутствие кандидатов до opt-in, создание ровно двух кандидатов из нового sweep после включения, отсутствие автоматической постановки исследований, прекращение обнаружения после выключения и сохранение выключенного состояния после перезагрузки; на ширине 320 px нет переполнения, цели управления не ниже 44 px, ошибок консоли и ответов HTTP ≥400 нет. Это проверки программного стенда, не физических приборов.

## Windows GUI

Модуль `radioinspector.windows` является тонким desktop-клиентом общего ядра. Команда `radioinspector-windows` и эквивалент `python3 -m radioinspector.windows` открывают Tkinter-окно и принимают `--server` с базовым URL ядра. Клиент выбирает существующий сеанс или создаёт двухприборный профиль, запускает и останавливает сеанс, все workers или отдельный stream, отправляет tune только выбранному `receiver`. Формы создают ручного кандидата или кандидата из фактического пика, ставят его в очередь, выполняют ручной и подтверждённый полуавтоматический handoff, complete/fail/cancel. Отдельные формы редактируют автоматические политики обнаружения и handoff с независимыми явными opt-in и проверкой диапазонов. Для `spectrum_analyzer` с исходными `dBm` отдельная вкладка показывает спектр и водопад реальных архивных sweeps.

`PlatformClient` принимает HTTP/HTTPS, отклоняет учётные данные в URL, ограничивает один ответ 2 МБ и проверяет `contract=openradioinspector-platform` и `contract_version=1`. Идентификаторы в путях кодируются как отдельные URL-сегменты, а фильтр `stream_id` выборки sweeps — как query-параметр. Ошибки транспорта, HTTP и контракта представляются типизированным `PlatformClientError`; частоты и приоритеты проверяются как целые Гц/значения до запроса. Модуль `workflows.py` только формирует payload: симуляторы выбираются явным opt-in, профиль без него не получает adapter, `level_unit` кандидата наследуется от источника без преобразования, а кандидат из пика ссылается на реальный `sweep_id`. Builders политик проверяют boolean, конечные числа и целые ограничения в тех же диапазонах, что API. Пустой выбор потока становится `null`; detector получает только `spectrum_analyzer/dBm`, scheduler — только `receiver`. Сохранение выключенной политики и её явное включение являются отдельными командами, выключение отправляет только `enabled=false` и не затрагивает другую политику.

Один `ThreadPoolExecutor(max_workers=1)` сериализует синхронные HTTP-операции. Future попадает в очередь сообщений только из `add_done_callback`, поэтому главный Tk-поток никогда не ждёт сетевой Future. Только он изменяет widgets. ID сеанса, потока, кандидата, исследования и экземпляр клиента фиксируются до dispatch, чтобы смена выбора не перенаправила команду и не связала sweeps с другим потоком. Treeview использует доменные ID и сохраняет выбор оператора между snapshots. Snapshot отдельно получает `/investigations/next`; кнопка отправляет именно показанный ID с `confirm=true`, а ядро отклоняет устаревшую рекомендацию. Polling выполняется каждые 2 секунды; SSE в Windows-клиенте не используется.

Snapshot запрашивает до 40 последних sweeps только выбранного `spectrum_analyzer/dBm`. Спектр Tk Canvas децимируется до 1000 точек с сохранением краёв и фактического пика; водопад PhotoImage использует max-агрегацию по не более чем 1000 пиксельным столбцам, старые sweeps находятся сверху. Повторный redraw пропускается по ID sweeps и размерам canvas, а пиксели водопада записываются одним пакетным вызовом. При выборе receiver sweeps не запрашиваются, прежнее изображение очищается, а `s_meter_count` не преобразуется в `dBm`.

Проверен desktop-сценарий на виртуальном дисплее и реальном HTTP-сервере с двумя симуляторами: подключение, запуск сеанса и обоих workers, отображение реальных `dBm` sweeps tinySA, отключённый tune для spectrum analyzer, переключение на AR-DV1 с очисткой спектра и доступным tune на `433075000` Гц в `DMR`, сохранение `s_meter_count`, возврат к tinySA с восстановлением спектра и водопада, остановка сеанса и закрытие окна. Второй полный сценарий прошёл формы создания сеанса и кандидата из пика `102500000` Гц с уровнем `−42 dBm`, очередь на AR-DV1, отсутствие запуска до подтверждения, переход в `listening` после кнопки и `completed`/`resolved` после реальных наблюдений. Третий сценарий проверил реальные формы политик: отказ `NaN` до HTTP, явное включение detector без handoff, независимое включение scheduler, выключение detector с сохранением порога и включённого handoff, затем раздельное выключение обеих политик. Это проверки GUI и программного стенда, а не Windows-инсталлятора или физических приборов.

## Режимы handoff

Оператор, внешний анализатор или явно включённый `AutomaticCandidateDetector` создаёт `Candidate`, затем оператор либо внешний контур ставит его в очередь с указанием receiver, частоты, режима и приоритета. Detector сам постановку не выполняет. Для кандидата существует не более одного открытого исследования. При ручном запуске оператор выбирает конкретную запись. При полуавтоматическом ядро рекомендует первую ожидающую запись по убыванию приоритета, затем по `created_at` и ID, но не перестраивает прибор до подтверждения актуального ID с `confirm=true`. Если очередь изменилась после предпросмотра, устаревшая команда отклоняется без tune.

При запуске ядро атомарно сохраняет `tuning`, освобождает общий lock и передаёт команду только выбранному receiver. Один receiver не выполняет два исследования в `tuning`/`listening`/`decoding` одновременно; ожидающая очередь сохраняется, а другие потоки не блокируются. tinySA продолжает писать свипы. Успешная команда переводит исследование в `listening`; ошибка — в `failed`, после чего кандидат можно поставить повторно. Завершение связывает только наблюдения целевого потока на целевой частоте не раньше `started_at`; без таких наблюдений успешный результат не создаётся. Отмена или сбой не останавливает другие приборы и не восстанавливает прежнюю частоту автоматически.

Автоматический handoff реализован отдельным `AutomaticHandoffScheduler`. Политика каждого сеанса строго opt-in и по умолчанию выключена. Она существует только в памяти процесса: после перезапуска сервер не включает её самостоятельно. Планировщик выбирает `queued` по общему порядку приоритета, применяет минимальный приоритет и необязательный фильтр receiver, пропускает занятые receiver и не блокирует независимые свободные receiver. Ручная гонка за receiver после предварительного выбора помечается `skipped`, а не засчитывается как отказ прибора.

Планировщик вызывает существующий `SessionService.start_investigation()`, поэтому не обходит проверки владельца, состояния и занятости и не удерживает глобальный lock во время tune. Автоматизируются только `queued → tuning → listening`; обнаружение кандидатов и завершение исследования остаются вне scheduler. После сбоя действует `retry_delay_seconds`, после `max_consecutive_failures` срабатывает circuit breaker и политика выключается. Проходы выполняются в отдельных dispatch-потоках с раздельными locks по сеансам, фоновый цикл создаётся лениво. Изменения политики, запуски и отключение после серии сбоев попадают в audit history/SSE.

## Автоматическое обнаружение кандидатов

`AutomaticCandidateDetector` выделяет непрерывные участки на/выше операторского порога в новых спектральных sweeps. Частота кандидата соответствует точке максимума, пик сохраняется в исходных `dBm`, `score` равен превышению порога, а интервал совпадает с интервалом измерения. Полоса оценивается по крайним точкам участка либо локальному шагу одиночной точки; это не заменяет точное измерение занимаемой полосы.

При включении фиксируется текущий конец архива, поэтому старые sweeps не порождают массовые записи. Runtime-курсор исключает повторную обработку, а активные и dismissed-кандидаты вместе с cooldown подавляют частотные дубли. Каждый результат проходит через общий `create_candidate()` и остаётся `new`; событие `automatic_detection.candidate_created` связывает его с `sweep_id`. Detector не вызывает очередь исследований, receiver или автоматическое завершение. Политика и cooldown не сохраняются, а проходы разных сеансов изолированы отдельными dispatch-потоками.

## Ограничения и безопасность

- `dBm` tinySA и `s_meter_count` AR-DV1 не сравниваются и не преобразуются друг в друга автоматически.
- Профиль устройства содержит только подтверждённые возможности. Непроверенные команды не включаются по умолчанию.
- Генератор tinySA не входит в мониторинговый сеанс.
- Отключение одного потока не должно останавливать другой.
- `SQLiteSessionStore` имеет одного писателя и сериализует транзакции. Независимые приборные очереди реализованы для симуляторов; пакетная запись и аппаратные адаптеры остаются следующими срезами.
- После перезапуска сервера архив восстанавливается, а runtime-состояния потоков сбрасываются в `disconnected`. Исполнители не перезапускаются автоматически. Активные исследования получают `failed` с событием прерывания; ожидающие остаются в очереди. Политики автоматического handoff и обнаружения не сохраняются и требуют новых независимых opt-in.
