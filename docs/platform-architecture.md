# Трёхплатформенная архитектура

## Целевая схема

```text
 tinySA Ultra ─┐                         ┌─ Raspberry Pi WebUI
               ├─ измерительное ядро ────┼─ Windows GUI
 AOR AR-DV1 ───┘        │                └─ macOS SwiftUI
                        └─ SQLite archive + event journal
```

Только ядро владеет приборами, workers и архивом. Клиенты подключаются к одному `/api/v1`, а не открывают общий последовательный порт самостоятельно.

## Общий домен

- `MonitoringSession` — сеанс мониторинга и его lifecycle `draft → running → stopped`.
- `DeviceStream` — независимый канал tinySA, AR-DV1 или будущего адаптера.
- `Sweep` — массив целых Гц и исходных `dBm` с `started_at`, `ended_at`, RBW и опорным уровнем.
- `ReceiverObservation` — частота, режим, исходный `s_meter_count`, признаки сигнала и доступности аудио.
- `Candidate` — ручной или будущий автоматический маркер частоты с источником и приоритетом.
- `Investigation` — очередная, выполняемая или завершённая ручная либо подтверждённая полуавтоматическая проверка.
- `SessionEvent` — сохранённое событие для истории, replay и SSE.

`dBm` и `s_meter_count` остаются разными величинами. Автоматическая калибровка между ними не выполняется.

## Служба сеансов и SQLite

`SessionService` — единственный координатор изменений. Создание/старт/остановка, изменение состояния потока, кандидаты, исследования, запись измерения и событие сохраняются в одной транзакции. Только после commit обновляются replay и SSE-подписчики.

Используются стандартный `sqlite3`, один защищённый RLock connection, `foreign_keys=ON`, WAL, `busy_timeout=5000`, `synchronous=NORMAL`. Схема версии 2 содержит сеансы, потоки, свипы, наблюдения, кандидатов, исследования и события.

После перезапуска сохранённые данные восстанавливаются. Runtime-потоки не пересоздаются автоматически: приборные каналы получают `disconnected`. Активные `tuning`/`listening`/`decoding` получают `failed` с `investigation.interrupted`, а соответствующие кандидаты возвращаются в `queued`.

## Независимые исполнители

Каждый `DeviceWorker` имеет собственный OS thread, очередь команд и блокировку runtime-состояния. Ошибка одного worker переводит только его в `degraded`/`error`; другой прибор продолжает измерения.

`DeviceWorkerManager` создаёт адаптер только по явному `settings.adapter`: `tinysa-sim` или `ardv1-sim`. Нет автоматического выбора по имени устройства или порту. Перестройка receiver происходит вне глобального lock `SessionService`.

Временная ошибка увеличивает счётчик и даёт `degraded`; успешное измерение возвращает `running`. После `max_consecutive_errors` завершается только сбойный worker.

## Raspberry Pi WebUI

Сервер использует существующий `ThreadingHTTPServer`, стандартную библиотеку и локальные HTML/CSS/JavaScript. React, Node и новые серверные зависимости не требуются.

`/platform` содержит три рабочие зоны: сеансы/приборы, спектр/водопад/события, кандидаты/исследования. Отдельная панель показывает рекомендацию `/investigations/next`; `/investigations/start-next` вызывается только по кнопке оператора с актуальным ID и `confirm=true`. Интерфейс не имитирует данные: он отображает только ответы `/api/v1`. Корневой `/` сохраняет прежнюю панорамную страницу.

SSE имеет named events, replay и keepalive. Постоянные measurement events объединяются в один refresh, polling-резерв выполняется раз в 5 секунд. История событий читается из SQLite. Спектр ограничен 40 свипами и 1000 точками на свип.

Браузерная проверка на реальном HTTP/SSE-сервере: создание двух workers, изменение независимых состояний, спектр и события; кандидат → queued → listening → completed/failed/cancelled; полуавтоматическая рекомендация не запускает receiver до подтверждения, после него исследование получает `listening`; отсутствие горизонтального overflow на 320 px; ноль console errors и HTTP ≥400 в проверенном сценарии. Это программный стенд, не аппаратная проверка.

## Ручной и полуавтоматический handoff

Оператор создаёт `Candidate` и `Investigation`. Ручной `start` или подтверждённый `start-next` сохраняет `tuning` до команды receiver. При успехе исследование становится `listening`, при ошибке — `failed`; кандидат возвращается в `queued` для повторной проверки.

Полуавтоматический preview только сортирует очередь по убыванию `priority`, затем `created_at` и `id`. Подтверждение повторно проверяет рекомендацию под общим lock. Устаревший ID отклоняется до `tune`. На одном receiver одновременно допускается только одно активное исследование; другие потоки и независимые receiver не блокируются.

`complete` требует подходящее `ReceiverObservation` того же сеанса/receiver, с совпадающей частотой и, если задан, режимом. Нельзя успешно завершить исследование без подтверждающего измерения. Остановка сеанса отменяет все открытые исследования. Отмена во время заблокированной настройки не перезаписывается поздним `listening`.

Состояние `decoding` зарезервировано контрактом, но публичного перехода в него пока нет. Следующий отдельный срез — автоматический планировщик с явно включаемой политикой, сохраняя ручной и полуавтоматический режимы. Автоматическое обнаружение кандидатов остаётся последующей задачей.

## Следующие направления

1. Windows GUI поверх того же `/api/v1`, без прямого доступа к приборам.
2. Адаптер macOS `/api/v1` без переписывания существующего SwiftUI-каркаса.
3. Аппаратные адаптеры только после подтверждения протоколов и стендовых испытаний.
4. Пакетная запись измерений при сохранении транзакционных событий.
5. Автоматическое обнаружение кандидатов как отдельный анализатор, не скрытый в UI.
6. Аудио, отчёты и последующая аналитика общего контура.
