# Приёмка модернизированного узла на оборудовании

Статус этого документа: **протокол, испытания не выполнены**. Результаты
синтетического release runner не заполняют строки аппаратной приёмки.
Целевые показатели приведены в [плане](plans/2026-11-11-modernization.md).

## Стенд и исходные сведения

Один Pi 5 / 8 ГиБ, SSD, tinySA Ultra, AR-DV1, выбранный аудиовход ядра;
Web, Windows и нативный macOS клиенты в гигабитной локальной сети. Записать
версии приложения, SQLite, прошивок, ОС, браузера/WebView, модель SSD и его
свободное место, питание, разрешение экрана, параметры антенн/тракта и UTC часов.
Для каждого запуска указать commit, проект, сеанс и контекст измерения.

Использовать поддерживаемые профилем диапазоны и режимы. Командное подтверждение
`mode input` / RF off регистрируется отдельно от внешнего измерения RF.
Программа не включает генератор tinySA в сценариях приёма. Эталон подтверждает
оператор после >=60 секунд и >=20 полных совместимых свипов.

Журналы, реальные измерения, адреса, серийные номера и аудио сохраняются в
закрытом каталоге результатов вне Git. Итоговый протокол содержит ссылки на
исходные ID и контрольные суммы, а не только скриншоты.

## Восьмичасовой двухприборный прогон

| Интервал | Действие | Проверяемый результат |
|---|---|---|
| 00:00–00:30 | Подготовка, эталон, явная постановка на охрану | Профили приёма, достаточный архив, RF выключен, UTC и полный контекст сохранены |
| 00:30–01:30 | Обычный фон, разрешённые несущие и изменение уровней | Исходники сохраняются; каталог и детектор дают объяснимые решения |
| 01:30–02:30 | Документированные оператором контрольные сигналы | Записать условия/число предъявлений, найденные и пропущенные события, задержки; исходники позволяют повторить анализ |
| 02:30–03:30 | Занятый AR-DV1, ручной захват/возврат, исчезновение сигнала | tinySA продолжает обзор; ручное владение видно; исчезновение не отменяет исходное обнаружение |
| 03:30–04:30 | История, исследование, сравнение и аудио в трёх клиентах | Охрана работает независимо от экранов; проверены задержки, отмена устаревших запросов и соответствие аудио частоте/режиму |
| 04:30–05:30 | Копия активного архива и параллельная аналитика | Все предъявленные измерения сохранены; рабочая память ограничена; тяжёлые задачи уступают приёму |
| 05:30–06:30 | Контролируемая потеря USB/аудио и недоступный webhook | Видимые ошибки и интервалы покрытия; старые команды не повторяются; восстановление проходит preflight |
| 06:30–07:30 | Поиск источника и возврат широкого обзора | При узком обзоре явно показана пауза широкого покрытия; возвращён подтверждённый приёмный профиль |
| 07:30–08:00 | Проверка исходников, аудио и явное снятие с охраны | Нет необъяснённых потерь/дубликатов; снятая охрана не возобновляется при старте |

Для проверки ошибок записи использовать отдельный тестовый архив/том с
контролируемой квотой. Отдельно различать логический предел архива и настоящий
ENOSPC. Проверяемый результат — остановка охраны с критической ошибкой при
невозможности сохранения, без автоматического удаления исходников.

Восстановление сначала проверять в новый файл, без запуска второго ядра с
теми же приборами. Использовать `radioinspector-archive-backup verify/restore`;
сравнить количества, ID, аудио и SHA-256. Переключение ядра и откат проверяются
в выделенном окне: остановить старого владельца, дождаться закрытия портов и
записи, отметить разрыв покрытия, затем проверить preflight и opt-in autostart.
Явное снятие с охраны и обычная остановка процесса — разные сценарии.

## Семь суток автономной работы

После восьмичасовой приёмки запустить семь **фактических** суток на отдельном
испытательном узле. Закрытие всех клиентов не прекращает запись. Снимать
память всех процессов, глубину очередей, задержки, размеры архива/WAL,
свободное место и состояние фоновых заданий минимум раз в минуту.

Ежесуточно проверять историю, согласованную копию и верификацию исходников;
однократно выполнить контролируемое восстановление процесса. Подтвердить
отсутствие повторных событий и автоматического повторения устаревших
исследований. Зафиксировать все разрывы покрытия и их причины.

Физическое отключение питания — отдельное испытание на тестовых данных с
зафиксированным типом питания/SSD и проверенной копией. SIGKILL проверяет
остановку процесса; он не доказывает долговечность при отключении питания.

## Итоговый протокол

Для каждого сценария записать `не выполнен / пройден / не пройден`, фактические
параметры нагрузки, p50/p95/max, количества предложенных и сохранённых
источников, длительность/число PCM-отсчётов, память всего приложения и причины
сбоев. Неизмеренные значения оставлять отсутствующими.

Ложные тревоги и полноту обнаружения сравнивать на одних исходниках с заранее
размеченными предъявлениями и одинаковыми каталогами разрешённых сигналов.
Указывать интервалы без покрытия отдельно. Улучшения чувствительности и
скорости публиковать только с условиями и результатами такого сравнения.
