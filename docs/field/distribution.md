# Публичная поставка OpenRadioInspector Field для Android

Google Play устанавливает `org.openradioinspector.field` из подписанного пакета приложения. Для работы без доступа к магазину GitHub Releases выдаёт универсальный APK, полученный от Google Play для того же `versionCode`. Play может установить набор APK для конкретного телефона. Универсальный файл содержит всё приложение для ARM64 с Android 12 и новее. SHA-256 файла на GitHub должен совпадать с SHA-256 универсального APK Google до последнего байта.

Поставка использует Play App Signing. Google хранит закрытый ключ подписи приложения. Издатель хранит отдельный ключ загрузки AAB. Поддержка и обращения по конфиденциальности — 9218907903@mail.ru. Издатель указывает в консоли публичный адрес политики после появления файла в основной ветке. [Политика](https://github.com/qlolp/openradioinspector/blob/main/docs/field/privacy.md) · [Карточка приложения](play-listing.md)

## Сохранение выездов со старой инженерной установки

Отладочные APK используют то же имя пакета. Сертификат может отличаться даже между двумя прогонами CI. Android отклоняет обновление с чужой подписью с ошибкой `INSTALL_FAILED_UPDATE_INCOMPATIBLE`.

1. Оставьте прежнее приложение на телефоне и завершите активный выезд кнопкой **Стоп**. Откройте каждый нужный выезд в **Архиве** и выберите **Экспортировать .orifield…**.
2. Сохраните файлы вне каталога приложения, перенесите отдельную копию на компьютер. Для **каждого** файла выполните `python3 tools/field_archive.py verify /path/to/session.orifield`. Откройте его на Mac и сверьте исходные измерения и отметки. Скопируйте также незавершённые/важные материалы, которые доступны для экспорта. При ошибке экспорта или проверки сохраните исходную установку и обратитесь в поддержку.
3. Сохраните проверенные копии. Пользователь сам решает, удалять ли прежнюю установку системными средствами после проверки всех выездов. Удаление стирает закрытую базу. На новой установке архив начинается с пустой базы, ранее экспортированные выезды доступны в просмотрщике. Установка поверх существующей production-версии в обе стороны выполняется штатным обновлением. Автоматическое удаление и очистка данных в этих инструментах отсутствуют.

## Подготовка издателя

Верифицируйте аккаунт Play Console и устройство, создайте бесплатное приложение и включите Play App Signing с ключом, который создаёт Google. Запишите **оба** открытых отпечатка SHA-256 со страницы целостности (сертификат подписи приложения и сертификат загрузки). Отключите автоматическую защиту Play с проверкой установщика, чтобы автономный запуск работал вне Play. Новый личный аккаунт проходит закрытый тест, обычно от 12 участников, подключённых непрерывно не менее 14 дней. Зафиксируйте фактические условия в консоли, отзывы и решение о доступе к production. Издатель заполняет Data safety и декларации служб и прикладывает видео, политику и контакт. [Требования к тестированию](https://support.google.com/googleplay/android-developer/answer/14151465) · [Подпись приложений](https://developer.android.com/studio/publish/app-signing) · [Декларация foreground service](https://support.google.com/googleplay/android-developer/answer/13392821)

В настройках GitHub разрешите deployment только из защищённой `main`. Храните резервную копию upload keystore и паролей у издателя. Для всех трёх environments задайте переменные `FIELD_PLAY_CERT_SHA256` и `FIELD_UPLOAD_CERT_SHA256` из Play Console. Отпечаток состоит из 64 шестнадцатеричных цифр, допускается обычная запись с двоеточиями. Если Google показывает свой сертификат только после первой загрузки, для первого внутреннего AAB задайте в signing окружении проверенный отпечаток загрузки и максимум 0. Сразу после регистрации пакета закрепите отпечаток Google во всех трёх окружениях. Приёмка и публикация всегда требуют двух разных отпечатков.

| GitHub environment | Доступ |
| --- | --- |
| `android-field-signing` | Секреты `FIELD_UPLOAD_KEYSTORE_B64`, `FIELD_UPLOAD_ALIAS`, `FIELD_UPLOAD_STORE_PASSWORD`, `FIELD_UPLOAD_KEY_PASSWORD`. В `FIELD_PLAY_MAX_VERSION_CODE` сохраните наибольший уже загруженный код со всех треков Play, включая внутренние и снятые с выпуска. До первой загрузки укажите `0`. |
| `android-field-review` | Переменные `FIELD_GOOGLE_WIF_PROVIDER` и `FIELD_PLAY_SERVICE_ACCOUNT`. Закройте доступ к токену за защищённым environment. |
| `android-field-publication` | Те же две переменные Google, обязательное ручное одобрение, права на GitHub Releases. Для проверки immutable releases нужен доступ Administration read. Поддерживаются переменная `RELEASE_APP_ID` и секрет `RELEASE_APP_PRIVATE_KEY` приложения GitHub с Contents write, Actions read и Administration read либо принятые проектом `RELEASE_PUBLISH_TOKEN` и `RELEASE_POLICY_READ_TOKEN`. В настройках репозитория включите immutable releases. |

Включите Google Play Android Developer API, привяжите выделенный сервисный аккаунт к этому приложению и дайте доступ к чтению треков, bundles и сгенерированных APK. Workload Identity Federation выдаёт короткоживущий токен с областью `https://www.googleapis.com/auth/androidpublisher`. Ограничьте доверие вашей организацией, репозиторием, защищённой `main`, путём workflow `.github/workflows/android-field-release.yml` и двумя environments чтения. Для чтения версии и треков API открывает временный edit и удаляет его в конце. Не используйте эту служебную учётную запись для параллельного редактирования карточки или релиза. Публикацию в Play выполняет владелец через консоль. [Generated APKs](https://developers.google.com/android-publisher/api-ref/rest/v3/generatedapks/list) · [Доступ к API](https://developers.google.com/android-publisher/getting_started)

## Сборка и загрузка AAB

1. Из защищённой `main` запустите **Sign Android Field upload bundle** и **Android Field** при одном SHA исходников. Дождитесь успешного эмулятора и импорта его экспорта на Mac. Для выпуска используется закреплённая в проекте версия JDK (17), Gradle, AGP, Kotlin, Rust, Android API 36, Build Tools 36.0.0 и NDK 28.2.13676358. Rust-сборка использует `Cargo.lock`; APK/AAB проходят проверку каждой AArch64 ELF-библиотеки и страниц 16 КиБ.
2. Публичный `versionName` хранится как `fieldVersionName` в `clients/android/gradle.properties`. Новый запуск workflow получает `versionCode = fieldVersionCodeBase + GITHUB_RUN_NUMBER`. При начальной базе 1 первый запуск получает 2. Повторная попытка того же запуска сохраняет код. После сброса счётчика или переименования workflow увеличьте базу в ревью так, чтобы результат превосходил все ранее загруженные коды. Для следующего публичного тега увеличьте также `fieldVersionName`. При локальном повторении сборки передайте `./gradlew --no-daemon -PfieldVersionCode="$CODE" :app:bundleRelease` из `clients/android`.
3. Скачайте артефакт `android-field-upload-<run-id>-<attempt>`, проверьте `sha256sum -c SHA256SUMS`. Сохраните именно этот `field-upload.aab`, контрольные суммы, SHA исходников, номер запуска и попытки. JAR-подпись содержит данные о моменте подписания. В Play загружается зафиксированный файл. После загрузки обновите `FIELD_PLAY_MAX_VERSION_CODE`. Для повтора используйте сохранённые байты. Номер версии, который Play уже принимал, не выделяется повторно.
4. Начните с внутреннего трека. Для **первого** публичного выпуска подготовьте два разных возрастающих кода. На более низком коде проведите подготовку данных и установите версию из Play заранее, пока она доступна тестовому устройству. Следующий запуск выдаст более высокий код для кандидата. После первого публичного выпуска исходной версией для испытания служит предыдущий публичный Android-релиз.
5. Из **App bundle explorer → Downloads → Signed, universal APK** сохраните файл нижнего кода и файл кандидата. Перед установкой задайте окружению оба публичных отпечатка сертификатов и `ANDROID_HOME`, затем проверьте пакет, например `python3 -m tools.field.android_release verify-apk candidate.apk 0.1.0 "$CODE"`. Команда проверяет подпись, идентификатор, версию, отсутствие debug/test, запрещённых разрешений и обязательных splits, выравнивание APK и ELF. Сохраните напечатанный SHA-256.

## Проверка перехода между каналами

Используйте два тестовых S22 Ultra с закрытыми выездами либо последовательно подготовленные отдельные тестовые устройства. Для первой установки APK без сети используйте отдельный чистый тестовый телефон. Рабочие данные оператора сохраняются согласно разделу выше. В приватном журнале запишите модель, Android, One UI, сборки, источник установки и дату. На устройстве для каждого направления создайте свой учебный выезд с измерением и заметкой.

* **Play → универсальный APK.** Установите нижний код из внутреннего трека, экспортируйте выезд. Снимите исходный отчёт. Отключите сеть. Выполните команду `sideload-update` ниже. Она повторно проверяет открытую установку, экспорт и подпись кандидата, затем выполняет единственную операцию записи — `adb install -r`. Подтвердите обновление при запросе Android и сохраните протокол операции. Откройте тот же выезд и отметку, повторите экспорт и снимите итоговый отчёт.
* **Универсальный APK → Play.** Установите нижний универсальный APK, создайте и экспортируйте выезд, снимите исходный отчёт. После выдачи более высокого кода тестовой записи откройте карточку в Play, нажмите **Обновить**, откройте старый выезд и повторите экспорт и отчёт. Сохраните версию и установщика. Оба направления требуют действительного повышения кода.
* **Автономная чистая установка.** На чистом тестовом телефоне отключите мобильную сеть и Wi-Fi, установите файл по USB или через локальный файловый менеджер, запустите приложение и запишите/экспортируйте учебное измерение. Сохраните SHA-256 отчёта и фактический результат. Проведите также три двухчасовых аппаратных выезда из протокола и сохраните приватные отчёты. [Приёмка на S22 Ultra](release.md)

Для каждого наблюдения перенесите свежий экспорт на компьютер. Команда `observe` читает состояние через ADB, вытягивает установленный base APK, сверяет его подпись и полностью проверяет экспорт. Время установки и идентификатор устройства из приватных наблюдений в публичный протокол не включаются. Хеш выезда учитывает идентификаторы и содержимое всех проверенных записей и устойчив к изменению временных меток ZIP. Используйте корень репозитория и задайте значения переменных для своих устройств и файлов.

```sh
python3 -m tools.field.android_upgrade observe "$SERIAL" before.orifield > before.json
python3 -m tools.field.android_upgrade sideload-update "$SERIAL" before.orifield before.json \
  "$VERSION_NAME" "$CODE" candidate.apk > transaction.json
# Откройте выезд после обновления и заново экспортируйте его в after.orifield.
python3 -m tools.field.android_upgrade observe "$SERIAL" after.orifield > after.json
python3 -m tools.field.android_upgrade compare play_to_apk before.json after.json \
  "$PREVIOUS_CODE" "$CODE" previous.apk candidate.apk --transaction transaction.json > play-to-apk.json
```

Для обратного направления снимите наблюдения вокруг кнопки **Обновить** в Play и вызовите `compare apk_to_play` с теми же позиционными аргументами, опустив `--transaction`. На исходной автономной установке регистрируется установщик, отличный от Google Play. Сравнение требует постоянного `firstInstallTime`, увеличения кода, одинакового хеша выезда, установщика Google Play на соответствующей стороне и точных байтов одиночного APK на другой. Храните `before.json`, `after.json`, `transaction.json` и экспорты у оператора.

## Приёмка и публикация

```sh
python3 -m tools.field.android_release receipt-template "$SOURCE_SHA" "$BUILD_RUN" "$CODE" \
  field-upload.aab candidate.apk "$PREVIOUS_CODE" previous.apk > field-acceptance.json
```

Заполните поля `model`, `android_api`, вставьте результаты `compare` в `play_to_apk` и `apk_to_play`. Укажите `passed`, длительности и SHA-256 соответствующих приватных отчётов для трёх выездов и чистой офлайн-установки. В свидетельство входят только поля шаблона. В нём отсутствуют маршруты, идентификаторы устройств и личные заметки.

```sh
gh workflow run android-field-release.yml --ref main \
  -f build_run="$BUILD_RUN" -f test_run="$ANDROID_FIELD_TEST_RUN" \
  -f receipt_b64="$(base64 < field-acceptance.json | tr -d '\n')"
```

Этап **review** находит точные успешные прогоны в этом репозитории, сверяет SHA-256 загруженного AAB с Google Play, получает `generatedUniversalApk` у Play и проверяет оба фактических APK, отпечатки, версии и свидетельство. Незавершённый тест или отсутствующий пакет останавливает процесс. В сводке Actions рецензент сверяет хеши с оригиналами. Ограничение GitHub на ожидание environment approval — 30 дней, поэтому длительный закрытый тест лучше закончить до запуска review.

Получив доступ к production, владелец продвигает в Play **этот же AAB**, дожидается полного выпуска и проверяет реальную установку из публичной карточки. Рецензент одобряет `android-field-publication` после этой проверки. Публикация повторно сверяет SHA-256 AAB и полностью развёрнутый production-трек через API и требует, чтобы кандидат имел наибольший обслуживаемый код. Она создаёт отдельный неизменяемый релиз `android-field-v<versionName>` на SHA подписанной сборки с универсальным APK, файлами `android-field-release.json`, `android-field-acceptance.json` и `SHA256SUMS`. GitHub сверяет SHA-256 каждого загруженного файла. Вручение APK и контрольных сумм для автономной установки выполняется после этого шага.

Получатель скачивает активы одного Android-тега, проверяет `sha256sum -c SHA256SUMS` (на Mac — `shasum -a 256 -c SHA256SUMS`) и сопоставляет SHA-256 сертификата из `apksigner verify --verbose --print-certs` с опубликованным отпечатком Play App Signing. Передача целого APK на телефон по USB позволяет установить его системным установщиком без сети.
