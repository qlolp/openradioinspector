# Двойной обзор для macOS

Нативное окно macOS для общего сеанса AOR AR-DV1 и tinySA Ultra. Основной режим является тонким клиентом `/api/v1`: приборами, workers и архивом владеет сервер OpenRadioInspector. Окно не открывает `/dev/cu.*`, не отправляет `scan`, `RF` или `LM` напрямую и не создаёт измерительные данные.

Уровень AR-DV1 остаётся в `s_meter_count`, уровень tinySA — в `dBm`. Автоматического пересчёта между ними нет. Цифровой сигнал декодирует приёмник, а не SwiftUI-клиент.

## Запуск

Нужны macOS 14 или новее и Xcode с поддержкой macOS 14.

1. Запустить ядро на Mac, Raspberry Pi или другом доступном хосте:

   ```bash
   python3 -m radioinspector serve --host 127.0.0.1 --port 8770 \
       --session-database /path/to/sessions.sqlite
   ```

2. Открыть [`DvoynoyObzor.xcodeproj`](DvoynoyObzor.xcodeproj), схему **DvoynoyObzor**, Run.
3. В окне указать адрес ядра, например `http://127.0.0.1:8770`, и нажать «Подключить».
4. Выбрать существующий сеанс или создать новый `draft`.

Кнопка «Новый с симуляторами» является отдельным явным opt-in и добавляет только `tinysa-sim` и `ardv1-sim`. Обычный «Новый draft» не назначает адаптеры, не открывает порты и не включает `hardware_control`. Аппаратный профиль и его запуск выполняются ядром после отдельной настройки.

## Что реализовано в remote-срезе

- Нормализация базового URL, отклонение credentials/query/fragment, проверка `contract=openradioinspector-platform` и `contract_version=1`.
- Типизированные Codable-модели сеансов, потоков, workers, sweeps, receiver observations, кандидатов, исследований и runtime-политик; ответ ограничен 2 МБ после загрузки.
- ID сеансов и потоков кодируются как отдельные URL-сегменты; `stream_id` кодируется как query-параметр.
- Создание и выбор сеанса, start/stop сеанса, start/stop всех workers и независимые start/stop каждого потока.
- Polling каждые 2 секунды вне блокировки главного потока. Поздний ответ прежнего сеанса отбрасывается по ID и generation.
- Ошибка или превышение лимита ответа одного workflow-списка изолируется и показывается отдельно; она не блокирует обновление workers, sweeps и observations. Сброс фильтра receiver/analyzer кодируется явным JSON `null`, а не пропуском поля.
- Спектр, минимальная/максимальная огибающая и водопад только из последних 40 архивных `dBm` sweeps. Повторно полученный ID не добавляется в водопад второй раз.
- Последнее наблюдение AR-DV1 с исходным `s_meter_count`, режимом, шумодавом и интервалом измерения.
- Перестройка только `receiver` по фактическому пику sweep или выбранному превышению. Частота отправляется целым числом Гц; tinySA при этом не останавливается.
- Закрытие окна отключает polling и UI, но не останавливает сеанс ядра и не закрывает приборы.
- Создание кандидата только из фактического архивного `dBm` sweep: частота пика, интервал, исходный уровень и ID измерения сохраняются без выдуманной занимаемой полосы.
- Отдельный serial-профиль с явными портами и адаптерами `tinysa-serial`/`ardv1-serial`: порты обязаны различаться и не использовать `sim://`; обычный draft и симуляторы не изменяются. Профиль не объявляет `hardware_decode`: serial-адаптер принимает только FM/AM и не подтверждает цифровое декодирование.
- Постановка и отклонение кандидата, ручной start, complete/fail/cancel и полуавтоматический запуск следующего только с `confirm=true` для актуального ID рекомендации.
- Независимые automatic detection и automatic handoff с проверкой диапазонов, раздельными действиями «Сохранить», «Включить явно» и «Выключить». Включение доступно только в running-сеансе; выключение отправляет только `enabled=false` и не отменяет активное исследование.

Automatic detection создаёт только `new`-кандидатов, automatic handoff автоматизирует только `queued → tuning → listening`. Автоматического complete нет. Политики runtime-only и после перезапуска сервера требуют нового opt-in. Remote-клиент не объявляет аппаратное подключение проверенным: для физических приборов нужен настроенный серверный адаптер и отдельный стенд.

## Проверки

Тесты HTTP-клиента находятся в `SpektrKomandyTests/PlatformAPITests.swift` и `SpektrKomandyTests/PlatformWorkflowTests.swift`. Они используют `URLProtocol` и не открывают приборные порты:

```bash
cd macos/SpektrKomandy
swift test
```

Тесты моделей окна и жизненного цикла:

```bash
cd macos
swift test
```

`RemoteSessionTests` входят в существующий `SessionTests.swift`; закрытие remote-окна проверяется без остановки серверного сеанса. Старые scripted transport и Unix socket тесты сохранены для прежней реализации низкоуровневых кадров.

В среде подготовки установлен Swift 6.0.3: пакет `SpektrKomandy` компилируется, все 41 его XCTest проходят, включая API, workflow и serial-профиль. Каждый test case запускается в отдельном процессе на Linux во временном каталоге вне FUSE worktree; это устраняет зависания общего XCTest runner. Полное AppKit-приложение и Xcode-схема на этом хосте не собираются: для них нужны macOS и Xcode. Аппаратная проверка remote UI также не выполнялась.

## Сохранённый низкоуровневый каркас

Прежние `ArModel`, `UltraModel`, `SerialPort`, `ArPane` и `UltraPane` сохранены как исходная реализация приборных кадров и тестов, но основное `ContentView` их не создаёт. Это не второй измерительный путь текущего приложения.

Ранее на физическом tinySA Ultra (`tinySA4_v1.4`, плата `ZS405`) были подтверждены низкоуровневые свойства исходного каркаса: CR (`0x0D`) в конце команды, приглашение `ch> `, ответы `info`/`version`/`deviceid`, последовательность настройки с `output off`, а также формат `scan` из 290 строк по 3 столбца. Это подтверждение относится к прежнему последовательному транспорту, а не к новому remote UI и не к серверному hardware adapter.

По-прежнему не заявляются калибровка S-метра в dBm, запись звука, автоматическая классификация, точная занимаемая полоса, TETRA/GSSI как проверенные возможности remote-клиента или автоматическое завершение исследований.
